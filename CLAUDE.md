# CLAUDE.md

> This file is the public edition of the working agreement the AI coding agent (Claude Code) operated under while this project was developed. The agent wrote and maintained it, from an analysis of how the author worked with it and what the code needed. It is not a verbatim copy. The behavioral sections (the default code-change workflow, rigor and self-skepticism, the honest-completion protocol, code style, the craft policy) stay close to what the agent worked under. The reference sections (architecture, environment variables, key design decisions, testing, deploy) were rewritten for this release so that they describe the published code, including the changes the pre-release review made (`docs/PRE_RELEASE_REVIEW.md`). Private details (people, customers, infrastructure identifiers, internal trackers) were removed. It is kept because it shows how the project was built with an agent: what the agent was told to treat as load-bearing, how it was told to verify its own work, and how it was told to report.

## Project: Craft & Ship

Craft & Ship is an agentic web-app creation platform. Customers describe a web app in plain English through a chat intake flow. The platform produces a structured JSON spec, builds the app, tests it and deploys it to Railway. Three product words mean less than they suggest: **preview** and **live** are statuses in the platform database (a preview is a public site, and marking a build live changes nothing on it), and **review** is a verdict recorded on the build row (a human reviewer by design; see the note under Craft Quality Policy for the automated review mode added in June 2026). `SECURITY.md`, "Preview, review and live", has the definitions.

The system ran in production from March to July 2026 and was then wound down; this repository is the archived codebase.

Two build engines exist side by side:

- **v1 (`cli/`)**: a Claude-driven pipeline. Claude Opus generates the app, then 117 registered deterministic post-processors (`@processor` functions in `cli/build.py`), a QA fix loop, and a design-review loop patch its output. Legacy; kept for forensics.
- **v2 (`compose/`)**: a deterministic static-compose engine. No AI in the build path: archetype, palette, font pair and layouts are chosen from curated JSON decision files and rendered through unit-tested EJS widgets. AI stays in the intake and Harbor conversations and in spec extraction; it does not write the code that ships. The code default is `CAS_BUILD_ENGINE=v2` (`queue/worker_pg.py`).

## Tech Stack: `web/`

Node (CI runs 24; no other version is tested), TypeScript strict, Express with `express-ejs-layouts`, EJS views. PostgreSQL via `pg.Pool` (raw parameterized SQL, no ORM). Auth: `express-session` + bcrypt + `connect-pg-simple`, with an HMAC CSRF token behind a global cross-origin write guard (see Key design decisions). Email: Resend REST over Node fetch (no SDK). Payments: Stripe Checkout. AI: Anthropic Claude API. CSS: Tailwind 4, built by its CLI (`@tailwindcss/cli`) without cascade layers so the views' own `<style>` blocks keep Tailwind 3's cascade (the top of `web/src/styles/input.css` says why). Tests: Vitest (unit) and Playwright (UI).

`app.ts` exports the Express app without binding a port (used by supertest). `server.ts` runs the migrations, binds the port (a port already in use is one log line and exit 1, `web/src/utils/listen.ts`) and only then starts the background jobs. `instrument.ts` initializes Sentry and must be the first import in `server.ts`.

Key files: `web/src/middleware/auth.ts` (`requireAuth`, `resolveSessionSecret`, `isAdminSession`, `isDevOrTestEnv`, `generateCsrfToken`, `validateCsrfToken`, `rejectCrossOriginWrites`), `web/src/middleware/anon-rate-limit.ts`, `web/src/middleware/auth-rate-limit.ts`, `web/src/middleware/companion-rate-limit.ts`, `web/src/db/schema.sql`, `web/src/db/migrate.ts`, `web/src/types/index.ts`. Route catalog: `ls web/src/routes/`. View catalog: `ls web/views/`.

**Harbor module map** (the "Haven" companion surface; detail archive in `docs/internals/HARBOR_IMPLEMENTATION_NOTES.md`; plans in `docs/CAS_HARBOR_PHASE_1_TECH_PLAN.md`, `docs/CAS_HARBOR_PHASE_2_TECH_PLAN.md`, `docs/CAS_LIVING_PLATFORM_TECHNICAL_ARCHITECTURE.md`):

- `web/src/companion/`: the runtime. `runtime.ts` (turn lifecycle), `persona.ts` and `persona-sections.json` (persona prompt and per-keeper context; the persona may describe the keeper's notes only plainly and is told never to claim encryption, therapist-level confidentiality or scheduled deletion), `ai_honesty_rail.ts` (deterministic regex rails: `dangerous` output flags replace the reply, `hygiene` flags sanitize in place), `crisis_detection.ts` (the regex crisis scan and the fixed script; the alert email to `ADMIN_EMAIL` and the stored turn are bounded by `crisisSideEffects` in `runtime.ts`, and an email failure never breaks a turn), `memory_capture.ts` and `memory_retrieval.ts` (Haiku classifier plus optional OpenAI embeddings; both degrade to a "lite" mode without `OPENAI_API_KEY`), `claude.ts` (SDK wrapper with prompt caching and a per-turn cost log).
- `web/src/middleware/trial-cookie.ts`: cookie identity for trial conversations. The cookie is an opaque random bearer token (32 random bytes, hex), not a signed value; the `trial_keepers.cookie_token` lookup is the whole validation. Mints `trial_keepers` rows, with a per-address cap on how many. Outside development and test the cookie is named `__Host-cas_harbor_trial` (`hostOnlyCookieName` in `web/src/middleware/auth.ts`; the session cookie is `__Host-cas.sid` the same way). Its value is replaced when the trial's first address is recorded (`rotateTrialCookie`, called from `lighthouse.ts`) and, after a payment releases the trial, once on the paying browser's next request (`resolveTrial`, `trial_keepers.cookie_rotated_at`); that cookie then identifies the paying browser for 30 days (`req.harborPaidKeeper`), and only if that trial was promoted into that keeper (`trial_keepers.promoted_customer_id`, read through `PROMOTED_KEEPER_OF_TRIAL_SQL`): it reaches the lamp pages of the one build it paid for and the conversation, it cannot cancel the subscription (that takes the account's login), and it is not an account session. It yields to the browser's account session (a browser logged in to another account gets a fresh trial in its place), logout clears it, and a completed password reset or email verification of the paid account expires it.
- `web/src/routes/lighthouse.ts`: the keeper surface, mounted only when `CAS_HARBOR_ENABLED=true` (chat at `/lighthouse/table`, template picker, build status and the make-public Stripe subscription flow). "Lighthouse" is the product's route name, not Google Lighthouse. It exports `crisisFirst`, which `app.ts` also mounts on `POST /lighthouse/table/turn` ahead of the session middleware. `resolveCompanionIdentity` decides whose conversation a request reads and writes (the keeper of an account session; for a logged-in account with no keeper row, its own unreleased trial; otherwise the keeper whose paying cookie it carries, else the cookie's trial); the crisis handler is the one writer that does not use it and files its turn from the trial cookie alone.
- `web/src/routes/admin.ts`: `/admin/harbor` inbox (unreleased trials; `?status=keepers` lists paid keepers; every view also lists "Payments needing a person", the recorded subscriptions no keeper row uses, `PAYMENTS_NEEDING_A_PERSON_SQL`) and the manual dispatch route, which dispatches through `dispatchHarborTrialBuild` (a captured address under the anonymous rule; the operator's own account only when the trial captured none). The review verdict routes record a verdict only on a build at `preview` (409 otherwise).
- `web/src/routes/webhooks.ts`: Stripe events, one database transaction each (the idempotency claim in `processed_webhooks` commits or rolls back with the handler's work); the checkout handler for `metadata.kind = harbor_make_public`, which locks the build row and holds one of the three statements that write `live` (the owner's and the admin's approve statements in `builds.ts` are the others); subscription lifecycle events mirrored into `harbor_subscriptions` and the keeper row (Stripe's status word for word), with late events skipped by `last_event_created` and events for a deleted account acknowledged through `harbor_subscription_tombstones`; the Resend delivery webhook; and an optional `POST /webhooks/build-status` hook (bearer `WORKER_WEBHOOK_SECRET`) that accepts only pipeline statuses, never `live`, puts the build back into review when it writes `preview` (as `pending`, or `ai_review_queued` under `CAS_HARBOR_AUTO_REVIEW`, the worker's decision), and that the bundled worker does not call (it writes Postgres directly). A payment the checkout handler cannot apply (a second trial's session for an account whose keeper already has a subscription, a trial that is not the build's own, a build that is no longer publishable, a session no login of the account opened for a verified account, a trial's session for an account its dispatch did not create) is recorded in `harbor_subscriptions`, commits, answers 200, mails `ADMIN_EMAIL` (`reportUnappliedPayment`) and is listed on `/admin/harbor`; nothing is refunded. A paid session whose metadata it cannot read is mailed the same way, with nothing recorded.
- `web/src/services/`: `harbor_dispatch.ts` (conversation to build: `insertHarborBuild` sets `builds.is_harbor`, `handoff_at` limits a conversation to one build without an operator, and a dispatch counts against the customer's build-start limits (an anonymous dispatch attaches only to an account row it creates in its insert transaction, refusing any existing account: `account_exists` or `address_in_use`; `builds.owner_created_by_dispatch` records it); the visitor's, the keeper's and the operator's dispatch answer a failed extraction from one table, `dispatchFailureResponse`), `keeper_promotion.ts` (trial-to-keeper promotion inside the webhook's transaction; it also extends the released trial's cookie window, and `PUBLISHING_SUBSCRIPTION_STATUSES` there is the one list of subscription statuses that publish; a trial is promoted only into an account whose keeper has no subscription of its own, in the one statement that writes the keeper row, `claimKeeperSubscription`, and only into the account its dispatch created (`builds.owner_created_by_dispatch`) or the payment created, unless the account's login or paying cookie opened the session), `spec_extraction.ts`, `harbor_to_compose.ts` (pure deterministic translator from the extracted spec to the v2 compose input; it resolves what the engine would refuse toward less exposure, with warnings), `site_copy_crawl.ts` with `site_copy_parse.ts` (the admin-triggered crawl; fetched HTML is parsed in a worker thread), `stripe.ts`, `template-families.ts`, `funnel-events.ts`.
- Harbor schema: `trial_keepers`, `keepers`, `companion_turns`, `keeper_memory` (partitions working, sacred, voice), `companion_cost_log`, `harbor_subscriptions`, `harbor_subscription_tombstones`, `funnel_events`, and the column `builds.is_harbor` with its trigger `builds_inherit_is_harbor`. Schema additions are written to be re-applied at every boot. No pgvector; cosine similarity runs in JS at MVP scale.

## Running the web app locally

Requirements: Node (CI runs 24; no other version is tested; `.nvmrc` and the `engines` field of `web/package.json` name it), PostgreSQL (the repo's `docker-compose.yml` provides one) and, for the Python side, Python 3.12 (what CI runs, named by `.python-version`; 3.13 cannot install `playwright==1.42.0`'s `greenlet`). The published results were measured on macOS with Node 25 and a Python 3.12 virtualenv. The worker image is a different set of versions again (`Dockerfile.worker`: the Playwright 1.42.0 image on Ubuntu 22.04 with the Python it ships, which is 3.10 for that release, Node.js 20, a PostgreSQL 15 client and Railway CLI 4.31.0) and was not built or run when the release was prepared (the `worker-image` job of `test.yml` builds it). With the placeholder `SESSION_SECRET` from `web/.env.example` the dev server generates a random per-process secret and says so at boot, so logins do not survive a restart until you set a real one (`openssl rand -hex 32`).

```bash
docker compose up -d --wait                  # Postgres from docker-compose.yml, matching web/.env.example
                                             # (or: createdb craftandship_web against your own Postgres)
cp web/.env.example web/.env                 # the DATABASE_URL in it matches the compose database
cd web && npm ci
npm run dev                                  # node --watch + ts-node on port 4000
# or: npm run build && npm start             # compiled server (runs css:build and tsc)
```

Local login: register an account at `/signup`. With no `RESEND_API_KEY` set, outgoing email is logged as `skipped` rather than sent, but in development or test the server prints the verification link to its console (`logDevEmailLink` in `web/src/services/email.ts`: `[dev] Email is not configured. Verification link: ...`); open it in the browser you signed up in and press the button on the page it shows, to verify the account and be logged in (confirmed in any other browser it verifies the account and asks you to choose a password). Password-reset links are printed the same way. Without `ANTHROPIC_API_KEY` the chat routes answer 503 with a message saying the assistant is not configured (`web/src/utils/assistant.ts`), and so do `POST /lighthouse/build` and the operator's dispatch (code `assistant_not_configured`, `respondAssistantNotConfigured`), but only once they get as far as the model: a fresh conversation is first asked for an email (402) and told it is not ready (409) until it holds four turns the extraction may read, so on a fresh checkout without a key expect the 402 and the 409 from a browser (a client the server classes as a crawler, plain `curl` for example, is answered 403 `bot_blocked` instead); `web/.env.example` ships `CAS_HARBOR_ENABLED=true`, so `/try` and `/intake` redirect into the Haven conversation. Set `ADMIN_EMAIL` in `web/.env` to that account's email, written in lower case (customer emails are stored lower-case and the comparison is exact), to reach `/admin/*`. The session must have been established by a password login or by that verification link (that is what stamps `authenticatedAt`); see Admin access below.

Other commands (see `web/package.json` and `Makefile`): `npm test` (Vitest, no database needed), `npm run test:ui` (Playwright; needs a seeded Postgres and a free port, see Testing), `npm run css:watch`, `make test` (pytest on `tests/` and `compose/tests/`), `make test-web`, `make hooks` (enable the repo's git hooks), `make verify-hooks`.

## Environment variables

Names and meaning only; never commit real values.

**Web app:** every variable the server reads is listed, with what happens when it is unset, in `web/.env.example`. Required to boot: `DATABASE_URL`, and `SESSION_SECRET` outside development and test. `ADMIN_EMAIL` is not needed to boot, but with it unset nobody is admin, the alert emails are skipped and the contact form answers 503 instead of sending. `NODE_ENV` matters beyond convention: only the exact values `development` and `test` count as development (`isDevOrTestEnv()` in `web/src/middleware/auth.ts`), and anything else, including unset, gets the production behavior (Secure cookies, HSTS, no error detail, a real `SESSION_SECRET`, every development bypass off). Only Railway writes from the admin pages (`isRailwayWriteEnabled`) key on `NODE_ENV` being exactly `production`; an unset value refuses them, the safe direction. TLS to a remote database (`poolSslOption` in `web/src/db/tls.ts`) and the boot warning about an unset `BASE_URL` follow `isDevOrTestEnv()`: both apply unless `NODE_ENV` is exactly `development` or `test`. Web variables that gate a safety control are described under Key design decisions below.

**Worker** (`queue/worker_pg.py`, `queue/mailer.py`, `cli/`, `compose/`; the worker reads its own environment, not `web/.env`):
- `DATABASE_URL`: the same database the web app uses (required).
- `CAS_BUILD_ENGINE`: `v2` by default; `v1` only for repro and forensics (also lifts the v1-only test skip in `conftest.py`).
- `MAX_CONCURRENT_BUILDS` (default 1); `DAILY_API_SPEND_CAP` (default 50 USD, 0 disables; fails closed if the spend query errors). The cap sums the recorded model spend of builds worked on today, which only the v1 engine records: under v2 the figure is 0 and the cap never triggers.
- On/off switches of the worker, `cli/deploy.py`, the ops agent and the coordinator are read by `coordinator/envflags.py` under one rule, in `docs/THREAT_MODEL.md`, "Escape hatches": a safety switch (a dry run, analysis only, a blocking gate) is turned off only by `false`, `0`, `no`, `off` or `disabled`, and an arming switch is turned on only by `true`, `1`, `yes`, `on` or `enabled`. A value that is neither leaves the switch in its safe state. The bullets below give each switch's default.
- `ENABLE_ORPHAN_SWEEP` (off by default): the Railway orphan sweep does nothing unless this is switched on; it stays off (see Deploy).
- `CAS_HARBOR_AUTO_REVIEW` (off by default): when on, a build that arrives at preview enters review as `ai_review_queued` instead of `pending` and no admin email is sent; nothing in this repository consumes that state. The worker and the web app's optional status hook read it with the same arming rule.
- `USE_MAGIC_LINK_AUTH` (default on): generated apps log in by magic link. Every reader (the worker, `cli/deploy.py`, `cli/build.py`, `cli/test.py`) parses it with the one safety switch, so any spelling gives one answer.
- `BLOCKING_DESIGN_REVIEW`, `BLOCKING_QA` (off by default), `MAX_DESIGN_FIXES` (3), `MAX_QA_FIXES` (4); `BLOCK_ON_CODE_REVIEW_CRITICAL`, `BLOCK_ON_QA_FIX_BUDGET` (v1 gates, on by default) and `BLOCK_ON_SCHEMA_DRIFT` (a v1 gate in `cli/build.py`, on unless set to a rollback token such as `false`); `CAS_DEPLOY_FIX_CALL_BUDGET_S`; `USE_ADVISOR_FIX` / `_DEPLOY_FIX` / `_QA_FIX` / `_DESIGN_FIX` (all default off); `DISABLE_BATCH_API`; `WIDGETS_ENABLED` (tri-state: unset, `true`, `false`).
- `ANTHROPIC_API_KEY` (v1 generation and QA, the monitor's diagnosis, and the coordinator's three model call sites: the support-answer draft, the failure-KB sync and failure triage); `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, `ADMIN_EMAIL`, `BASE_URL` (worker mail; `SEND_BUILD_PROGRESS_EMAILS`, off by default, turns on progress emails); `GENERATED_APP_RESEND_API_KEY` (optional; the only mail key a generated app receives, `_generated_app_mail_env` in `cli/deploy.py`; the platform `RESEND_API_KEY` is not copied to an app, and this variable is refused when it holds the same value) with `GENERATED_APP_RESEND_FROM_DOMAIN` (the sending domain of that key, handed to the app as `RESEND_FROM_DOMAIN`); `deploy()` also sets the app's `ADMIN_EMAIL` (the site owner's address from the build's spec, not the platform's) and `SITE_NAME`, and, once the first deployment is running, `SITE_ORIGIN` (the Railway domain, the origin of the links the app emails); `SENTRY_DSN` (the worker sends no stack-frame locals and scrubs event text with `_sentry_scrub_event`).
- `RAILWAY_API_TOKEN` (deploys customer apps), `RAILWAY_PROJECT_ID` (the platform project, never deleted), `RAILWAY_ENVIRONMENT` (selects the failure-KB volume path), `PROTECTED_RAILWAY_PROJECT_NAMES` (extra names `destroy_project()` refuses; any name starting with `craftandship` is always refused, and `deploy()` and the v2 spec gate refuse to create one).
- `FAILURE_KB_PATH`, `REVIEW_KB_PATH`: override where the learned-rules files live.
- `SOURCE_DATE_EPOCH`: pins the build time in a v2 compose build (the sitemap `lastmod` and the base date of sample "upcoming" events) so the output is reproducible; `CAS_LINT_EXTERNAL_URLS` selects the external-link lint mode (tests default it to `skip`).

**Coordinator** (`coordinator/`, started by the worker):
- `COORDINATOR_ENABLED` (off by default; an arming switch) and `COORDINATOR_DRY_RUN` (on by default; a safety switch: every gated action, model calls included, is recorded and not performed; `finding_add`, which files a row in `coordinator_findings` for a person to review, is the one exemption).
- `COORDINATOR_INTERVAL_S` (1800; a value that is not a whole number of at least 1 means 1800), `COORDINATOR_MAX_PARALLEL` (3 agents at once), `COORDINATOR_DAILY_BUDGET` (20 USD).
- The admin settings page (`/admin/settings`) writes only twelve of these to the worker service: `COORDINATOR_ENABLED`, `COORDINATOR_DRY_RUN`, `COORDINATOR_DAILY_BUDGET` (0 to 500), `COORDINATOR_INTERVAL_S` (300 to 7200) and eight `AGENT_*_ENABLED` toggles. It asks for the typed phrase `go live` before it turns dry run off or enables the coordinator (`docs/THREAT_MODEL.md`, "Coordinator budget and permission gates").
- `ANTHROPIC_ADMIN_KEY`: when set, the Anthropic cost report is the budget's one spend source. When unset the budget reads the worker's own ledger of build and agent-task costs, which leaves out what the web tier spends on chat. With either source, unreadable spend means no budget and no model call in that tick (a task of a category its agent declares model-free still runs), and unknown is never read as zero (a report without a bucket for today, or with a non-USD or non-finite amount, is unknown; a result with no amount counts as zero, and one with no currency counts as USD). The web app needs the same key for the executor: see the executor variables below.
- `COORDINATOR_APPROVAL_REMINDER_HOURS` (3) and `COORDINATOR_APPROVAL_TIMEOUT_HOURS` (4; an unanswered request is rejected, never approved), `COORDINATOR_FAILURE_RETRY_HOURS` (6; how long a failing agent and category pair stays skipped before one probe task is let through) and `COORDINATOR_INITIATIVE_INTERVAL_DAYS` (7; an agent's initiative turn), `COORDINATOR_MAX_REBUILDS_PER_BUILD` (2 per 24h), `COORDINATOR_MAX_REBUILDS_PER_LINEAGE` (3 per root build per 7 days; 0 switches automatic rebuilds off), `COORDINATOR_ANALYSIS_ONLY` (off by default; narrows every agent), per-agent `AGENT_*_ENABLED` toggles (on by default) and `AGENT_RECONCILIATION_ENABLED` (off by default).
- `RAILWAY_ENVIRONMENT_ID`, `RAILWAY_WEB_SERVICE_ID`, `RAILWAY_WORKER_SERVICE_ID` (the only services a playbook may redeploy). Nothing in Python reads a GitHub token, and nothing in `ops/` or `coordinator/` commits to a repository.

Detail in `docs/internals/coordinator.md`. The legacy ops agent (`ops/`) runs instead when the coordinator is off: `OPS_DRY_RUN` (on by default), `OPS_SCAN_INTERVAL`, `OPS_CIRCUIT_BREAKER_LIMIT` and `_WINDOW_MINUTES`, `OPS_MAX_CLAUDE_CALLS_PER_DAY` (a cap on fixer runs per day; the playbooks make no model calls).

**Monitor** (`monitor/`): `MONITOR_INTERVAL` (health checks, 900s), `MONITOR_MAX_LLM_CALLS_PER_DAY` (rolling 24h cap on diagnosis model calls, 60), `CAS_BACKUP_DIR` (where dumps go; point it at a mounted volume), `CAS_BACKUP_TIMEOUT_S` (per pg_dump or psql run, 900).

**Executor and dev scripts** (`scripts/`; the executor's test gate needs python3 3.11 or newer and pytest 8.4 or newer): `CAS_EXECUTOR_STATE_DIR` (locks, counters and the failure tracker; default `$TMPDIR`, else `/tmp`), `CAS_OPS_BASE_URL` and `OPS_API_KEY` (the ops API the executor asks before it starts a session or pushes: the build counts and today's spend are required, and without an answer it starts no session and pushes nothing; it also starts nothing unless the web app's cost report is complete, and that report is always partial when the web app has no `ANTHROPIC_ADMIN_KEY`; its heartbeats, run results and zombie sweep are best effort), `CAS_OPS_TIMEOUT_SEC` (per ops API request, 10), `CAS_EXECUTOR_NET_TIMEOUT_SEC` (git fetch and pull, `gh` and the gate's `npm install`, 300), `CAS_EXECUTOR_PUSH_TIMEOUT_SEC` (a push, which includes the pre-push hook, 1800) and `CAS_EXECUTOR_GATE_TIMEOUT_SEC` (each of the gate's test commands, 1800), each in seconds, `CAS_WATCHDOG_PROBE_TIMEOUT_SEC` (the watchdog's Claude probe, 30; the watchdog honours `CLAUDE_BIN` too), `CLAUDE_BIN`, `GH_BIN` (the path of `gh`, used for the draft-PR path), `RUN_ONCE`, `CRASH_RATE_WINDOW_SEC` / `CRASH_RATE_LIMIT` / `ZOMBIE_SWEEP_MAX_AGE_MIN`; `CAS_PROD_URL`, `CAS_STAGING_URL` and the `RAILWAY_*_ID` / `STAGING_*_ID` variables (`wait_for_deploy.py`, `smoke_prod.py`); `CAS_SKIP_AUDIT=1` (skip the pre-push dependency audits), `CAS_PROMOTE=1` and `CAS_EXECUTOR=1` (let a push through the pre-push staging check); `CAS_ALLOW_REMOTE_DB=1` (lets `run_worker_local.sh` use a non-local database).

**Tests:** `CAS_TESTS_ALLOW_NETWORK=1` turns off the network guard in the root `conftest.py`; `CAS_BUILD_ENGINE=v1` runs the v1-only tests; `CAS_SCHEMA_TEST_DATABASE_URL` names a throwaway database for the web test files that execute real SQL (`web/tests/unit/schema.idempotency.test.ts` and every `web/tests/unit/*.realdb.test.ts`), and `CAS_WORKER_PYTHON` names an interpreter that can import `queue/worker_pg.py` for the one case there that runs the worker's cleanup function (unset, `python3` is tried and the case skips if it cannot); `CAS_COMPOSE_TEST_DATABASE` names one database for the generated-site tests to use instead of a new one per test (each booted site gets a schema in it, and the column tests replace its `public` schema, so name one that holds nothing else); the browser suite reads `PORT` (the port it starts its server on, default 4000) and `CAS_UI_REUSE_SERVER=1` (use a server you started yourself; ignored when `CI` is set), and also `DEV_TEST_EMAIL`, `DEV_TEST_PASSWORD`, `ADMIN_TEST_EMAIL`, `ADMIN_TEST_PASSWORD`.

## v2 engine facts that bite

Detail and test guards are in `docs/internals/V2_ENGINE_BEHAVIOR.md`.

- v2 is deterministic static compose with no AI in the build path. Never run the v1 Claude fix loops (`deploy_fix.py`, QA fix, design fix) on v2 artifacts; they corrupt them. The worker fails fast with `reason="v2-deploy-crash-no-fix-loop"` (`_run_pipeline` in `queue/worker_pg.py`). The correct remediation is fixing the compose engine.
- v2 skips the design-review, QA-fix, UI-test and deploy-fix loops, and also `verify_routes`, `verify_auth` and `verify_data` (each produces false failures against v2 output; guarded by `TestV2DeployFixSkip`). The retry loop is skipped for deterministic failures (`_is_deterministic_failure`: an error tagged `[v2-deterministic]`, or a spec the engine refused with "Spec validation failed"): same input, same output.
- Deploy health: `verify_health` times out at 120s and returns `"infra"` on silence (URL not routable yet) versus `"failed"` on a 5xx. `"infra"` is never a pass: the worker keeps waiting, and if the app stays silent the attempt ends as a transient failure and is retried, with no preview and no fix loop on either engine. `wait_for_deployment` raises only after two consecutive CRASHED or FAILED polls, since Railway often reports CRASHED then SUCCESS during the post-migration restart (`cli/deploy.py`). A generated site answers 503 `home_page_error` when its own home page did not render when it started (`services/health.js`, one loopback request at boot), and `verify_health` reads that as `"failed"`, never `"ok"`.
- Railway projects: `builds.railway_project_id` is written only by the preview write, so it names a deployment that reached preview. The project an attempt creates lives in that attempt's state, and the attempt deletes it if it ends without reaching preview (`_discard_unannounced_project`; also when the thread ends after the supervisor gave up on it, through `_discard_after_abandonment` on a connection of its own). `_fail_build`, the supervisor, orphan recovery and the janitor delete no Railway project.
- v1-shape intake specs are auto-translated through `compose.intake.translate_v1_spec()`. Compose emits the `/magic?token=` page (sha256 of the raw token, a TTL; opening the link does not spend the token, the POST from its confirmation page does) and logs no query strings, so the token is not in the app's access log. The worker's login probe posts its own verification token to `/magic/consume` and never puts it in a URL.
- A spec whose `auth_required` page would be answered without a login by something else in the build does not build (`_auth_required_page_errors`). Fix the spec; do not look for a warning. A page that lists `allowed_roles` is a protected page even without `auth_required` (`_roles_imply_login`: `resolve_spec` sets the flag and records `allowed_roles_imply_login`).
- A v2 app seeds its admin without a password, so the worker calls `deploy(build_dir, password_login_probe=False)` for v2; the v1 password probe would report a healthy app as failed.
- v2 does not read `builds.rebuild_request`. A revision or a reviewer's change request queues a new build that carries the same spec plus that text, and only the v1 engine reads the text, so under v2 the rebuilt site comes out the same unless the spec itself was changed.
- A build requeued in place (a retry, a reset, an ops requeue) keeps its stored artifact when it has one: the worker resumes it from the test stage (`_resume_stage`) and redeploys the stored files without composing again, so a fix to the engine does not reach it. The rebuild routes insert a new build row, and that one is composed afresh.
- A custom page never lists a model's rows. Rows are public only where the spec sets `public_listing_path` on the model or an archetype layout reads the table (`_public_row_sources`). A public form into a publicly shown model with no boolean `published` column does not build (`_public_form_errors`); with it, a submitted row is stored unpublished until the admin publishes it, and each value is validated before the insert. Only a BOOLEAN column named `published` (typed `boolean` or `bool`) is the flag; one of that name with another type is an ordinary column (`_publication_column`), and a row whose flag has no value is not published (`_published_condition`, the one definition every public read uses).
- A spec is JSON written by a model, so the validator owns the type and size of everything an emitter reads. `validate_spec` returning nothing means `resolve_spec` accepts the spec too (it runs it on a copy), `build_app` bounds the whole decoded document first, unknown keys included (`_document_size_errors`), and `_spec_size_errors` bounds the containers (nesting 32, 200,000 values, 100,000 characters per string, 4,000,000 in all, 300 custom pages, 100 models, 100 fields per model, 100 roles; a spec file over 32 MiB is refused unread), and page data reaches a view only through the parameters its widget declares in `compose/data/widget-registry.json` (`_spec_widget_data`). A new key an emitter reads needs an entry in a `*_KEY_KINDS` table (`_kind_problem`), a new widget parameter an entry under `params`, and a new optional part of a spec belongs in `EXTRAS` in `compose/tests/_spec_matrix.py`, which is how the wrong-type matrix reaches it. A column the engine reads with a fixed meaning belongs in `_ENGINE_COLUMN_KINDS` and in `ENGINE_COLUMN_POSITIONS` of `compose/tests/test_spec_shape_matrix.py`, and a public form page must name its `allowed_fields` (the spec is refused without them).
- The build report has two kinds of warning line: `warning: ` lines are the engine's, added only through `_engine_warning` and written first, and `spec-warning: ` lines are text the spec carried, never to be mistaken for an engine finding. Record an engine finding with `_engine_warning`, never by appending to the spec's list. The manifest's shape is stated once, in `docs/internals/V2_ENGINE_BEHAVIOR.md`; the worker copies every `warning: ` line and checks `engine_warnings_count` (`_manifest_warning_checks`).
- A generated site has no notion of preview: it serves `robots.txt` with `Allow: /` and a sitemap, marks its public pages `index, follow`, and reads no setting that tells a preview from a live site (`emit_routes_seo_js`, `compose/templates/layout-public.ejs`).

## Deploy

While it ran, the platform was deployed on Railway from the default branch; nothing is deployed from this repository now, and the rules below are what the agent followed then. The web app and the build worker were separate services; see `railway.toml` and `Dockerfile.worker`. The web service builds from `web/`. The worker builds from the repo root and redeploys only when its `watchPatterns` match (`cli/`, `compose/`, `queue/`, `coordinator/`, `monitor/`, `ops/`, `Dockerfile.worker`, `requirements.worker.txt`, `railway.toml`); `drainingSeconds = 60` is far shorter than a build, so a redeploy that does happen cuts off an in-flight build; orphan recovery then resumes it from the stored artifact or requeues it. The `watchPatterns` are the real protection: a merged change outside those paths does not redeploy the worker.

After every push, confirm both services run the new commit before triggering customer builds: `python3 scripts/wait_for_deploy.py` compares each service's `/health` `git_commit` against the remote default branch. Railway may skip a config-only commit with "No changes to watched files"; a manual redeploy fixes that.

Operational rules learned the hard way:
- Fresh-project deploy timeouts: retry at most once, then rebuild in an existing project or stop retrying.
- When writing prose or JSON through `psql`, dollar-quote it (`$json$ ... $json$`); apostrophes inside single-quoted SQL broke automated review runs.
- Verify production without forging credentials: smoke-probe public routes and exercise the DB write path directly. Never mint reset tokens or session hashes to impersonate an admin.
- Never give a background agent Railway write access. The production Railway project was deleted twice in one day, once by a background agent that had Railway write access and once by an orphan-sweep path with no guardrails; the recovery write-up and the four-layer protection that followed are in `docs/RAILWAY_DISASTER_RECOVERY.md`. The sweep (`_sweep_orphan_railway_projects`) does nothing unless `ENABLE_ORPHAN_SWEEP=true`; do not enable it.

Runbooks: `docs/RAILWAY_DISASTER_RECOVERY.md`, `docs/FAILOVER_RUNBOOK.md`.

## Working alongside autonomous agents

An autonomous executor (`scripts/cas-roadmap-loop.sh`, configured by `scripts/cas-executor-config.json`; full behavior in `docs/LOCAL_EXECUTOR.md`) picks items from `coordinator/roadmap.json` and works each in a git worktree. **It ships disabled** (`"enabled": false`, and a config with no `enabled` key also means disabled; only a JSON `true` enables it). When it is on, anything filed into the roadmap gets executed and deployed without further review, so verify premises before filing an item. After the session exits, the loop carries one commit, by hash, through four gates: a committed change that descends from the commit the worktree was created from; the merge guard over that commit's diff; `npm test` and `pytest tests compose/tests` on a fresh checkout of that commit (not Playwright); then, holding the merge lock, a wait until the ops API reports no build queued, building, testing or deploying (`wait_for_builds_clear`: 45 minutes at most, and nothing is pushed when the counts cannot be read), the guard again, a check that the branch still is the tested commit, and the merge of that commit. The loop then commits the item's `completed` mark as exactly that one change to `coordinator/roadmap.json` through the pre-commit hook (`record_roadmap_status`; if the commit cannot be made the merge is taken back and nothing is pushed) and pushes. `ARCHITECTURE.md`, "Roadmap executor", has the steps and the guard's path list, and `docs/LOCAL_EXECUTOR.md` the full behavior.

What that means when working next to it: a branch that touches anything the guard protects (`scripts/`, `.githooks/`, `.github/`, `.claude/`, any `CLAUDE.md`, the roadmap, package manifests and npm configuration, test-runner configuration and setup files, any `conftest.py`, top-level Python modules, compiled Python at any depth (`__pycache__`, `.pyc`, `.pyo`, `.pyd`, `.so`), the Vitest, PostCSS, Tailwind and Playwright configuration, every Dockerfile and `.dockerignore`, the Railway and nixpacks configuration, every `requirements*.txt`, the `Makefile`, any compose file, and `web/src/db/schema.sql` with `migrate.ts`) or that deletes a test file, uses a path with a byte outside printable ASCII, or leaves a symlink or a submodule link is rejected, and a session that committed nothing leaves its item pending. An interrupted merge is settled from a journal at the next cycle, and a push is taken back only after the remote has said it lacks the merge. A merge the loop gives up on mid-run (the status mark or the journal cannot be written) is taken back only while the checkout is on the target branch, only if it is the loop's own, and with `git reset --keep`; otherwise it stays, unpushed, with its journal, and nothing starts until it is settled. The guard reads the commit's diff and the gate tests exactly that commit, but a branch may add and edit tests and the code they import, so neither can stop a session from weakening a test. The session itself is not sandboxed.

- Interactive sessions may run in a worktree, so your working directory may not be the repo root. Check `git worktree list` before relying on relative paths.
- Fresh worktrees do not carry gitignored files: run `cd web && npm ci` and copy `web/.env` explicitly. Prefer `npm ci` to symlinking `web/node_modules` from another checkout. The ignore rule in both `.gitignore` files is `node_modules` with no trailing slash, so a symlink is ignored like the directory; the earlier `node_modules/` form matched directories only, `git add -A` staged the symlink, and that broke two production web deploys. (The executor links `node_modules` into its throwaway worktrees, which is why its merge guard refuses a committed symlink.) Prefer explicit `git add <paths>` over `git add -A`.
- The executor yields a cycle when the project directory is off the target branch, when `coordinator/roadmap.json` differs from HEAD, or when any other tracked file other than `cli/failure_kb.json`, `scripts/cas-executor-config.json` and `CLAUDE.md` has uncommitted changes, or when any path is unmerged (a conflicted stash pop or an unfinished merge) (`DIRTY_OK_RE` in `scripts/cas-roadmap-loop.sh`, which matches the end of each path, so a CLAUDE.md in a subdirectory is tolerated too; it never commits those three). Its pre-merge stash can contend for the git index lock; set `"enabled": false` (or `scripts/cas-exec pause`) before bulk git operations.
- The executor pushes everything on its target branch that the remote lacks: its merge, its own roadmap status commits and any commit a person (or a session, which is not sandboxed) made on that branch in the same checkout, so a commit left there while it is enabled goes out with its next push.
- With `tiered_governance` on, high-risk diffs become draft PRs instead of merging; mark them ready before merging. When merging stacked PRs bottom-up, retarget the dependent PR's base before deleting the merged branch, or the dependent PR auto-closes.

## Key design decisions (behavioral contracts: load-bearing)

These are the most bug-prone behaviors. More decisions (logo upload, legal pages, cost dashboard, admin page catalog, ops API surface) are in `docs/internals/design-decisions.md`.

- **Pricing (Harbor, single product):** one subscription, $39/month sliding to a $19/month floor (any whole-dollar amount in between). Literals live in `web/src/app.ts` (`res.locals.harborSubscriptionPrice`, `harborSlidingScalePrice`) and `web/src/services/stripe.ts` (`HARBOR_SUBSCRIPTION_AMOUNT_MIN_CENTS`, `HARBOR_SUBSCRIPTION_AMOUNT_MAX_CENTS`, `HARBOR_SUBSCRIPTION_DEFAULT_AMOUNT_CENTS`). Never hardcode a price in a view. The pre-Harbor tier system and its `/payment` flow were removed; `BuildTier` remains only for `builds.tier` column type-safety.
- **Development gate (`isDevOrTestEnv()` in `web/src/middleware/auth.ts`):** "development" means `NODE_ENV` is exactly `development` or `test`. Anything else, including unset and `staging`, is treated as production. Every convenience that weakens a control (the two payment bypasses, the admin `?dev_trial=` override, Secure-cookie and HSTS relaxation, error detail in responses, the random session secret) keys on this helper, never on `NODE_ENV !== 'production'`, so a deployment that forgot `NODE_ENV` fails safe. TLS to a remote database follows the same rule (`poolSslOption` in `web/src/db/tls.ts`): a host that is not loopback, a Unix socket or `*.railway.internal` gets TLS without certificate verification unless `NODE_ENV` is exactly `development` or `test`. Railway writes (`isRailwayWriteEnabled`) are the one check that requires exactly `production`, the safe direction.
- **Session secret (`resolveSessionSecret` and `sessionSecretWeakness`, `web/src/middleware/auth.ts`):** one `SESSION_SECRET` signs the session cookie, CSRF tokens and unsubscribe tokens. In development or test an unset or placeholder value is replaced by a random per-process secret; anywhere else the server refuses to boot on a short, repetitive or stand-in value. The full rule is in `docs/THREAT_MODEL.md`, "Session secret and boot refusal".
- **CSRF (two layers; detail in `docs/THREAT_MODEL.md`):** (1) `rejectCrossOriginWrites`, mounted globally in `web/src/app.ts` before every router, refuses any write the browser labels cross-origin; requests that carry neither `Sec-Fetch-Site` nor `Origin` (webhooks, the ops API, curl, server-side tests) pass. This is the layer that actually stops a forged cross-site request. (2) An HMAC token from `generateCsrfToken()` bound to the session the page was rendered in (`nonce.tag.mac`): `validateCsrfToken` refuses it from any other session, which is what stops login CSRF, and rendering a page stores the session so a logged-out form has one (`keepSessionForRenderedPage`). A JSON route that reads the token itself calls `verifyHmacToken(token, req)`; without `req` it checks only that the app issued the token, so always pass the request. Every POST form must include `<input type="hidden" name="_csrf" value="<%= csrfToken %>">`. `validateCsrfToken` returns JSON `{error}` with 403 for a script's request and renders the 403 page (`views/403.ejs`) for form submissions; whether a request is a script's is one rule, `isJsonRequest` in `web/src/utils/json-request.ts` (a JSON content type, the `x-csrf-token` header, a path under `/api/`, `/ops/api/`, `/webhooks/` or `/admin/api/`, a listed fetch endpoint, or `?format=json`), shared with the model limiter, the 404 handler and the error handler. Other refused requests render `views/error.ejs` through `renderErrorPage` (`web/src/utils/error-page.ts`), which prints the status the response is sent with; `500.ejs` is for server faults.
- **EJS escaping:** `<%= %>` for user content (HTML-escaped). `<%- %>` only for trusted raw HTML (iframe `srcdoc`, pre-rendered email HTML, controlled inline attributes). Mixing them up is a frequent bug.
- **Sessions:** `connect-pg-simple` with the `user_sessions` table created in `schema.sql` (not by `createTableIfMissing`, to avoid constraint-name conflicts on redeploy). Cookie flags and lifetimes are in `docs/THREAT_MODEL.md`, "Sessions". A password login, and an email verification completed in the browser that typed the account's password, go through `startAuthenticatedSession` (`web/src/routes/auth.ts`), which regenerates the session id (fixation defense), copies across only funnel state, stamps `authenticatedAt`, and saves before redirecting, to avoid races with the async store. The security headers are the first middleware, ahead of the preview password gate; the session middleware is installed after the crisis handler and before `express.static` and the cross-origin guard (`ARCHITECTURE.md`, "Web app", has the whole order). `app.set('trust proxy', n)` uses `TRUST_PROXY_HOPS` (`resolveTrustProxyHops` in `web/src/app.ts`): unset, empty or not a whole number means 1, the single Railway edge proxy, with a warning at boot, and `web/.env.example` ships 0. Set 0 when nothing proxies the app, otherwise a client can forge `X-Forwarded-For` past every per-address limiter; set 1 behind one proxy such as Railway, otherwise every visitor shares the proxy's address and the Secure session cookie is never issued.
- **Email:** web-tier mail goes through `sendEmail()` in `web/src/services/email.ts`, which logs every attempt to `email_log` (with `token=` values in the stored HTML redacted, so the table and `/admin/emails` cannot be used to replay a reset or login link). The worker's mailer (`queue/mailer.py`) redacts its stored bodies the same way (`_redact_secret_params`). Marketing and lifecycle templates check `isUnsubscribed()` first and carry an absolute `List-Unsubscribe` URL (built from `BASE_URL`); the transactional templates (`password_reset`, `email_verification` and the two admin alerts; `TRANSACTIONAL_TEMPLATES`) skip that check and carry no unsubscribe link. Exceptions that do not use `sendEmail()`: the contact form (`POST /contact` in `app.ts`, which posts straight to Resend and writes no `email_log` row; the page confirms only when Resend answers 2xx, a provider failure is a 502 and missing mail configuration a 503, both with the typed values kept) and the Python services (`queue/mailer.py`, `coordinator/actuators.py`, `monitor/diagnose.py`, `ops/alerter.py`). Fire-and-forget: `sendXxx(...).catch(err => console.error(...))`. Unsubscribe tokens are `HMAC-SHA256(SESSION_SECRET, email)`, deterministic, with no DB storage.
- **Password reset, email verification and the unverified-claim rule** (`web/src/routes/auth.ts`; the full statement is in `docs/THREAT_MODEL.md`, "Passwords, signup, reset and verification"): reset and verification tokens are random, stored only as SHA-256, single use; forgot-password and resend-verification answer the same for known and unknown addresses, run one statement whatever the address and send the mail after the response, and at most one verification link goes to an address per hour. Opening a verification or unsubscribe link changes nothing: it shows a page whose button posts back, and the POST verifies or unsubscribes. Verification is required on signup. Until the mailbox is proven, the password and name on a row are only a claim, and the claim that counts is the one made in the browser that then proves the mailbox (`pendingSignup` in that browser's session; a correct-password login on another device records the same claim). No existing account is changed by a signup (the claim stays in the session), and an address someone else registered first (the configured `ADMIN_EMAIL` included) does not come through verification with their password. A completed reset or verification also expires the paid trial cookies promoted into the account (`expirePromotedTrialCookies`).
- **Payment bypasses:** `STRIPE_BYPASS` (an arming switch: only `true`, `1`, `yes`, `on` or `enabled` turn it on, and `false`, empty or anything else leave it off) enables a bypass on the feature-request payment flow: in development/test any logged-in customer can use it on their own requests; in production only the admin session can. `CAS_HARBOR_STRIPE_BYPASS=true` lets a Harbor trial skip Stripe on "make it public" (`POST /lighthouse/bypass`), works only in development/test, goes through the same keeper claim as a payment (409 `account_already_subscribed`), and refuses the admin email (unless the session is already an admin session) and any address that already has an account (other than the current session's own). Both exist for testing; never remove them, never set them where real money moves.
- **`PREVIEW_PASSWORD`:** HTTP basic auth (any user name) on every route except the public marketing pages, `/health`, `/try`, `/ops/api/*` (own bearer key), `/webhooks/*` (own signatures) and static assets. A static asset here is a file that exists under `web/public` and has one of the listed extensions (`isPublicStaticAsset` in `web/src/app.ts`); a route whose path merely ends in `.css` or `.png` is challenged like any other. Compared with `timingSafeEqualStrings`. Unset leaves the site open, which is the normal state. The name is historical: it gates the platform's own site, not customers' preview sites, which have no password.
- **Admin access:** admin is `isAdminSession(req)` (`web/src/middleware/auth.ts`), the one definition, used by `requireAdmin` in `web/src/routes/admin.ts`, the admin branches of `routes/builds.ts` and `routes/features.ts`, and the nav flag in `app.ts`. It is true only for a session that `startAuthenticatedSession` established (it carries `authenticatedAt`) whose email exactly equals `ADMIN_EMAIL`, and it fails closed: with `ADMIN_EMAIL` unset nobody is admin, and a session that merely carries the admin's address is not enough (`docs/THREAT_MODEL.md`, "Admin definition"). `requireAdmin` redirects unauthenticated users to login and returns 403 otherwise. An admin can view any build; admin pages live under `/admin/*`.
- **Admin delete gate (`/admin/builds/:id/delete`):** a client-side typed-confirm modal asks the admin to type the app name or build id. The route deletes the Railway project only when `isRailwayWriteEnabled()` (`web/src/services/railway.ts`) is true, meaning `NODE_ENV === 'production'` AND `CAS_ALLOW_RAILWAY_WRITES === 'true'`; a project listed in `PROTECTED_RAILWAY_PROJECT_IDS`, or the platform's own `RAILWAY_PROJECT_ID`, returns 403. When disabled, the Railway call is skipped and the database row still cascades. A Railway failure returns 502 and preserves the row so the delete can be retried. Before anything is deleted the route reads the project's name back; a name that cannot be read, or that does not match the build's app name after lowercasing and collapsing separators, returns 502 and keeps the project and the row. Only the `NOT_FOUND` error code counts as already deleted. Defense in depth: the service guard throws, the route gate skips, the UI hides the Railway wording.
- **SE review gate (non-negotiable):** the gate stands in front of the `live` status in the platform database. It does not stand in front of the site, which is public from the moment it is deployed. The full statement (entering review, deciding, the three statements that write `live` and what each requires, which subscription statuses publish) is in `docs/THREAT_MODEL.md`, "Review gate and publication". The load-bearing parts:
  - The worker has no statement that writes `live` (`_set_status` in `queue/worker_pg.py` writes only the three pipeline stages and raises for anything else), and every worker status write carries the build's current status and its attempt token (`builds.started_at`); the token is required.
  - A verdict belongs to one arrival at preview, never to the row: the preview write resets it, and every web statement that sends an existing row back to `queued` must include `REVIEW_RESET_ASSIGNMENTS` (`web/src/routes/builds.ts`).
  - The review condition (`review_status = 'approved'`) lives in the `WHERE` clause of the owner's and Stripe's publishing `UPDATE`, never in a separate read. The owner's statement (`CUSTOMER_APPROVE_SQL`) also requires a subscription for a Harbor build; the admin's (`ADMIN_APPROVE_SQL`) requires only `preview`.
  - Whether a build is a Harbor build is `builds.is_harbor`, set by `insertHarborBuild` and inherited through the trigger `builds_inherit_is_harbor`. It is a column on the build because the rows it could be derived from (a parent build, a hand-off stamp) can be deleted by the worker's janitor and by the admin and ops routes.
  - The coordinator never promotes preview to live: it has no method or permission that approves or promotes a build. An approval request is filed only by an agent's escalation or the reconciliation agent, is advisory, and is rejected after 4 hours unanswered, never approved. See the Craft Quality Policy below.
- **Build-start limits:** a customer may have at most 2 builds queued or in progress, start at most 10 builds per rolling 24 hours (a conversation's first build, rebuilds, revisions and manual retries together) and manually retry one build at most 3 times (`MAX_ACTIVE_BUILDS_PER_CUSTOMER`, `MAX_BUILD_STARTS_PER_DAY`, `MAX_MANUAL_RETRIES_PER_BUILD` in `web/src/services/build-start-limits.ts`, counted from the `build_start_events` ledger under a per-customer advisory lock; the admin is exempt). The retry, rebuild and revision routes in `web/src/routes/builds.ts` and the Harbor dispatch (`dispatchHarborTrialBuild`, `dispatchHarborKeeperBuild` in `web/src/services/harbor_dispatch.ts`) all go through that module, and a dispatch writes a `build_start_events` row of kind `dispatch` (the other kinds are `retry`, `rebuild` and `revision`). The checks that can refuse a dispatch (a verified account, any existing account for an anonymous dispatch, a limit, the anonymous share of the model-call budget) run before its extraction calls the model. The coordinator's automatic rebuild (`Actuators.queue_rebuild`) repeats the two counts and the lock in Python. The product promises unlimited revisions; these only stop a runaway loop.
- **Anonymous intake handoff:** `/try` creates an anonymous draft tied to the session; `POST /signup` claims it, and after email verification the user resumes at `/intake/:buildId`. When `CAS_HARBOR_ENABLED=true`, `/try` and `/intake` redirect to the Haven conversation, which has its own email gate at turn 22 (`CAS_HARBOR_EMAIL_GATE_TURN_COUNT`), and `POST /try/start` and `POST /try/:buildId/message` answer 404 with a `redirect` field before any limiter, query or model call (`refuseWhenHarborEnabled` in `web/src/routes/anon-intake.ts`).
- **CSP nonce:** `web/src/app.ts` emits a fresh 24-byte base64 nonce per request (`res.locals.cspNonce`); `script-src` uses `'nonce-...'` and every inline `<script>` in `web/views/**/*.ejs` carries `nonce="<%= cspNonce %>"`. `unsafe-inline` is retained only on `style-src` (inline `style=` attributes are pervasive and nonces do not apply to attributes). Never keep `'unsafe-inline'` alongside a nonce on `script-src`; it silently disables nonce enforcement.
- **Companion spend limits and the crisis path:** `POST /lighthouse/table/turn` has layered defenses against spend amplification, and one handler that runs ahead of all of them. The order of the whole request is in `ARCHITECTURE.md`, "Harbor companion turn"; the bounds and their numbers are in `docs/THREAT_MODEL.md` ("Harbor companion rails" and the model-spend table).
  - *Crisis first.* `crisisFirst` (`web/src/routes/lighthouse.ts`, mounted in `app.ts` right after the body parsers and before the session middleware) answers a message that matches the crisis scan with the fixed script, from the request body alone. Only the security headers, the optional `PREVIEW_PASSWORD` gate and the body parsers run before it. Never put anything that can refuse or fail in front of it. It shares the web process's event loop with everything else, so slow synchronous work anywhere in the process delays it (the faithful-copy crawl parses fetched HTML in a worker thread for that reason).
  - *Its side effects are bounded* because that path is not rate limited (`crisisSideEffects` in `web/src/companion/runtime.ts`); past a bound the crisis is in the server log only, and the counters are in process memory.
  - *Rate limits* live in `web/src/middleware/companion-rate-limit.ts` (per trial and per client address; `CAS_HARBOR_TURN_MAX`, `CAS_HARBOR_TURN_WINDOW_MS`, `CAS_HARBOR_TURN_IP_MAX`, `CAS_HARBOR_BUILD_MAX`) and `web/src/middleware/trial-cookie.ts` (`CAS_HARBOR_TRIAL_MINT_MAX`).
  - *Cost caps* over a trailing 24 hours (`web/src/companion/runtime.ts`; `CAS_HARBOR_TURN_DAILY_COST_CAP_MICROS` per identity, `CAS_HARBOR_GLOBAL_DAILY_COST_CAP_MICROS` shared) throw `CompanionDailyCostCapError` before any rail, memory or Claude work happens; the route turns that into a 429 without revealing the figures. The cost query fails open: a DB error never blocks a real keeper. The caps have no test-mode values; tests supply their own spend figures.
  - `CAS_LLM_DAILY_CALL_CAP` separately caps intake, revision, feature and support chat model calls and the Harbor spec extraction (in memory, per process). Callers without an account (the legacy `/try` turns, which exist only while Harbor is disabled, and a cookie-only trial's extraction) may cause at most 80% of it (`tryAdmitAnonymousCalls` in `web/src/services/llm-budget.ts`); the rest can be spent only by callers with an account, who still share one pool. The turn response carries no cost figures; spend is recorded in `companion_cost_log`.
- **Customer app isolation:** customer apps must be completely isolated from each other. Never store platform API keys in customer app code. Wrap multi-step DB operations in transactions where atomicity matters. Self-healing actions that touch databases must snapshot first.
- **Bug-recurrence prevention:** `docs/internals/MW_BUG_RECURRENCE_RCA.md` identifies six categories of recurring pipeline bugs (convention drift, contract mismatch, regex scope, ordering, hotpatch-not-fed-back, generation completeness) and maps each to a pipeline guard. Hotpatches must be fed back into the pipeline in the same session, otherwise the next build regenerates the bug. `docs/MW_TEST_CHECKLIST.md` is the living regression checklist for the reference event-site build; every regression found in QA gets a permanent entry.

TYPE`, `TRUNCATE`, `DELETE` with no `WHERE` or with one that names no column; a `-- SAFE: <reason>` comment above the statement, or above the `DO`, satisfies this hook only. Because the file runs at every boot, any `UPDATE`, `INSERT`, `DELETE`, `MERGE`, `COPY ... FROM` or dynamic `EXECUTE` anywhere in it needs a `-- SAFE:` reason of its own, on its line or directly above it, not one above the `DO`, and a statement that names the status `live`, or a default of `live`, is refused whatever the comment. ## Code style

- TypeScript strict mode; `async`/`await` only (no raw promises or callbacks).
- No em dashes in comments, logs or user-facing text (use commas, colons or semicolons).
- Prefer explicit types over `any`.
- Descriptive variable names; no single-letter variables except loop counters.
- Functions under 50 lines, doing one thing.
- Always catch and log errors; never swallow them silently.
- All API calls must have retry logic with exponential backoff.
- All DB queries must be parameterized (never string-concatenated SQL).

Nothing enforces these rules. The one linter, `ruff` (`ruff.toml`, run in CI), checks Python for correctness only (undefined names, syntax errors and the other pyflakes bug rules), not style; no formatter or Python type checker is configured. `ARCHITECTURE.md`, "Where the bodies are buried", counts where the code breaks them (functions over 50 lines, and handlers that swallow an error).

## Model selection

Pick the cheapest model that does the job well, escalate (and say so) rather than ship degraded output, and never downgrade correctness-critical steps. Where this is encoded:

- `coordinator/scorer.py`: the per-role ladder (`AGENT_MODELS`, `role -> (primary, escalation, trigger)`). A new coordinator agent needs an explicit entry; it must not default to the most expensive model. Most role agents are rule-based and ignore the model they are handed (the entry only sets the cost reserved for the task); only customer service, the failure-KB sync and the build-failure categorizer call a model, all Haiku (the sync uses the cheap tier whatever tier the infra agent's task was dispatched on).
- `coordinator/budget.py`: the allowed-model list per tick and the per-tick `ModelCallMeter`; the per-call cost assumptions are `ESTIMATED_COST` in `coordinator/scorer.py`. Keep them in sync with real pricing. Each dispatched task is charged its estimate (`_task_charge` in `coordinator/tick.py`), because no agent reports token usage, and each model call is granted one at a time by the meter through `Actuators.authorize_model_call`; a zero budget grants none. Both count estimates, not measured spend.
- `monitor/diagnose.py`: tiers 1 and 2 (in `monitor/ping.py`) are deterministic; tier 3 uses Haiku and tier 4 (`TIER4_MODEL`) uses Opus, under a rolling 24-hour cap on model calls (`MONITOR_MAX_LLM_CALLS_PER_DAY`).
- `web/`: the AI intake and the Harbor companion (`DEFAULT_MODEL` in `web/src/companion/claude.ts`) use fixed models. Do not raise them casually.

Because the executor, when it is enabled, merges and pushes unattended, build and fix steps, security review and the final review gate keep their current tier. Savings come from the cheap phases, not the gate.

## Brand voice (required reading before any copy edit)

Every customer-facing copy change must follow `docs/BRAND_VOICE.md`, the single source of truth for landing, pricing, how-it-works, gallery, intake, chat, status, dashboard, contact, auth views, emails and meta tags.

**Hard rules** (`.githooks/pre-commit` runs `scripts/check_brand_voice.py`, which enforces rule 1, the competitor names of rule 2 and a ban on technical-ownership terms such as "self-host"; the other rules are for the writer and the reviewer):

1. **No em dashes.** U+2014 and its HTML named entity are rejected in staged `web/views/**/*.ejs`, `web/src/services/**/*.ts`, `web/src/cron/**/*.ts`, `web/src/routes/**/*.ts`, `web/src/app.ts`, `queue/mailer.py`, `coordinator/actuators.py` and the HTML comments of `compose/widgets/**/*.ejs`. The lint is Python-aware (it skips comments and plain docstrings but scans `f"""..."""` blocks where customer HTML lives). Use colons, semicolons, commas or new sentences. En dashes in numeric ranges are fine. A specific line can be allowed with a `brand-voice-allow-em-dash: <reason>` comment.
2. **Affirmative voice.** Describe what Craft & Ship does, not what it is not or what competitors do. Competitor names stay out of visible body copy, comparison tables included; the `/vs` SEO pages carry them only in titles, meta tags, URLs and JSON-LD. The one exemption is the citation page `web/views/docs-research.ejs`, which must name the vendors whose public pricing it cites (`COMPETITOR_RULE_EXEMPT_PATHS` in `scripts/check_brand_voice.py`); the em-dash rule still applies there.
3. **"Website," not "software", "app" or "platform"** in customer copy. "Web app" is reserved for technical internals.
4. **No review turnaround in customer copy.** Customer-facing copy gives no review time (no hours, minutes or business days), and it says a website needs a recorded review approval before it goes live.
5. **Plain English about the build.** No "compose" or "reviewed components" jargon in customer copy.
6. **Accuracy about AI.** AI powers the intake chat, the support chat and self-healing. It does not write the code that ships: the v2 engine composes each site from a library of unit-tested building blocks. The copy rule the agent was given also said that a human reviews every build before it goes live; that was the policy, and the note under Craft Quality Policy says where the code later departed from it. For this release rule 6 of `docs/BRAND_VOICE.md` and the web app's customer copy were rewritten to say only what the code supports: a site is built from tested building blocks and is reviewed before it goes live, with no reviewer named and no claim that the review comes before the preview address. Never say "AI builds your app" in customer copy.
7. **Internal vocabulary stays internal.** Never use the word "keeper" in customer-facing copy, and keep internal codenames out of surfaces they were not designed for.

Before editing copy, read `docs/BRAND_VOICE.md` top to bottom and take prices from `web/src/app.ts`. After editing, the pre-commit hook catches what the lint enforces and the web unit tests (`scripts/run_web_tests.sh`) catch test-assertion drift.

## Default code-change workflow

When asked for any code edit, fix, bug repro, feature update or pipeline change, run this loop without being asked.

**The loop (run until green, then stop):**

1. **Edit.** Make the change.
2. **Type and lint.** `cd web && npx tsc --noEmit` for TypeScript; `python3 -m py_compile <file>` for Python.
3. **Unit test.** `cd web && npx vitest run tests/unit/<file>` for affected Vitest specs; `python3 -m pytest tests/<file> -q` for pytest. If no test exists for the changed surface, write one before claiming green.
4. **Run it if observable.** For any edit visible in a browser (EJS, routes, CSS, admin UI, generated-app output), start the dev server and look at it before asking anyone else to. Never hand back "go check it yourself."
5. **UI verify.** Read the page structure for content, check console and network for errors, inspect CSS, exercise interactions; take a screenshot only when visual proof is needed.
6. **Diagnose and revise.** If step 5 finds anything (console errors, broken layout, wrong copy, 4xx or 5xx), go back to step 1 and update the tests too. A failing UI that "passes tests" means the tests are wrong.
7. **Repeat** until tests are green, the UI matches intent, there are no new console or network errors, and the regression surface has been checked.
8. **Gap sweep before reporting.** Enumerate everything touched, nearly touched, or noticed and set aside. For each, ask: "Did I actually verify this, or am I about to claim it without checking?" Typical loose ends: tests edited but not re-run; sibling routes or views affected but not opened; edge cases mentioned but not exercised (empty state, error state, unauthenticated, mobile, dark mode); console warnings dismissed as "probably unrelated"; TODO or FIXME comments added; schema changes whose callers were not grepped; dead code, stale imports, debug logs and hardcoded test values left behind. Close each gap now if it takes under five minutes. The completion report should list intentional deferrals, not things that were too tedious to finish.
9. **Honest-completion report** per the protocol below.

**For app-build verification** (rebuilding a customer app to check a pipeline change): after the build completes, the login link is in the preview-ready email (the operator mailbox gets a BCC when `ADMIN_EMAIL` is set). The worker keeps it out of `build_logs` and stores the email body with the token redacted, so no script prints it. If the link is past its 24-hour TTL, re-trigger the build instead of resetting a password.

**Skip the loop for:** pure documentation edits, read-only research, and throwaway debug prints reverted in the same turn. When in doubt, run it: an extra snapshot costs seconds, a shipped-broken UI costs trust.

**Run scoped tests while iterating** (`pytest compose/tests/test_build_pipeline.py -q`, `cd web && node_modules/.bin/vitest run tests/unit/auth.middleware.test.ts`) and reserve the full battery for pre-commit, pre-push and review gates. **Batch related fixes** locally and promote them together; pay for one deploy cycle, not one per fix, except for a true customer-impacting hotfix. Pipeline edits (`cli/`, `queue/`, `coordinator/`) need the full `pytest tests/ -q` plus `npm test` green locally before they ship.

## Rigor, self-skepticism, and the production-ready bar

**This system was built to charge customers money and deliver the sites their reputations depend on. Overconfidence is the primary failure mode.** The v12 to v16 build cycle (see `docs/internals/MW_BUG_RECURRENCE_RCA.md`) is the case study: five successive "production-ready" reports, each missing real defects that a reviewer found within minutes of inspection.

Every claim of "done", "fixed", "green" or "production-ready" must survive an adversarial self-review before it is written. Before using any of those phrases, ask:

1. What did I NOT test that could still be broken?
2. What edge case did I skip because it was inconvenient?
3. Did I verify by proxy (HTTP 200, test counts, a log grep) or by observation (clicking, screenshotting, reading the rendered output)?
4. Did I click through every flow or spot-check a few?
5. Are my tests exercising the behavior the user cares about, or just the shape I wrote them to verify?
6. What would a skeptical reviewer find in five minutes?
7. If this were my own money and reputation, would this be enough evidence to ship?

If any answer reveals a gap, do not ship the optimistic claim; report the gap. Default phrasing when uncertain: "I verified X, Y, Z. I have NOT verified A, B, C. Want me to verify those before shipping?" Not: "Everything looks good." / "Production-ready." / "All green."

**Non-negotiable practices:**
- Write acceptance criteria BEFORE starting anything non-trivial.
- Visual UI work requires screenshots and click-through, not HTTP 200s.
- Pair end-to-end integration tests with unit tests for any user-exposed feature.
- Enumerate what was NOT tested in every report; let the reader decide whether the gap is acceptable.
- A user report of broken behavior always trumps the agent's confidence. Reproduce the exact scenario instead of arguing the tests "should" have caught it.

This applies to any "the build is ready" claim, any "all tests green" summary, any "the fix is complete" verdict, any "not production-ready" reversal (be just as rigorous about caveats), and any pipeline, post-processor, admin CRUD, route or schema change.

## Honest-completion protocol

Every response that claims completion, success, readiness or verification must include a paired enumeration of what was NOT done. This is a structural backstop against training-induced overconfidence, not a style preference. A Stop hook (`scripts/honest_completion_audit.py`, wired in `.claude/settings.example.json`; copy that file to .claude/settings.json to enable it) backs the protocol up. It is a phrase tripwire, not a judge: when the final message contains one of the red-flag phrases listed below and no enumeration that actually lists something, it sends the message back once for revision. The protocol asks for more than the hook can check.

**Five required disclosures in every "done/ready/verified" response:**

1. **What I did NOT verify.** Name untested branches, skipped edge cases and unchecked assumptions specifically. "Edge cases" is not a list; "concurrent delete plus rebuild race" is.
2. **What I relied on memory for without re-checking.** Notes from earlier sessions are frozen snapshots. Any claim sourced from them that was not re-verified against current code or data must be tagged: "Memory-only, not re-checked this session: <claim>".
3. **What was not executed end-to-end.** If code was reasoned about but not run (no pytest, no browser click, no curl to the deployed endpoint, no DB row fetched), say so. HTTP 200 is not end-to-end; a rendered page with the correct content is.
4. **What should be re-checked later.** Any deferred verification goes in the response and in a dated deferred-checks log, so it surfaces next session.
5. **What I guessed versus what the user specified.** If acceptance criteria were ambiguous and an interpretation was chosen, name the choice and the alternatives rejected.

**Accepted forms of the enumeration section** (`GAPS_RE`, `EXPLICIT_NO_GAPS_RE` and `_has_enumeration` in `scripts/honest_completion_audit.py` decide what the hook accepts; examples): `Not verified: ...`, `Did NOT: ...`, `Unchecked: ...`, `Skipped verification of ...`, `Gaps: ...`, `Deferred: ...`, `To re-check: ...`, `Assumed without checking: ...`, `Relied on memory: ...`, or `Gaps: none, observed end-to-end: <complete list of observations>` (only when genuinely true).

**Red-flag phrases that REQUIRE the enumeration:** production-ready, all green, everything works, everything looks good, all tests pass, fully verified, works perfectly, completely verified, ready to ship, ready for prod, deploy successful, shipped and verified, verified end-to-end.

**What the hook does and does not do** (`tests/test_honest_completion_audit.py` pins each of these):

- An empty enumeration does not count: a label followed by nothing, `none`, `n/a` or `nothing` is refused, and so is a denial such as "No gaps" or "nothing left unverified". The explicit no-gaps form counts only when it lists what was observed.
- A plain "done", "fixed", "verified" or "shipped" is not a red-flag phrase and passes untouched.
- It cannot tell whether a listed gap is real or relevant. A gap phrase used in passing ("I did not rename the file") satisfies it.
- It blocks at most once per stop, and it fails open: unreadable input or any error in the hook allows the stop.
- Of the six hooks in `.claude/settings.example.json` it is the only one that can block. The other five add reminder text to the model's context.

**Ambiguity protocol: ask, don't guess.** When a request lacks the acceptance criteria needed to know when the work is done (what "done" looks like, which edge cases must work, which surfaces count as tested), ask a numbered list of clarifying questions BEFORE implementing. Never "make reasonable assumptions" on work that is load-bearing, user-visible or hard to reverse. This governs ambiguity about what done means, asked once up front. It does not license pausing on obstacles found mid-task: those get fixed, and a blocker is not a question.

**Pattern for a disciplined completion claim:**

> Shipped: `<change>`. Observed end-to-end: `<concrete observations with evidence>`.
> Not verified: `<list of gaps, why each was skipped>`.
> Memory-only: `<any claim from earlier notes that was not re-checked>`.
> Deferred (logged): `<items to re-check next session>`.

At the start of a non-trivial session, skim the deferred-checks log. For each item adjacent to today's task, decide: re-check now, keep deferred (and say why), or promote to the roadmap. Items that age past about 14 days without triage are a sign of workflow drift.

## Craft Quality Policy

Craft & Ship's core tenet: human experience and AI capability work together. Every site is co-created, not merely generated, and every build receives a Senior Web Craftsman review before delivery. This commitment is non-negotiable. If demand exceeds review capacity, raise prices or add reviewers; never skip, shorten or automate away the human review.

> Note for readers of the public repository: the paragraph above is the policy as the agent was given it. In June 2026, shortly before the wind-down, an automated review mode was added that departs from it: with `CAS_HARBOR_AUTO_REVIEW=true` the worker queues a finished build as `ai_review_queued` instead of `pending`, for an automated review loop that ran outside this repository and is not included here. The schema comments in `web/src/db/schema.sql` and `_initial_review_status` in `queue/worker_pg.py` are what remains of it. This repository does not record which production builds were reviewed by a person and which by that loop. What the code enforces is narrower than the policy: a recorded verdict (`review_status = 'approved'`) before the owner or a payment can mark a build live, and the web app's customer copy in this release was rewritten to say no more than that.

## Communication model

Customer co-creation happens over asynchronous text chat on the customer's preferred channel (email, the in-product chat, or a messaging app). Phone and video calls are optional extras, never the default. Customer copy gives no review turnaround (brand rule 4 in `docs/BRAND_VOICE.md`).
