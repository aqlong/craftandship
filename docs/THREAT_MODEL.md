# Threat model and controls

What the code defends against, control by control, and which switches weaken it. It is written for someone who intends to check the claims: controls are cited by file and symbol, and the test file that covers each one is named. A control listed without a test has no test aimed at it. Where this file and the code disagree, the code is right.

Read [SECURITY.md](../SECURITY.md) first: it defines what "preview", "review" and "live" mean here, and every control below should be read with those definitions in mind. What the code does not defend against is in [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md). [ARCHITECTURE.md](../ARCHITECTURE.md) describes how the system fits together, and [PRE_RELEASE_REVIEW.md](PRE_RELEASE_REVIEW.md) how the code was reviewed before publication.

## Threat model in one page

**Assets.**

- Customer accounts and sessions (`customers`, `user_sessions`).
- Payment state: Stripe subscription state mirrored in `harbor_subscriptions`, and the webhook event ledger `processed_webhooks`.
- The build pipeline: a conversation becomes a spec, the spec becomes generated files, and the worker deploys them to a hosting provider. It writes and deploys code.
- Platform credentials held by the worker: model API keys, a Railway account token, mail and GitHub keys, and the platform database URL.
- Customer conversations (`companion_turns`, `keeper_memory`, `intake_messages`).

**Actors and the controls in front of them.**

| Actor | Can reach | Standing in front of them |
|---|---|---|
| Anonymous visitor | Public pages, `/try`, `/lighthouse/*` through a trial cookie, signup and login, the contact and guide forms, three webhook endpoints | Per-address rate limits ([auth-rate-limit.ts](../web/src/middleware/auth-rate-limit.ts), [anon-rate-limit.ts](../web/src/middleware/anon-rate-limit.ts), [companion-rate-limit.ts](../web/src/middleware/companion-rate-limit.ts)); trial-mint limit and cost caps ([trial-cookie.ts](../web/src/middleware/trial-cookie.ts), [runtime.ts](../web/src/companion/runtime.ts)); the cross-origin write guard and CSP ([auth.ts](../web/src/middleware/auth.ts), [app.ts](../web/src/app.ts)); signature checks on webhooks ([webhooks.ts](../web/src/routes/webhooks.ts)) |
| Customer | Their own builds, intake and revision chats, support chat, publishing their own reviewed build | Ownership predicates in the SQL (`customer_id = $n`); a daily model-call ceiling per customer ([llm-rate-limit.ts](../web/src/middleware/llm-rate-limit.ts)); build-start limits on retries, rebuilds, revisions and a conversation's first build ([build-start-limits.ts](../web/src/services/build-start-limits.ts), [harbor_dispatch.ts](../web/src/services/harbor_dispatch.ts)); the promoting `UPDATE` requires `review_status = 'approved'` and, for a Harbor build, a subscription |
| Admin | Every build, review decisions, customer list, cost and settings pages, the ability to promote any preview | One definition of admin, `isAdminSession`, which fails closed ([auth.ts](../web/src/middleware/auth.ts)); no MFA (see limitations) |
| Hostile spec or model output | A visitor steers what the extraction model writes; the spec then reaches the build engine as text | The translator drops what it does not recognize and resolves what the engine would refuse toward less exposure ([harbor_to_compose.ts](../web/src/services/harbor_to_compose.ts)); `_spec_safety_errors` (which also bounds the spec's size and checks the type of every value the emitters read), per-context escaping and `_safe_output_path` in [compose/build.py](../compose/build.py). The review stands between the site and the `live` status, not between the site and its public address |
| Compromised customer app | Code running in its own Railway project: a v2 app by a bug in the engine, a v1 app by model-written code | No platform key is handed to an app (the mail key is opt-in and separate, `_generated_app_mail_env` in [cli/deploy.py](../cli/deploy.py)); the worker's probes stay on the app's origin and connect only to public addresses they resolved themselves; the worker's browser refuses non-public addresses but cannot be pinned to one. v1 children are scrubbed but not sandboxed (see limitations) |
| Operator misconfiguration | An unset `NODE_ENV`, a placeholder secret, a wrong proxy depth, a forgotten flag | `isDevOrTestEnv` treats anything but exactly `development` or `test` as production for cookies, HSTS, error detail, the session secret and the development bypasses; `resolveSessionSecret` refuses to boot on a placeholder or stand-in secret; secrets that are unset make their endpoints fail closed; the coordinator and ops agent default to dry run. The database TLS decision (`poolSslOption` in [db/tls.ts](../web/src/db/tls.ts)) and the `BASE_URL` boot warning follow the same rule |

Out of scope: the hosting, database, model, payment and mail providers themselves; a compromised developer machine (the roadmap executor is discussed under limitations); network-layer denial of service.

**Session secret and boot refusal.** One `SESSION_SECRET` signs the session cookie, the CSRF tokens and the unsubscribe tokens. `resolveSessionSecret` in [auth.ts](../web/src/middleware/auth.ts) decides what is accepted:

- In `development` or `test`, an unset or placeholder value is replaced with a random per-process secret (a warning in development), and any other configured value is accepted as it is, however short.
- In any other environment, including an unset `NODE_ENV`, the server refuses to start unless the value passes `sessionSecretWeakness`: at least 32 characters, at least 8 different characters, not a block of 16 or fewer characters repeated, and none of nine placeholder words (`changeme`, `password`, `example` and so on) once the value is lower-cased and reduced to letters and digits. The two placeholder literals that appear in this repository are refused by name.
- The check catches a value typed as a stand-in. It is not an entropy estimate: a long sentence passes.

[app.ts](../web/src/app.ts) turns the `SessionSecretError` into a fatal exit. Tests: [auth.middleware.test.ts](../web/tests/unit/auth.middleware.test.ts), [app.boot-security.test.ts](../web/tests/unit/app.boot-security.test.ts).

**Sessions.** The cookie is `__Host-cas.sid` (`cas.sid` under development and test, where it is not Secure; `hostOnlyCookieName` in [auth.ts](../web/src/middleware/auth.ts)): HttpOnly, SameSite=Lax, Path=/, no Domain, Secure unless the environment is development or test, with a 24-hour rolling idle expiry and a Postgres store (`user_sessions`; memory store under `NODE_ENV=test`). The `__Host-` prefix makes a browser accept the cookie only from this host over HTTPS, never from a sibling subdomain. A session is stored, and its cookie set, once a page is rendered (`keepSessionForRenderedPage`), so that the page's CSRF token has a session to belong to; a JSON answer, a redirect, a webhook or a health check stores none. Logout and account deletion clear the cookie with the same Secure and Path attributes, which a browser requires for a `__Host-` cookie. `startAuthenticatedSession` in [auth.ts](../web/src/routes/auth.ts) regenerates the session id, carries over only funnel keys, stamps `authenticatedAt`, and saves before redirecting. It runs after a password login and after an email verification completed in the browser that typed the account's password. `enforceSessionLifetime` regenerates any authenticated session more than 30 days past `authenticatedAt`, however active. A password reset and an account deletion delete the user's rows in `user_sessions`. Tests: [routes.auth.test.ts](../web/tests/unit/routes.auth.test.ts), [auth.middleware.test.ts](../web/tests/unit/auth.middleware.test.ts), [session-store.test.ts](../web/tests/unit/session-store.test.ts), [app.boot-security.test.ts](../web/tests/unit/app.boot-security.test.ts) (the `__Host-` names outside development and test).

**CSRF: token plus cross-origin write guard.** Two layers.

- `rejectCrossOriginWrites` is mounted before every router in [app.ts](../web/src/app.ts) and refuses a POST, PUT, PATCH or DELETE that the browser labels as coming from another origin (a `Sec-Fetch-Site` other than `same-origin` or `none`, or `Origin` against `Host` on older browsers). A request carrying neither header (curl, webhook senders, the ops API, tests) passes, because it carries no ambient cookie to forge.
- `validateCsrfToken` checks an HMAC token (`nonce.tag.mac`, `generateCsrfToken` in [auth.ts](../web/src/middleware/auth.ts)) whose tag is derived from the session id, and refuses it from any other session, so a token read from one browser's page is refused in another and a forged login fails here even where the guard cannot see where the request came from. The token has no expiry of its own; it is good for as long as its session. A token minted without a session id, which only test code does, is accepted from any session. The JSON routes that read the token themselves (anon-intake.ts, features.ts, builds.ts, feedback.ts, intake.ts) check it against the request's session the same way (`verifyHmacToken(token, req)`). A refused token is answered in JSON when the request is a script's (`isJsonRequest` in [json-request.ts](../web/src/utils/json-request.ts): a JSON content type, the `x-csrf-token` header, a path under `/api/`, `/ops/api/`, `/webhooks/` or `/admin/api/`, a listed fetch endpoint, or `?format=json`), otherwise with the 403 page; the 404 handler and the error handler use the same rule.
- Cross-origin preflights get a bare 204 and any downstream `Access-Control-Allow-Origin` is stripped.
- Three Harbor JSON routes carry no token by design (`POST /lighthouse/table/turn`, `/build`, `/bypass`; a comment in [lighthouse.ts](../web/src/routes/lighthouse.ts) says why). The crisis handler mounted ahead of the guard makes the same cross-origin check itself (`isCrossOriginWrite`).

Tests: [app.security.test.ts](../web/tests/unit/app.security.test.ts), [cors-same-origin.test.ts](../web/tests/unit/cors-same-origin.test.ts), [auth.middleware.test.ts](../web/tests/unit/auth.middleware.test.ts) (the token's binding), "login CSRF" in [routes.auth.test.ts](../web/tests/unit/routes.auth.test.ts), and in a browser [verify-and-unsubscribe.spec.ts](../web/tests/ui/verify-and-unsubscribe.spec.ts) (a login token from one browser refused in another).

**Passwords, signup, reset and verification.** All in [auth.ts](../web/src/routes/auth.ts).

- *Passwords.* bcrypt at cost 12; 8 to 72 bytes (bcrypt reads only 72, so longer input is refused rather than silently truncated). Every hash this code makes comes from one module, [password-hash.ts](../web/src/utils/password-hash.ts) (`BCRYPT_ROUNDS`), including the placeholder password of an account made at checkout, by a dispatch or by the bypass; an account made before that change keeps a placeholder hashed at cost 10 ([KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md)).
- *Login.* One bcrypt comparison runs against a throwaway hash when the email is unknown (`getDummyPasswordHash`, made at the cost of every stored hash, so an unknown address and a wrong password do the same bcrypt work). An unverified account is refused even with the right password, and that refusal is reachable only with the right password.
- *Signup.* The password is hashed before the address is looked up, and the response is the same redirect, with a session cookie set in every case, whether the address is free, claimed but unverified, or verified. The number of database statements still differs between those cases.
- *Unverified accounts.* Until the mailbox is proven, the password and name on a row are only a claim. A signup writes nothing to an existing row, verified or not, and voids no link; its claim stays in that browser's session (`pendingSignup`). Opening a verification link (`GET /verify-email`) spends nothing: it shows a page whose button posts the token back, so a mail scanner that fetches the link changes nothing. `POST /verify-email` verifies the account and settles its credentials in one statement: the claim made in this browser (a signup, or a correct-password login there) if it has one, which also stamps `terms_accepted_at` on a row that has none, otherwise an unusable random password and a name taken from the address, followed by a single-use link to choose a password. Only the first case starts a session, and a claim this browser holds for another address is kept for that address's link. So an address someone else registered first does not come through verification with their password, the configured `ADMIN_EMAIL` included. The verification mail greets "Hi there," and prints no name, because the name on an unverified row was typed by whoever created it. At most one verification link is issued to an address per hour, from signup or resend, whoever asks (`ISSUE_VERIFICATION_TOKEN_SQL`).
- *Tokens.* Reset and verification tokens are 32 random bytes, stored only as SHA-256, valid for one hour and 24 hours. A reset token is spent and the password changed in a single `WITH claimed AS (UPDATE ... RETURNING)` statement, which also marks the account verified (the link proved the mailbox). The account's other outstanding reset and verification tokens are voided, and its sessions are deleted. A completed reset of an account that was not verified also replaces its name with the address's local part, so the name on a verified row is its owner's own claim or the local part; the reset mail greets by name only a verified account. A completed reset or verification also expires the paid trial cookies promoted into the account (`expirePromotedTrialCookies`, [trial-cookie.ts](../web/src/middleware/trial-cookie.ts)).
- *Forgot password and resend.* `POST /forgot-password` and `POST /resend-verification` render the same page for known and unknown addresses, never contain the link, and run one statement whatever the address (`ISSUE_PASSWORD_RESET_TOKEN_SQL`, `ISSUE_VERIFICATION_TOKEN_SQL`, which insert a token only for an account); the mail starts after the response is sent (`sendAfterResponse`). The insert itself remains: measured locally, a known address still cost about 0.2 ms more server time on `POST /forgot-password`, and no test bounds the timing.
- *Links and pages.* Token pages are `no-store`, `Referrer-Policy: no-referrer` and drop the analytics script (`markTokenPage`). Emailed links and the Stripe return address use `BASE_URL` (`publicBaseUrl`, which ignores a value that does not match its pattern; without one it takes a plain-host `Host` and the scheme `https` only when `req.protocol` is exactly `https`, otherwise `http`, so a client's `X-Forwarded-Proto` cannot choose any other scheme; test: [auth.public-base-url.test.ts](../web/tests/unit/auth.public-base-url.test.ts)), and the web app's `email_log` stores bodies with token values redacted (the redaction, `redactSecretParams` in [recent-errors.ts](../web/src/utils/recent-errors.ts), also catches `&amp;token=` and percent-encoded forms). The worker's mailer redacts its stored bodies the same way (`_redact_secret_params` in [mailer.py](../queue/mailer.py), held to the web app's output on a shared corpus by `test_the_redaction_is_the_web_apps` in [test_mailer.py](../tests/test_mailer.py)). `GET /ops/api/v1/errors` returns request paths without their query string (`loggablePath`), and `trial_keepers.entry_path` and `entry_referrer`, and `funnel_events.path` and `referrer`, hold the path only; campaign parameters are kept in `entry_utm`. The signup, login and resend routes keep the email address in the session, never in a redirect URL (the unsubscribe link, by contrast, carries the address in its query string). Post-login redirects go through `safeReturnTo`.

Tests: [routes.password-reset.test.ts](../web/tests/unit/routes.password-reset.test.ts), [routes.auth.test.ts](../web/tests/unit/routes.auth.test.ts), [routes.auth.unverified-claim.test.ts](../web/tests/unit/routes.auth.unverified-claim.test.ts), [email.service.test.ts](../web/tests/unit/email.service.test.ts), [auth.public-base-url.test.ts](../web/tests/unit/auth.public-base-url.test.ts); on real SQL, the signup cases in [money-path.realdb.test.ts](../web/tests/unit/money-path.realdb.test.ts) (among them a stranger's signup for an unverified account, which writes nothing to it and spends none of its links); in a browser, the verification and unsubscribe confirmation pages in [verify-and-unsubscribe.spec.ts](../web/tests/ui/verify-and-unsubscribe.spec.ts).

**Rate limits.** Every limiter is per process and is built by `boundedRateLimit` ([companion-rate-limit.ts](../web/src/middleware/companion-rate-limit.ts)), the only place in `web/src` that calls `express-rate-limit`: counters live in a `BoundedRateLimitStore` (at most 20,000 keys per limiter, oldest window dropped first) and a key longer than 128 characters is stored as its SHA-256. [middleware.rate-limit-callsites.test.ts](../web/tests/unit/middleware.rate-limit-callsites.test.ts) fails if another file imports the library. The chat, feedback and logo-upload limiters key on the customer id (`customerOrAddressKey`); the rest key on the validated address.

- The address bucket is checked first, so a refused client adds nothing to memory. An email longer than 254 characters is answered 400 before any key holding it exists, and a key keeps an email longer than 64 characters as a SHA-256 (`emailKeyPart`). The account forms (`/login`, `/signup`, `/logout`, `/forgot-password`, `/reset-password`, `/resend-verification`, `/verify-email`, `/unsubscribe`, `/account/delete`) accept bodies up to 10 KB (`AUTH_BODY_LIMIT` in [app.ts](../web/src/app.ts)).
- A `req.ip` that is not an IP address gets the single key `ip:invalid` (`rateLimitIpKey`), because with a proxy depth set too high it is the `X-Forwarded-For` text.

- Login, forgot-password and reset-password pass three buckets: 10 per 15 minutes per address and email pair, 30 per email across addresses, 50 per address across emails.
- Signup and resend-verification: 5, 15 and 25 per hour.
- `POST /account/delete`, the one other route that checks a password: 5 attempts per 15 minutes per account (the customer id of the session) and 25 per address (`makeAccountDeleteRateLimit` in [auth-rate-limit.ts](../web/src/middleware/auth-rate-limit.ts)); like the others it is skipped under `NODE_ENV=test`.
- IPv6 clients are keyed on their /64 (`rateLimitIpKey`).
- The contact form allows 10 submissions an hour per address and the guide form 20. The Harbor make-public form, which opens a Stripe Checkout session, allows 10 an hour per trial cookie and 40 per address (`MAKE_PUBLIC_MAX_PER_HOUR` in [lighthouse.ts](../web/src/routes/lighthouse.ts)).
- The ops API allows 60 requests a minute per address and runs before its key check.
- Page views are recorded in `page_views` at most 30 a minute per client address and 600 a minute overall (`PAGE_VIEWS_PER_ADDRESS_PER_MINUTE`, `PAGE_VIEWS_PER_MINUTE` in [app.ts](../web/src/app.ts); in process memory, the per-address map bounded by `createMintLimiter`). Past a cap the page is served and the view is not recorded. A view stores the path, the campaign parameters, the session and customer ids and the Referer as a path only (`loggablePath`: no query string, no fragment, 200 characters at most), because a mailed unsubscribe or reset link carries its address and token in the query and a visitor who follows a link out of it sends that URL as the Referer.
- Limits for model-backed routes are in the table below.
- Under `NODE_ENV=test` the auth, anonymous, Harbor and public-form limits and the trial-mint cap are skipped or raised (a boot warning is printed). The Haven cost caps are not.

Tests: [middleware.auth-rate-limit.test.ts](../web/tests/unit/middleware.auth-rate-limit.test.ts), [middleware.companion-rate-limit.test.ts](../web/tests/unit/middleware.companion-rate-limit.test.ts), [escape-hatches.test.ts](../web/tests/unit/escape-hatches.test.ts), [app.page-views.test.ts](../web/tests/unit/app.page-views.test.ts) (the page-view caps).

**Admin definition.** `isAdminSession` in [auth.ts](../web/src/middleware/auth.ts) is the only definition: `ADMIN_EMAIL` must be set, the session must be a logged-in customer session carrying `authenticatedAt` (stamped only by `startAuthenticatedSession`), and its email must equal `ADMIN_EMAIL` exactly. `requireAdmin` in [admin.ts](../web/src/routes/admin.ts), the admin branches of [builds.ts](../web/src/routes/builds.ts) and [features.ts](../web/src/routes/features.ts), and the navigation flag in [app.ts](../web/src/app.ts) all call it. A session that merely carries the admin's address, such as the one the development payment bypass writes, is not admin. `/admin/harbor?status=keepers`, which lists paid keepers with their conversation counted by keeper id, is behind `requireAdmin` like the rest of the inbox. Tests: [auth.middleware.test.ts](../web/tests/unit/auth.middleware.test.ts), [app.boot-security.test.ts](../web/tests/unit/app.boot-security.test.ts).

**Account deletion.** `POST /account/delete` in [auth.ts](../web/src/routes/auth.ts) asks Stripe to cancel the account's subscriptions at period end before its transaction opens, then deletes the account's personal data in one transaction. That includes the account's Haven trials: a trial stamped with one of the account's builds, or one carrying the account's address unless another account's build is stamped on it (`ACCOUNT_TRIALS_SQL`); the trials' turns and notes cascade, and the address is cleared from any other trial row. The builds are kept with their customer link removed. Locks are taken in the order the payment webhook uses (the account's builds, then those trials, then the customer row). What is left behind is in [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md). Tests: "removes the account and its Haven trials from every table" in [money-path.realdb.test.ts](../web/tests/unit/money-path.realdb.test.ts), which scans every table the schema creates for the address and for what was said, and [routes.auth.test.ts](../web/tests/unit/routes.auth.test.ts).

**Webhooks.** All three are in [webhooks.ts](../web/src/routes/webhooks.ts). Tests: [routes.webhooks.test.ts](../web/tests/unit/routes.webhooks.test.ts) (a fake database that matches statement text), [stripe.webhook-signature.test.ts](../web/tests/unit/stripe.webhook-signature.test.ts), and on real SQL the Stripe cases in [money-path.realdb.test.ts](../web/tests/unit/money-path.realdb.test.ts).

- *Stripe, the envelope.* The route receives the raw body and verifies the signature through the SDK's `webhooks.constructEvent` (`constructWebhookEvent` in [stripe.ts](../web/src/services/stripe.ts)). Each event is one database transaction on one connection: the claim row in `processed_webhooks` (`INSERT ... ON CONFLICT DO NOTHING RETURNING`), the handler's work, then `COMMIT`. A duplicate delivery is answered 200 without work. A handler that throws rolls the claim back with everything else and the route answers 500, so Stripe's retry is processed from scratch. An event without an id is refused with 400. Emails are sent after the commit.
- *Stripe, the checkout handler* (`handleHarborMakePublic`). It locks the build row with `FOR UPDATE`, moves the trial's conversation into the paying customer (the trial named in the Checkout metadata or, when the metadata names none or something that is not a UUID, the unreleased trial stamped with the build: `unreleasedTrialForBuild` in [keeper_promotion.ts](../web/src/services/keeper_promotion.ts)), flips the build to `live` with `WHERE status = 'preview' AND review_status = 'approved'`, and records the paying session id on the build, so one session is never applied twice. A session whose `payment_status` is present and not `paid` changes nothing. A paid session whose metadata the handler cannot act on (no `build_id` or one that is not a UUID, no session id, an amount that is not a positive whole number of cents, a Stripe customer or subscription id of the wrong shape) also changes nothing and records nothing, but its event commits like any other, so `ADMIN_EMAIL` is mailed the same `harbor_payment_not_applied` alert; an unpaid one is only logged. A payment is applied only to an account whose keeper has no subscription of its own that this payment may not replace (`claimKeeperSubscription` in [keeper_promotion.ts](../web/src/services/keeper_promotion.ts): one statement with the condition in its `WHERE`, so two sessions completing together cannot both be applied), and a trial is promoted only for the build it is stamped on, and only into the account its own dispatch created (`builds.owner_created_by_dispatch`) or this payment created, unless the account's login or paying cookie opened the session (the session's `keeper_customer_id` metadata, which the make-public route sets only then; `promoteTrialInTransaction`). No keeper row is created or claimed on a verified account for a session that no login of it opened: the handler reads `email_verified` under a share lock before any promotion. When a payment cannot be applied (a second trial's session for an account whose keeper already has a subscription, a keeper's second payment while the first still publishes, a trial that is not the build's own, a session no login of the account opened for a verified account, a trial's session for an account its dispatch did not create), nothing the promotion or the claim would have written is written: the keeper row, the trial and the build stay as they were, the payment is recorded in `harbor_subscriptions` against the account and listed on `/admin/harbor` under "Payments needing a person" (`PAYMENTS_NEEDING_A_PERSON_SQL` in [admin.ts](../web/src/routes/admin.ts)), the event commits and answers 200, and `ADMIN_EMAIL` is mailed a `harbor_payment_not_applied` alert after the commit (`reportUnappliedPayment`; the other cases where money arrives and the site cannot go live send the same alert). Nothing is refunded and Stripe is never called.
- *Stripe, subscription events.* One statement updates `harbor_subscriptions` and its mirror on the keeper row, matched by subscription id. The keeper row holds Stripe's status word for word (a status this code does not know is stored as `incomplete`); which statuses publish is decided in one place (see the review gate below). `canceled` is final. `invoice.payment_failed` only moves a publishing status to `past_due`; it cannot lift `unpaid`, `incomplete` or `paused`. An event older than the newest one already applied (`last_event_created`) is skipped. A subscription `updated` or `deleted` event for a subscription with no local row is acknowledged at once when `harbor_subscription_tombstones` shows that its account was deleted; otherwise it is refused with 500 for 24 hours after its creation, then acknowledged and dropped. A failed invoice for an unknown subscription is acknowledged without a retry.
- *Resend.* `verifySvixSignature` computes the Svix HMAC over the exact request bytes (kept by a `verify` hook on the JSON parser), compares in constant time and rejects timestamps more than five minutes from now. With `RESEND_WEBHOOK_SECRET` unset the route answers 500 to everything.
- *Worker status hook.* `POST /webhooks/build-status` takes a bearer `WORKER_WEBHOOK_SECRET`, answers 500 when it is unset, and accepts only `building`, `testing`, `deploying`, `preview` and `failed`, each as an `UPDATE` guarded by the statuses it may start from (`BUILD_STATUS_PREDECESSORS`). `live` is refused with a 400. Its `preview` write sets `review_status` to `pending`, or to `ai_review_queued` when `CAS_HARBOR_AUTO_REVIEW` is on (`initialReviewStatus`, the same decision as `_initial_review_status` in the worker), and clears any earlier verdict. A valid call can set `preview_url` to any http(s) URL and send the build's owner the preview-ready email (status `preview` with the address in `preview_url`, or in `live_url`, the older name, which is still accepted; `preview_url` wins when both are sent) or the build-failed email (status `failed`); it cannot send the app-live email, and it sends no review email to the admin. Nothing in this repository calls the route; the bundled worker writes the `builds` table directly.

**The address a payment is tied to.** `POST /lighthouse/lamp/:buildId/make-public` in [lighthouse.ts](../web/src/routes/lighthouse.ts) settles which account a payment lands in before Stripe is called, because the checkout handler above promotes the conversation into the build's customer and mails that account.

- When the website already belongs to an account (a keeper's own, or the customer a trial's build was attached to), Checkout is created with that account's address (`createHarborSubscriptionCheckoutSession` in [stripe.ts](../web/src/services/stripe.ts): `customer_email`, which Checkout shows and does not let the payer edit; a keeper who has paid before is passed their stored Stripe customer instead). The page shows the address as text. A request that names another address is refused with 409 `email_mismatch`, and that address is not looked up.
- A trial cookie pays only into the account for the address its own conversation gave, and only while that account is not verified (`trialMayPayInto`). If the build's account is another one, or its owner has verified it, the request is refused with 409 `account_login_required` and that account's address is not shown; a trial also cannot pay into an account that already has a subscription (409 `account_already_subscribed`). That is kept in two places: the route refuses it when it opens Checkout, and the webhook refuses it again when a session opened earlier completes (`claimKeeperSubscription`): the keeper row, the trial and the build are left as they were, the payment is recorded in `harbor_subscriptions`, and `ADMIN_EMAIL` gets a `harbor_payment_not_applied` mail; nothing is refunded and Stripe is never called. A keeper's own second payment replaces only a subscription that no longer publishes.
- A released trial's cookie speaks as a keeper only if its own trial was promoted into that keeper: `trial_keepers.promoted_customer_id`, written by the statement that releases the trial, must be the account of the trial's build, and that account must have a keepers row (`PROMOTED_KEEPER_OF_TRIAL_SQL` in [keeper_promotion.ts](../web/src/services/keeper_promotion.ts), used by `loadPaidKeeper` in [trial-cookie.ts](../web/src/middleware/trial-cookie.ts) and by `persistTurn` in [runtime.ts](../web/src/companion/runtime.ts)). A released trial without all of that, including one released before the column existed, is a stale cookie and gets a fresh trial. The cookie's value is replaced once, on the first request that presents the trial after the payment released it (`resolveTrial` in [trial-cookie.ts](../web/src/middleware/trial-cookie.ts), recorded in `trial_keepers.cookie_rotated_at`; the update is conditional on the old value, so of two racing requests one replaces it and the other sets no cookie), and it was already replaced when the trial's first address was recorded (`rotateTrialCookie`, called from [lighthouse.ts](../web/src/routes/lighthouse.ts) at the email gate and in `POST /lighthouse/build`). A copy taken before either step finds nothing; the old value gets a fresh trial. The paying cookie reaches the lamp pages and the conversation but cannot cancel the subscription: `POST /lighthouse/lamp/:buildId/cancel-subscription` requires the account's own login and answers the cookie alone with a 403 page that says to log in. The cookie also stops speaking for an account when its browser logs in to a different account (`identifyTrialCookie` returns nothing, and the browser gets a fresh trial), when that browser logs out (`clearPaidTrialCookie` clears it), and when a password reset or verification completes for that account (`expirePromotedTrialCookies`).
- A trial must confirm on the page that the address is its own (400 `email_confirmation_required`). The address was typed into the conversation and nobody has verified it, and whoever reads that mailbox can enter the account the payment creates.
- A trial whose build has no customer yet cannot pay with an address that already has an account unless the visitor is logged in as that account (409 `account_exists_login_required`).
- The "website is public" mail goes to the account's address, which is the address Checkout was opened for: the route refuses any other and no route changes an account's address.

**SQL.** The web app passes request-supplied values to its queries as `$n` parameters. What was checked is a scan, not a proof: of the `.query(` calls whose first argument is a template literal, 41 contain `${...}`:

```bash
perl -0777 -ne 'while (/\.query(?:<[^(]*?>)?\(\s*`([^`]*)`/g) { $n++ if $1 =~ /\$\{/ } END { print "$n\n" }' $(find web/src -name '*.ts')
```

Each interpolates one of the following, never a request value:

- a constant or a fixed SQL fragment (`STATUS_PAGE_COLUMNS`, `RETRY_SQL_SET`, `REVIEW_RESET_ASSIGNMENTS`, `SAFE_TURNS_FILTER`, `PUBLISHING_SUBSCRIPTION_STATUS_LIST_SQL`, `ACCOUNT_TRIALS_SQL`, a number of days);
- a fixed fragment chosen by a boolean (the event-ordering clauses in [webhooks.ts](../web/src/routes/webhooks.ts));
- an identifier chosen from two constants (`idColumn`; the `column` that `memoryOwnerColumn` returns, which is `keeper_id` or `trial_id`; the same two words passed to `harborConversationSql` in [admin.ts](../web/src/routes/admin.ts) and to `extractableTurnCountSql` in [spec_extraction.ts](../web/src/services/spec_extraction.ts), whose other argument is SQL the caller wrote, a `$1` or an outer column, never a request value);
- a clause list assembled from fixed strings with `$n` placeholders (`whereClause`), or a placeholder index;
- an integer passed through `sanitizePositiveInt`;
- in a test hook of the topic sweep, the ISO form of a `Date`.

Queries assembled in a variable first were not scanned (the publishing statements in [builds.ts](../web/src/routes/builds.ts) are built that way, from constants), and no test enforces the rule mechanically.

- *The crisis handler runs first.* `crisisFirst` in [lighthouse.ts](../web/src/routes/lighthouse.ts) is mounted in [app.ts](../web/src/app.ts) directly after the body parsers, ahead of the session middleware and everything that follows it (the trial-cookie lookup, both rate limiters, the length check, the email gate, the cost caps). **Build engine: spec safety gate, escaping, contained writer.** Spec text is treated as hostile.

- *The gate.* `_spec_safety_errors` in [compose/build.py](../compose/build.py) runs inside both `validate_spec` and `resolve_spec`, and the emitters take the `ResolvedSpec` that only `resolve_spec` constructs. It refuses an unsafe `app_name` or `admin_email`, unsafe page ids, model names, slugs and field names, two fields of one model that differ only by letter case (Postgres folds them into one column), a `sql_type` outside an allowlist pattern (all matched with `fullmatch`), reserved table names and model slugs, reserved page ids (`_RESERVED_PAGE_IDS`, the engine's own views and routes), a model listing path under `/admin` or on a built-in route, a custom page path that names another origin (`_is_offsite_reference`) an `allowed_roles` entry that is not a short non-empty string, a column the engine reads with a fixed meaning that has a type it cannot work with (`id`, `created_at`, `published_at`: `_engine_column_type_errors`) and a spec that names a stock photo of a specific person or place (`_personal_stock_photo_errors`). `resolve_spec` adds refusals of its own, which `validate_spec` reports too: the link to a parent model or the newsletter email in a column of the wrong type (`_engine_column_errors`), models that belong to each other in a ring (`_models_in_creation_order`) and a public form page that names no column a visitor may fill in (`_public_form_field_errors`).
- *Shape.* A spec is JSON written by a model, so any value can stand where another type was meant. `validate_spec` returning nothing means `resolve_spec` accepts the spec too: it runs the gate and then `resolve_spec` on a copy (`_resolution_errors`). The gate gives each key the emitters read one accepted JSON type (`_kind_problem`), and page data reaches a view only through the parameters its widget declares in [compose/data/widget-registry.json](../compose/data/widget-registry.json) (`_spec_widget_data`): a number where text is declared becomes its text, an undeclared key is left out, anything else is refused. The allowlist patterns are compiled with `re.ASCII`, so a full-width digit is not a digit to them.
- *Size.* `build_app` bounds the whole decoded document before anything reads it, keys the engine does not know included (`_document_size_errors`: the link lint walks every key and the report reads `tier`), and `_spec_size_errors` bounds the containers the engine reads; each stops at the first bound it meets, and every walker of the raw document is iterative (`_json_size_errors`, `_extract_from_node` in the link lint, `_personal_stock_photo_errors`). The bounds are nesting of more than 32 levels, more than 200,000 values, a string or a key of more than 100,000 characters, more than 4,000,000 characters of text in all, or more than 300 custom pages, 100 models, 100 fields in one model or 100 roles. `build_app` refuses a spec file over 32 MiB before reading it, and one nested too deeply for the JSON reader. A stored timestamp is read only up to 64 characters (`_STORED_TIMESTAMP_MAX_CHARS`); a longer one is refused before the pattern runs.
- *A protected page that would be public does not build.* `resolve_spec` refuses a spec whose `auth_required` custom page has a path that something else in the build answers without a login: a page of the site, a model's public listing or detail pages, a built-in public route, an earlier public custom page (`_auth_required_page_errors`). It refuses and does not warn because a build is deployed to a public address before anyone reads its warnings.
- *What it drops instead of refusing.* Other unusable custom page paths (a built-in route such as `/login`, a duplicate, a public page under `/admin`, a path a model's own routes answer first) are dropped by `_classify_custom_pages`, once; routes, views, sitemap and navigation all use the survivors. A dropped `auth_required` page that is not public at its path is recorded as `auth_required_page_not_emitted`. A seed row or a column default that Postgres would refuse (and a few that it takes: dates and times in any form but ISO, arrays of more than one dimension, and a timestamp longer than 64 characters) is left out, and the report says `seed_value_unfit` or `column_default_ignored`; a stock photo of a person that got past the gate is not copied (`stock_photo_not_copied`).
- *Guards on emitted routes.* Every verb of an `auth_required` custom page carries the same guard list (`_custom_page_guards`): `requireAuth`, then at most one role guard that passes an account holding any one of the listed roles. A page that lists `allowed_roles` is a protected page whether or not it says `auth_required`, because a list of roles is a restriction: `resolve_spec` sets the flag and records `allowed_roles_imply_login`, and the web translator and `translate_v1_spec` do the same.
- *Escaping.* Strings are escaped for the context they land in (`_sql_esc`, `_js_escape`, `_ejs_json`, `_html_attr`), identifiers taken from a model go through `_sql_ident`, and link targets are normalized by `_sanitize_spec_content`. The public layout's JSON-LD is escaped in its template instead: `<`, `>`, U+2028 and U+2029 become backslash-u escapes ([layout-public.ejs](../compose/templates/layout-public.ejs)).
- *The writer.* `_write_build_files` is the one place emitted files touch the disk. `_safe_output_path` rejects absolute paths, `..` and `.` components, NUL bytes, backslashes and anything that resolves outside the build directory, including through a symlink; two emitted files at one path (compared without regard to case) fail the build before anything is written. Before writing, `build_app` deletes an existing output directory, that directory only, and only when `_remove_previous_build` recognizes it as an earlier build (empty, holding `compose-manifest.txt`, or directly under a `builds/` directory); a symlink or anything else is refused.
- *What a build publishes.* A model's rows are served without a login in exactly two cases: the spec sets `public_listing_path` on the model, or a page layout of the archetype reads the model's table (`_public_row_sources` is the one definition). Nothing is published because of a name: a custom page whose path is a model's name is emitted as an ordinary page, the model stays admin-only, its router answers a visitor with 404 below that path before any query, and the build report carries `page_named_like_model`. The tables the archetypes' layouts read are a fixed list, enumerated per archetype in `CURATED_PUBLIC_TABLES` in [test_spec_hardening.py](../compose/tests/test_spec_hardening.py); it never includes contact inquiries or newsletter subscribers.
- *A visitor's row is not public until the owner publishes it.* Every unauthenticated INSERT into a model table (custom form pages, the contact form, the newsletter signup) stores `published = FALSE` when the model has a boolean `published` column, and every public read leaves such a row out. `resolve_spec` refuses a spec whose public form stores into a model that is shown to visitors and has no boolean `published` column (`_public_form_errors`). Only a BOOLEAN column named `published` (typed `boolean` or `bool`) is the flag; a column of that name with another type is an ordinary column (`_publication_column`). A row whose flag has no value is not published: `_published_condition` is the one definition, used by the resource router, the composed lists and details and the related-rows query. A custom form page takes only the columns its `allowed_fields` names (a public form page that names none is refused), and a visitor can sort a public list only by a column the list prints (`_public_sort_columns`; any other request gets the default order).
- *The translator resolves what the engine would refuse.* The web translator ([harbor_to_compose.ts](../web/src/services/harbor_to_compose.ts)) resolves every contradiction the engine refuses, toward less exposure and with a warning: a form target it picks itself is never a model visitors can read; an explicit public form into a model visitors can read gets a boolean `published` field, or loses its form when that is impossible; `ContactInquiry` and any `*Subscriber*` model lose `public_listing_path`; a protected page left with no usable role becomes `['admin']`; a protected page at a route the engine would answer without a login is dropped (at a model's listing, the listing is withdrawn and the page kept). [test_translator_output_builds.py](../compose/tests/test_translator_output_builds.py) runs its real output through the engine. The archetype rules are unions over every archetype, so a protected page at another archetype's page name is dropped though the engine would have built it, and a v1 spec that did not come from the translator is still refused for these contradictions. A crawled page at a protected page's route is left out by `translate_v1_spec` (`copy_pages_protected_path`), because the crawl is merged after the translator has run. It also names the columns of each public form page it keeps (`nameVisitorFields`), leaves the columns the engine owns to the engine (`engineOwnedFieldProblem`), keeps one link between models that belong to each other (`resolveModelLinks`), takes a stock photo of a specific person out of everything it returns (`scrubPersonalStockPhotos`) and makes a page that lists roles a protected page.
- *Public forms validate.* Each submitted value is checked before the INSERT: strings only, a length limit (the smallest of the field type's maximum, the width of a VARCHAR column and 10,000 characters), the field type's pattern, and what the column can hold. A rejected submission stores nothing and the form comes back with one message per field and the typed values.

**Worker: guarded status writes, and no statement that writes `live`.** In [worker_pg.py](../queue/worker_pg.py):

- `_set_status` writes only `building`, `testing` and `deploying` and raises `ValueError` for anything else. Its `UPDATE` matches only a build in the same stage or an earlier one, so it cannot move a build backwards.
- `_set_preview_status`, `_requeue_for_retry` and `_fail_build` (`_MARK_FAILED_SQL`, the one statement in the worker that sets `failed`) match only a build still in `building`, `testing` or `deploying`.
- Each of those writes also requires the writer's attempt token (`builds.started_at`, set by the claim and cleared by every requeue), so a thread left over from an earlier attempt cannot advance, preview, requeue or fail a later one. The token is not optional: a call without one raises `ValueError` before any SQL runs (`_attempt_param`), and a claim that returned no token returns no job. The pipeline stops at the first stage write that matches no row (`BuildNoLongerOwnedError`).
- The worker moves a deployed build to `preview` only after its `/health` answered: HTTP 200 with a JSON body whose `status` is `ok` (`health_response_ok` in [cli/deploy.py](../cli/deploy.py)), on the normal path (`verify_health`) and on the supervisor's probe ([watchdog_probe.py](../queue/watchdog_probe.py)) alike. A generated site answers `ok` only when its database answers and its own home page rendered when it started: `services/health.js` makes one request for `/` over loopback when the listener comes up (3 seconds at most, body discarded), a status from 200 to 499 passes and is remembered for the life of the process, a failure is tried again by a later probe at most every 10 seconds, and `/health` answers 503 `db_error` or 503 `home_page_error` otherwise. Any other page, any POST and a home page that breaks after it passed are not noticed. A deployed app that stays silent ends the attempt as a transient failure and is retried (`_DEPLOY_NEVER_HEALTHY`). A local build with no Railway token is the exception: it is recorded as `preview` with no address and nobody is emailed.
- The Railway columns of a build row are written by the preview write, in the same guarded statement (plus `_record_environment_id`, which fills a missing environment id on a row that already names that project), so `builds.railway_project_id` names a deployment that reached preview. The worker deletes a project in three places: `_discard_unannounced_project` (the project the ending attempt created, only if no build row records it and no preview write announced it; also on a connection of its own when the thread outlived the supervisor), `deploy()` cleaning up after its own failed call, and the orphan sweep that ships off. `_fail_build`, the supervisor, orphan recovery and the janitor delete none.
- No worker SQL sets `live` (a test greps the source for it). The reconciliation agent in [coordinator/agents/reconciliation.py](../coordinator/agents/reconciliation.py) writes no build row either: it files an approval request and an alert.
- The claim, the lease, orphan recovery and the janitor are described in [ARCHITECTURE.md](../ARCHITECTURE.md#queue-worker). What matters here: a build is claimed under a transaction-scoped advisory lock and only when a thread is free to run it, it is owned and leased from the claim on, and the janitor deletes rows only, re-checking each in the `DELETE` itself and keeping any row that has a surviving descendant, a hand-off stamp, a recorded Railway project or a `live_url`.

What that does not mean: the worker is what makes a site public, by deploying it. And "the one statement that sets `failed`" is about the worker: the web app's admin kill, the ops API, account deletion (for the account's queued builds) and the optional status hook write `failed` with statements of their own.

No test runs two worker processes against one database: the claim lock is exercised from one process.

**Review gate and publication.** The verdict is `builds.review_status`; publication is `builds.status = 'live'`. The gate stands in front of that status, not in front of the site (see "Preview, review and live"). This is the one full statement of the gate; the other documents point here.

- *Entering review.* Every arrival at `preview` sets `review_status` to `pending` (or `ai_review_queued` under `CAS_HARBOR_AUTO_REVIEW`) and clears the previous verdict in the same statement (`_set_preview_status` in [worker_pg.py](../queue/worker_pg.py); the optional status hook does the same, through `initialReviewStatus`, and a test lands one build through each and compares the rows). Every web statement that sends an existing row back to `queued` clears it too (`REVIEW_RESET_ASSIGNMENTS` in [builds.ts](../web/src/routes/builds.ts), used by the retry, reset and requeue statements in `builds.ts`, [admin.ts](../web/src/routes/admin.ts) and [ops-api.ts](../web/src/routes/ops-api.ts)). A verdict therefore covers one arrival at preview, not the row.
- *Deciding.* `/admin/reviews` ([admin.ts](../web/src/routes/admin.ts)) records approve or request-changes (notes required). It touches `review_status`, never `builds.status`, and records a verdict only on a build at `preview`: the `UPDATE` locks the row and carries `b.status = 'preview'`, and a build in any other status gets a 409 page with nothing recorded and no email (`refuseVerdictOffPreview`; tests in [harbor-account-claims.realdb.test.ts](../web/tests/unit/harbor-account-claims.realdb.test.ts)).
- *What the reviewer is shown.* The review page shows the build row, the preview address, the stored screenshots, the last 20 log entries and the build's warnings: what the engine wrote about its own decisions and, apart from it and labelled as such, the text the spec carried, which is attacker-influenced and is never presented as an engine finding.
- *Publishing.* Three statements write `live`, each a single `UPDATE` with its conditions in the `WHERE` clause:

| Path | Requires |
|---|---|
| Owner: `POST /builds/:buildId/approve` (`CUSTOMER_APPROVE_SQL` in [builds.ts](../web/src/routes/builds.ts)) | A logged-in session that owns the build; `status = 'preview'`; `review_status = 'approved'`; and, for a Harbor build (`builds.is_harbor`), a subscription on the owner's keeper row whose status is `active`, `trialing` or `past_due` |
| Admin: the same route (`ADMIN_APPROVE_SQL`) | An admin session; `status = 'preview'`. No review and no subscription condition: the admin is the reviewer and the operator, and this is an intentional bypass |
| Stripe: `checkout.session.completed` for a Harbor subscription (`handleHarborMakePublic` in [webhooks.ts](../web/src/routes/webhooks.ts)) | A valid Stripe signature; a session whose `payment_status`, when present, is `paid`; the build row locked with `FOR UPDATE`; `status = 'preview'` and `review_status = 'approved'` |

- *The schema file is not a writer of `live`.* `schema.sql` is applied at every boot, on every row, and it writes or defaults no build to `live`. [check_destructive_ddl.py](../scripts/check_destructive_ddl.py) (the pre-commit hook, on the staged content) and [schema.idempotency.test.ts](../web/tests/unit/schema.idempotency.test.ts) (the pre-push hook, with a reader of its own) both refuse, whatever comment is above it, any row change or dynamic `EXECUTE` that names the string `live` and any `DEFAULT` of `live`; every other row change needs a `-- SAFE:` reason of its own and is listed in that test (the file has nine, all `UPDATE` backfills inside `DO` blocks); and the merge guard keeps an executor branch out of the file and out of `migrate.ts`. The check reads literal text: a value built by concatenation, an escape or a variable is not followed, so the reason a person writes is the control for those.
- *Which subscriptions publish.* The keeper row holds Stripe's status word for word; `unpaid`, `paused`, `incomplete`, `incomplete_expired` and `canceled` do not publish (`PUBLISHING_SUBSCRIPTION_STATUSES` in [keeper_promotion.ts](../web/src/services/keeper_promotion.ts)). The row's default status is `active`, so the gate also requires a Stripe subscription id on it.
- *Source download.* The owner's download of a build's source follows the same rule: it is served for a `live` build or for one the owner could publish right now (`OWNER_SOURCE_DOWNLOAD_SQL`). The admin can download any preview or live build.
- *Nobody else.* The worker has no statement that writes `live`. The coordinator cannot promote: it has no method or permission that approves or promotes a build; an approval request is filed only by an agent's escalation or the reconciliation agent, is advisory, and is rejected after 4 hours unanswered ([actuators.py](../coordinator/actuators.py), [test_coordinator_actuator_gates.py](../tests/test_coordinator_actuator_gates.py)), and approving a request in `/admin/approvals` updates that row and nothing else. The ops API has no route that writes `live`, the optional status hook refuses it, and `schema.sql` has none.

What the gate leaves free (builds that are not Harbor builds, a subscriber's other builds, anything after `live`) is listed under Known limitations.

**What the build worker trusts.**

- Spec text: nothing (the build engine above). `builds.app_name` and URLs from database rows are input too: the name must pass `_is_safe_dir_name` before it becomes a directory, and URLs pass the guards below. An `app_name` that starts with `craftandship`, the prefix `destroy_project` refuses to delete, is refused by the spec gate (`_spec_safety_errors`) and by `deploy()` before any Railway call (`RESERVED_PROJECT_NAME_PREFIX` in [deploy.py](../cli/deploy.py)), and the web translator prefixes `site-` to such a name, so no project is created that the worker could not clean up (`TestReservedProjectName` in [test_deploy_security.py](../tests/test_deploy_security.py)).
- Model output: data. There is none in the v2 build path. In v1 it becomes files and then child processes, without the worker's secrets but as the same user in the same container.
- Railway responses: ids and state. Domains still pass `probe_url_problem`, and a project is deleted only after its name was read back and checked against the protected names. `destroy_project` fails closed and returns only when Railway confirmed the delete; any other outcome raises, so a caller that gets no exception may say "deleted" (`TestDestroyProjectIsTruthful` in [test_probe_guard.py](../tests/test_probe_guard.py)).
- Deployed customer apps: untrusted. The probes and the review browser that load them are described under the outbound request guards below; the browser is launched with a scrubbed environment.

**Outbound request guards.** Every place the platform fetches an address that data can influence:

- *Faithful-copy crawl* ([site_copy_crawl.ts](../web/src/services/site_copy_crawl.ts), admin-triggered). Ports 80 and 443 only, no credentials in the URL, textual checks for private, internal and special-use hosts, IPv6 literals included: the transition ranges that embed an IPv4 address (6to4, NAT64 and local-use NAT64, IPv4-translated, IPv4-compatible, Teredo), site-local, multicast, discard-only and the IPv4 and IPv6 documentation ranges (`PRIVATE_ADDRESS_RANGES`; for a literal address that check is the whole guard, because no name is resolved), and a transport (`createPinnedFetch`) that resolves the name inside the socket's own lookup hook and connects only to an address that passed, then re-checks the peer address, so a DNS answer cannot change between check and use. Redirects are followed by hand, at most three, within the same site. Bounded by page count, 16 KiB of headers, 2 MiB of decompressed body, page paths of at most 200 characters and media URLs of at most 2048. A request is abandoned 15 seconds after it starts, wherever it is by then (the DNS check, a redirect hop, the body read), and the whole crawl has a 60-second deadline. The HTML that comes back is segmented by single-pass scanners ([site_copy_parse.ts](../web/src/services/site_copy_parse.ts)) in a `worker_threads` worker with a 10-second kill and a 256 MB heap cap (`ParseWorker`; the cap is soft, see KNOWN_LIMITATIONS.md), so a page built to make parsing slow costs one abandoned crawl and does not hold the web process's event loop, which also serves the crisis handler.
- *Link lint* ([compose/lint_external_urls.py](../compose/lint_external_urls.py)). HEAD requests to external URLs found in the spec, through `_guarded_create_connection`, which resolves the host and refuses unless every address is public, on the connection it actually opens. Every redirect target passes the same precheck as the first URL (ports 80 and 443, no credentials), and the body of a redirect is not read. At most 40 URLs per build; a 60-second budget is enforced on every connect and header read; proxies ignored; fail-open by design. A refused destination is reported as "refused: resolves to a non-public address" (`BLOCKED_DESTINATION_TEXT`): the warning names the URL the spec supplied and never the address it resolved to. The walk over the spec is iterative, and the build report's `external_url_lint:` line says whether the lint was skipped, ran or failed (a lint that raised judged no URL; the warning `external_url_lint_error` says why). `CAS_LINT_EXTERNAL_URLS=skip` turns it off.
- *Monitor and deploy probes* ([monitor/ping.py](../monitor/ping.py), [cli/deploy.py](../cli/deploy.py)). Two layers. `probe_url_problem` checks the text of a URL with the parser that sends it (urllib3) and refuses a URL the standard library reads differently, non-http schemes, embedded credentials, host names with characters outside letters, digits, dots and hyphens, internal names, legacy numeric host spellings and non-public literal addresses. The requests themselves go through `guarded_session`, whose connections resolve the host once, refuse unless every address is public and connect to the address they checked; every redirect hop is checked again, and proxy settings are ignored. The health checks follow no redirects. The supervisor's watchdog probe, the reconciliation agent (through that probe) and the security agent's daily scan send through `guarded_session` as well. `_app_url` and `_same_origin_session` also keep the deploy probes on the app's origin. The login probe signs in with the worker's own verification token by POST (`verify_magic_link_auth`), so that token is never in a URL and is used up.
- *Bounds on outbound requests.* Every request `guarded_session` sends is one bounded exchange ([monitor/bounded_fetch.py](../monitor/bounded_fetch.py)): the `timeout` a caller passes is a deadline for the whole exchange (name lookup, every connection attempt, TLS handshake, request, headers, body and at most 5 redirect hops), not a per-read timeout, and a fixed number of decoded body bytes is kept: 64 KiB for a health check, 2 MiB for a page probe, 4,096 bytes for the watchdog probe. A gzip or deflate body is inflated by a decompressor that is never asked for more than the room left, any other `Content-Encoding` is refused, and at the cap the connection is dropped. Deadlines: 10 s for a monitor ping, 5 s per `verify_health` poll, 5 to 12 s for route, login and data probes, 5 s per URL inside a 20 s budget for the watchdog probe, 10 s per app inside a 600 s budget for the security scan, 10 s for the certificate check. Provider calls: Railway 30 s per attempt and at most 5 attempts (20 s from the monitor and backups, 30 s and 256 KiB from ops playbooks), 4 MiB; Resend 10 s, 64 KiB; the Anthropic cost report 10 s per page, at most 5 pages, 4 MiB each. Model clients are built with a 60 s timeout per phase and one retry (a per-phase limit, not a deadline for the call). Before this, a `/health` that sent one byte per read held a probe for 11 s at a 1 s timeout, a 40 MiB body was read in full and 24 KiB of gzip became 24 MiB. [test_bounded_fetch.py](../tests/test_bounded_fetch.py) also fails on any other outbound client in the Python packages.
- *Review browser* ([cli/deploy.py](../cli/deploy.py)). `_guard_browser_page` aborts any request in the browser to a host that fails `probe_url_problem` or resolves to a non-public address, and blocks service workers and downloads. It checks and cannot pin: the browser resolves the name again (see limitations). Each page gets a 10 s step timeout and a 20 s navigation timeout, a full-page screenshot is cut at 16,000 px of height, and `verify_render` (60 s) and `capture_deploy_screenshots` (90 s) start no further page once their budget is spent. The browser's memory is not capped.

Residuals are listed under limitations. Tests: [services.site-copy-crawl.test.ts](../web/tests/unit/services.site-copy-crawl.test.ts) with its `linear-time`, `time-limits`, `parse-worker`, `reference` and `address-ranges` companions in the same directory (the last refuses each special-use literal before any socket connects), the SSRF cases in [test_spec_hardening.py](../compose/tests/test_spec_hardening.py), [test_lint_external_urls.py](../compose/tests/test_lint_external_urls.py), [test_probe_guard.py](../tests/test_probe_guard.py) (the guard against what is sent on the wire, pinning, the login probe), [test_login_probe_generated_router.py](../tests/test_login_probe_generated_router.py) (the probe against the router the engine emits), `TestProbeUrlGuard` in [test_ops_monitor_hardening.py](../tests/test_ops_monitor_hardening.py), `TestProbesRefuseInternalBaseUrls` and `TestBrowserGuard` in [test_deploy_security.py](../tests/test_deploy_security.py).

**Uploaded logos.** `POST /intake/:buildId/logo` in [intake.ts](../web/src/routes/intake.ts) is the only file upload in the web app: any logged-in customer, at most 2 MB, at most 20 uploads per 15 minutes per customer (checked before the body is read). The first bytes decide what reads the file ([logo.ts](../web/src/services/logo.ts)):

- PNG, JPEG and WebP are decoded by the image library under a 24-megapixel limit checked from the header, first frame only, with decoder warnings treated as errors, and re-encoded as a PNG of at most 512 pixels.
- An SVG never reaches the image library and is never drawn on the server. [svg_sanitize.ts](../web/src/services/svg_sanitize.ts) rebuilds it from an allowlist of elements and attributes (no script, event handlers, `foreignObject`, embedding or animation elements, processing instructions, doctype or entities; references only to `#id`, embedded raster data on `<image>`, and http(s) or mailto on `<a>`; `@import` and external `url()` removed) in one pass proportional to its length, in a worker thread with a 5-second kill, and reads its size and palette from the text. When too many rebuilds are already running the route answers 503 with `Retry-After`.

**Coordinator budget and permission gates.**

- *One gate.* The writes, sends and model calls of a coordinator agent, and of the failure-triage step in work detection, are made through `Actuators` in [actuators.py](../coordinator/actuators.py), which checks analysis-only mode and the caller's entry in `AGENT_PERMISSIONS`, then dry run (the default), and logs the action. The table has eleven principals and nine permissions (29 pairs): `railway_deploy` and `railway_env` gate `run_playbook` and only `infra_engineer` holds them; `approval_request` gates `create_approval_request` and is held by `infra_engineer`, `security`, `financial`, `customer_service` and `reconciliation`. An agent cannot build its own `Actuators`: the constructor raises `PermissionError` for a caller in the `coordinator` package other than `coordinator.tick` and `coordinator.work_detection`. That is a check on first-party code, not a sandbox. What keeps an effect from going around it is an import rule, not a proof: outside `actuators.py` a coordinator module may import only an allowlist of standard-library modules and other coordinator modules, and a network, subprocess, database or model library, or first-party code from outside `coordinator/`, fails the test unless it is listed there with a reason.
- *Dry run.* A gated method records what it would have done and writes, sends and spends nothing. One method is exempt because its only effect is an entry a person reviews: `finding_add`. `create_approval_request` is gated like the rest: refused in `COORDINATOR_ANALYSIS_ONLY` mode, recorded and not filed under dry run. Reads and the tick loop's own bookkeeping are outside the gate.
- *Limits on live actions.* A redeploy and a Railway variable write are reachable only through `Actuators.run_playbook`. Nothing in `ops/` or `coordinator/` commits to a repository. Their limits are enforced in [ops/fixer.py](../ops/fixer.py), in the functions that make the call, so they hold for the legacy ops agent as well: `trigger_redeploy` and `upsert_env_var` act only on the configured web and worker services in the configured environment; `upsert_env_var` sets only `DATABASE_URL`, `RESEND_API_KEY` and `ADMIN_EMAIL` (`SETTABLE_ENV_VARS`). `queue_rebuild` refuses a deterministic failure, a customer at the build-start limits, a parent with a child in flight or `COORDINATOR_MAX_REBUILDS_PER_BUILD` (2) rebuilds in 24 hours, and a lineage with `COORDINATOR_MAX_REBUILDS_PER_LINEAGE` (3) automatic rebuilds in 7 days. Unanswered approval requests are rejected after a timeout, never approved.
- *A task past its deadline.* A task whose agent runs past the round's deadline is marked failed then; its actuators refuse from that moment (every gated call and `create_approval_request`) and its late result is discarded. The thread is not stopped ([tick.py](../coordinator/tick.py)).
- *The admin settings page* ([coordinator-settings.ts](../web/src/services/coordinator-settings.ts), [env-switch.ts](../web/src/utils/env-switch.ts), [admin-settings.ejs](../web/views/admin-settings.ejs)) shows each switch as the worker's parser reads the stored text, writes only the settings that were changed, and refuses to turn dry run off or enable the coordinator without the typed phrase `go live`. It can write one service's variables (the worker's, `RAILWAY_WORKER_SERVICE_ID`, with `RAILWAY_ADMIN_TOKEN`), only twelve names from a list in the code (`COORDINATOR_ENABLED`, `COORDINATOR_DRY_RUN`, `COORDINATOR_DAILY_BUDGET` from 0 to 500, `COORDINATOR_INTERVAL_S` in whole seconds from 300 to 7200, and eight `AGENT_*_ENABLED`), and only `true` or `false` for a switch. A save needs `isRailwayWriteEnabled()`, an admin session and a CSRF token; changes toward the safe state are sent first, and the save stops at the first Railway failure. Variables the page cannot read are not drawn, and then nothing can be saved. The page reads the worker's variables with `RAILWAY_ADMIN_TOKEN`; `fetchWorkerVars` in [admin.ts](../web/src/routes/admin.ts) keeps only the twelve setting names and drops every other value before the page or a log sees it, though Railway returns the whole map to the web process for the length of the request.
- *Budget.* [budget.py](../coordinator/budget.py) gives a tick nothing to spend, zero dollars and zero model calls, when today's spend cannot be read from its one configured source: the Anthropic cost report when `ANTHROPIC_ADMIN_KEY` is set, otherwise the worker's own ledger. No earlier figure is substituted. Unknown is never read as zero: a cost report without a list under `data`, without a bucket for today, with a non-USD or non-finite amount, or with `has_more` and no `next_page` makes today's spend unknown (a result with no `amount` counts as zero, and one with no `currency` counts as USD); a figure whose refresh failed is `None`, and unknown pipeline counts are read as a customer build in progress. Within a tick each dispatched task is charged its estimated cost and one call, and every model call, failure triage included, is granted one at a time by a per-tick meter inside `Actuators.authorize_model_call` (`ModelCallMeter`); an `Actuators` instance that was handed no meter grants none. The meter counts calls at fixed estimates, not tokens.
- *What stays free of the budget.* A tick with no budget still dispatches the tasks whose agent declares their category model-free (`model_categories`; an app-down alert is one) from an unmetered allowance, and the meter grants no model call at zero ([tick.py](../coordinator/tick.py), [test_coordinator_model_free_tasks.py](../tests/test_coordinator_model_free_tasks.py)).
- *Reads.* `query_readonly` runs exactly one statement, counted by a lexer for PostgreSQL text ([sql_statements.py](../coordinator/sql_statements.py): nested comments, strings, E strings, quoted identifiers, dollar quotes), checked as written and again as psycopg2 sends it, in `BEGIN READ ONLY` on a session whose `default_transaction_read_only` is on, with a 15-second connect and statement bound. A read-only transaction does not stop a function that acts outside the connection (dblink and the like; the platform's schema installs no extension), and a lock the statement takes lasts until the connection closes ([test_coordinator_readonly_query.py](../tests/test_coordinator_readonly_query.py)).
- *What an agent reports.* Each alert, finding, KB entry, rebuild and approval request an agent asks for comes back as sent, recorded, queued, dry_run, refused or failed (`Effects` in [base.py](../coordinator/agents/base.py)); the tick stores the list in the task row's `result` and logs a refused or failed one, and an alert-only task's success follows it ([test_coordinator_agent_effects.py](../tests/test_coordinator_agent_effects.py)).
- *Prompts.* Customer text inside coordinator prompts is wrapped as data by [untrusted.py](../coordinator/untrusted.py), which replaces every `<` so the text cannot open or close a tag. `monitor/diagnose.py` wraps deployment logs with the same function (last 50 lines, at most the most recent 64,000 characters, redacted, cut to 8,000). A model reply can add one allowlisted fix and cannot remove the notification: every run ends in `_escalate`. It is a mitigation, not a boundary.

## What a generated site does not defend against

These describe the v2 engine's output ([compose/build.py](../compose/build.py)). They are properties of the generated code, so a review of an individual site does not change them.

- **Being found before it is approved.** A preview is not private: see "Preview, review and live" above. The emitted `server.js` sends no `X-Robots-Tag` and has no switch that would close the site until it is published.
- **Password guessing beyond per-address limits.** `emit_middleware_rate_limit_js` limits login to 10 attempts per 15 minutes per address, in memory, per instance. There is no lockout, no MFA and no breach check.
- **A spoofed Host header.** The links a site emails (the login link and a form notification's "View in admin" link) are built on `SITE_ORIGIN`, which `deploy()` sets to the Railway domain once the first deployment runs, else on the stored `site_url`, and never on the `Host` or `X-Forwarded-*` headers (`linkOrigin` in `emit_middleware_settings_js`). With neither, the login link is not emailed and the notification carries no link (when no mail key is set the requested link is logged as a path, for the operator). Pages still build their absolute Open Graph and canonical URLs, and `robots.txt` and the sitemap their origin, from the `Host` of the request they answer when `site_url` is unset; that answer goes only to the requester. Tests: the link cases in [test_generated_app_runtime.py](../compose/tests/test_generated_app_runtime.py), `test_with_a_mail_key_the_login_link_goes_to_the_mailbox_and_not_to_the_log` in [test_generated_site_security_e2e.py](../compose/tests/test_generated_site_security_e2e.py), `TestSiteOrigin` in [test_deploy_security.py](../tests/test_deploy_security.py).
- **Log readers, when no mail transport is configured.** With no `RESEND_API_KEY`, `POST /request-magic-link` writes the login link to the server log so the owner is not locked out; that line is the only place the app prints a login token. With a mail key the app does not log the token: the access log records request paths and referrers without their query strings, the CSRF-mismatch line does the same, and a request body the parsers reject is logged by error type only (`emit_server_js`, `emit_middleware_logging_js`). Whatever sits in front of the app (a reverse proxy, the hosting platform's request log) still sees the full URL of a login link, and opening a link by GET does not use the token up. If the mail send fails the link is lost, not logged.
- **A hostile or compromised admin.** There is one admin role with full create, read, update and delete on every model, and no audit log. Pages can list other roles (`allowed_roles`; a page that lists roles requires a login even when it is not marked `auth_required`, any one listed role passes, and `user` means any signed-in account), but the site has no sign-up and no user management: an account other than the seeded admin exists only if the operator inserts a row into `users`. Role names other than `admin` and `user` are compared exactly, letter case included.
- **CSS injection by policy.** The emitted CSP keeps `style-src 'unsafe-inline'`.
- **Session table growth.** The CSRF middleware writes a token into the session of every visitor, so every first-time visitor creates a 30-day `user_sessions` row.
- **Stolen sessions.** A session lasts 30 days. Setting a password (`/set-password`, `/admin/change-password`) ends every other session of the account (`endOtherSessions` in `emit_middleware_auth_js`), though a request of another session that is in flight at that moment can write its row back. The role is copied into the session at sign-in, so changing or deleting a `users` row does not affect sessions already open. Replacing an existing password needs the current one, except within 15 minutes of a login-link sign-in (`passwordChangeRule` in `emit_routes_auth_js`), and the first change made that way spends the allowance, so at most one such change is possible in the window; an account that has no password yet can set one from any signed-in session. Opening a login link (`HEAD` and `GET /magic`, which spend no token) is limited to 60 requests per 15 minutes per address (`magicLinkOpenLimiter`).
- **Upload content.** Admin uploads are accepted by extension (raster images only; SVG excluded) and declared type, up to 10 MB each, and written to the app's local disk with a generated name (`deploy()` attaches no volume). There is no content scanning and no quota.
- **Spam on public forms.** CSRF token, honeypot (`website_url_hp`, on the custom form pages, the contact form and the newsletter signup; a filled one gets the normal answer and nothing is stored) and a per-address limit; no CAPTCHA. A submission is validated and, where the model has a boolean `published` column, held unpublished; a public form page takes only the columns its `allowed_fields` names.
- **A spec model on a table an archetype page reads.** A layout names a table, so a spec model that redefines the archetype's model of that name (a `Testimonial`, a `Review`), or takes the table through `plural`, is what the archetype's page shows. The build report says so (`spec_model_shown_by_archetype_page`); nothing refuses it.
- **An explicit listing is taken at its word.** `public_listing_path` in a spec publishes that model's rows whatever it holds. The spec is written by a model from a conversation, and the engine does not judge whether the listing was meant.
- **Duplicate newsletter addresses under a race.** The signup stores an address only if it is not stored yet, in one statement, but the table has no unique constraint, so two simultaneous signups with one address can both be stored.
- **Publication warnings do not block.** They are in `compose-manifest.txt` and `translation-warnings.txt`, and the worker copies every warning line of the manifest's first 256 KiB into the build log (`_manifest_warning_checks` in [worker_pg.py](../queue/worker_pg.py)): the engine's own `warning:` lines first, then the `spec-warning:` lines the spec carried, a bounded and cleaned copy, so a spec cannot add, remove or imitate an engine line (the shape is stated once, in [V2_ENGINE_BEHAVIOR.md](internals/V2_ENGINE_BEHAVIOR.md)). The review page shows all of them for the build's latest lint run (`readBuildWarningLog` in [admin.ts](../web/src/routes/admin.ts)): the engine's warnings in the engine's order, the spec's text in a separate box labelled as not written by the engine, and the lint's failure lines, among them the two that say the list in the log is incomplete. Every value is escaped. Nothing makes a reviewer read them, and an approval does not depend on them.
- **Wrong proxy depth.** The app trusts exactly one proxy hop.
- **Dependency drift.** The emitted `package.json` uses caret ranges and no lockfile is emitted, so a deploy installs the newest matching release.
- **SQL reserved words as field names.** Column names are not quoted, so a field named like a reserved word makes the schema fail at first boot. It is a failed deploy, not an exposure.
- **Secrets the platform hands it.** An app has whatever the deploy gave it: its own database URL, its session secret and, if the operator set one, the shared mail key.

## Secrets in this repository

The public history is new: it contains no commits from the private repository this code came from. The working tree is scanned with gitleaks using [.gitleaks.toml](../.gitleaks.toml), which uses the default rules plus one allowlist entry: a `generic-api-key` finding whose value is exactly 64 lowercase hex characters is suppressed in the one file `tests/golden/medicine-waves-canonical/artifact.snapshot.json`, where such values are SHA-256 content hashes (one sits on a line whose key contains the word "password"). A real secret of that shape in that file would be suppressed too, and a `--no-git` scan given an absolute `--source` names the file by its absolute path and so reports the hash; run it from the root with `--source .`. `test_the_gitleaks_allowlist_hides_a_hash_in_the_golden_snapshot_and_nothing_else` in [test_dev_scripts.py](../tests/test_dev_scripts.py) checks the entry (it skips without gitleaks on `PATH`). Tests that need secret-shaped values assemble them at runtime instead of storing them, and [web/.env.example](../web/.env.example) holds placeholders only: the local development database URL that matches `docker-compose.yml`, and a session-secret placeholder that the server refuses to sign with. The `secrets` job in [test.yml](../.github/workflows/test.yml) runs gitleaks with the same rules over the full git history, on pushes to the default branch and on pull requests; it is not part of the local git hooks.
