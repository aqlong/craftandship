# CAS Harbor implementation notes (migrated from CLAUDE.md, 2026-07-03)

Verbatim implementation/changelog narratives for the Harbor companion + make-public work,
moved out of CLAUDE.md to keep session context lean. The condensed module map in CLAUDE.md
is the working reference; this file is the detail archive. Facts here were accurate as of
their inline dates; trust the code over this file.

**New modules (2026-04-26: CAS Harbor Phase 1):**
- `src/companion/`, companion runtime for the CAS Harbor pivot. Modules: `runtime.ts` (turn lifecycle), `prompt.ts` is folded into `persona.ts` for Phase 1; `persona.ts` (Haven persona prompt + per-keeper context block; `assignCompanionName()` returns `'Haven'` for MVP, a single companion persona).
  - **Persona structure (revised through 2026-04-26 dogfood iterations):**
    - WHAT THIS PLACE IS, WHERE WE ARE RIGHT NOW (Phase 1 has no automated hand-off; Ocean does it manually; Haven must not promise "the spec is going to the engineering side"),
    - YOUR WORKING ARC (LISTEN → REFLECT → GATHER → PROPOSE → SKETCH; explicit transition phrase; "no product to sell" regression guard),
    - GENTLE SCREENING (soft screening for poor-fit requests; soft door, never reject),
    - WHO YOU ARE (AI honesty + half-non-transactional / half-arc-progressing),
    - WHAT YOU NEVER DO (hard rails: therapy / medical / legal refusal; no fake content; **no-browse rule** added 2026-04-26, Haven cannot claim to read URLs the keeper shares; "Never refuse the build itself" replacement of the old "AI builds your website" rule),
    - THE METAPHORS WE USE HERE, HOW YOU REMEMBER + OPENING + VOICE NOTES,
    - **WARMTH AND ACKNOWLEDGMENT** (calibrated flattery: mild affirmations OK, one medium-warm acknowledgment near the start + one near the handoff if justified; "Beautiful / Perfect on every turn" is the named anti-pattern), closing rule.
  - Tested by `web/tests/unit/companion/persona.test.ts` covering each section, working-arc steps, screening anti-patterns, no-browse rule, warmth calibration, and the WHERE WE ARE RIGHT NOW honest-handoff. Plus regression guard in `ai_honesty_rail.test.ts` that build-related asks never trigger a rail flag.

  - `markdown.ts`: tiny purpose-built markdown→HTML renderer for companion turns (bold, italic, paragraphs, bullet lists). Exposed twice: `renderCompanionMarkdown(text)` for server-side EJS render, and `RENDER_COMPANION_MARKDOWN_CLIENT_JS` (a self-contained JS string) for inlining into the chat view's script tag so client-side appended turns render identically. Test asserts parity by running both implementations against shared fixtures.

  - `ai_honesty_rail.ts` output flags now classified by severity (`OUTPUT_FLAG_SEVERITY`): `dangerous` flags (e.g. `output-claims-personhood`) replace the entire response with the deterministic refusal template; `hygiene` flags (e.g. `output-uses-em-dash`) are sanitized in-place via `sanitizeOutput()` (em dashes → semicolons; idempotent). This fixes the 2026-04-26 dogfood iteration 2 finding where a single em-dash slip nuked 700 chars of valid response down to a 137-char recovery template.

  - `memory_capture.ts` and `memory_retrieval.ts` are tolerant of embed failures.
    - If `OPENAI_API_KEY` is unset OR the embed call throws (quota / network / bad key), capture still runs the Haiku classifier and persists rows with `embedding=NULL`; dedupe falls back to normalized-content equality; retrieval falls back to recency-only ordering. Lets the operator dogfood Haven's memory layer entirely without OpenAI.
    - **Verified 2026-04-26:** a 10-turn synthetic dogfood run with `OPENAI_API_KEY` unset captured 60 memory rows (58 working + 2 sacred), zero rail flags.
    - The chat surface (`web/views/lighthouse/table.ejs`) renders Haven's bold + bulleted-list markdown correctly server-side and client-side, with markdown parity asserted in the test suite.
    - **Companion modules:**
      - `memory_retrieval.ts` (JS-side cosine ranking + recency boost over `keeper_memory.embedding DOUBLE PRECISION[]`; no pgvector at MVP scale),
      - `memory_capture.ts` (Claude Haiku classifier into 0-N items, dedupe at >0.93 cosine, sacred flag at >0.7 sacred_likelihood; classification is best-effort and non-blocking),
      - `ai_honesty_rail.ts` (deterministic regex scans for impersonation/roleplay/therapy/medical/legal/fake-content/keeper-impersonation requests, plus output scans for personhood claims and em-dash slips; `railTemplate(flag, companionName)` returns the deterministic-reply template the runtime uses to short-circuit the Claude call),
      - `crisis_detection.ts` (a regex scan over normalized text for suicide, self-harm, harm-to-others, abuse and acute-medical disclosures, with a crisis-script template that names AI status, points to 988 + findahelpline.com, and names 911 or the local emergency number for abuse, for a threat to another person and, first, for a medical emergency; its measured recall and known misses are in `docs/KNOWN_LIMITATIONS.md`).
        - On detection the runtime fires `notifyHarborMaster()`, which both `console.warn`s the alert and lazy-imports `services/email.sendCrisisAlertEmail` to email `ADMIN_EMAIL` with the categories, trialId and keeperId (added 2026-04-28). Email failures are caught and logged and never cascade into a turn failure, so a Resend outage cannot break the keeper-facing crisis script. Tested by 2 cases in `web/tests/unit/companion/runtime.test.ts` (the success path asserts the spy was called with categories and trialId; the failure path asserts `mockRejectedValueOnce` does not throw).
      - `claude.ts` (Anthropic SDK wrapper with two-block prompt caching: persona prefix + per-keeper memory block both `cache_control: ephemeral`; `computeCostMicros()` for per-turn cost log),
      - `embeddings.ts` (OpenAI text-embedding-3-small via fetch, no SDK dependency),
      - `cosine.ts` (pure cosine similarity helper).
    - Companion runtime is invoked by the `/lighthouse/*` routes only; everything is gated by `CAS_HARBOR_ENABLED=true`.
- `src/middleware/trial-cookie.ts`: mints + reads `cas_harbor_trial` cookie (an opaque random bearer token, 32 bytes hex, looked up in `trial_keepers.cookie_token`; it is not signed, and the database lookup is the whole validation; 7-day TTL, HttpOnly/Secure-unless-development-or-test/SameSite=Lax).
  - Each fresh visitor gets a row in `trial_keepers` with companion_name='Haven'.
  - The cookie is the identity for Phase 1; no email, no password, no card. Phase 2 layers trial-to-keeper conversion + Stripe.
  - After a payment releases the trial, the cookie keeps one narrow meaning until `expires_at` (promotion moves it to `PAID_TRIAL_ACCESS_DAYS`, 30, from payment): "this browser paid for the build stamped on this trial".
    - `loadPaidKeeper` follows trial, then its `handoff_build_id`, then that build's `customer_id`, then a `keepers` row, and sets `req.harborPaidKeeper`; nothing in a URL takes part, so a build id or the Checkout session id identifies nobody.
    - It is not an account session (`req.session.customerId` is not set): it opens the lamp pages of that one build, the conversation that promotion moved to the keeper, and continuing it.
    - A released trial without that chain gets a fresh trial like any stale cookie.
- `src/routes/lighthouse.ts`: CAS Harbor /lighthouse surface (Phase 1, hidden behind feature flag). Routes:
  - `GET /lighthouse` redirects to /lighthouse/table
  - `GET /lighthouse/table` renders the chat UI (uses its own `views/lighthouse/table.ejs` layout; opening message is deterministic on first visit)
  - `POST /lighthouse/table/turn` accepts `{ keeperText }` (≤4000 chars), returns `{ companionText, turnId, railFlags }` (the runtime's `turn()` still computes `costMicros` and logs it to `companion_cost_log`, but the route no longer sends cost figures to the client)
  - `GET /lighthouse/table/recall` renders an HTML page (`views/lighthouse/recall.ejs`) showing what Haven remembers about the keeper. Pass `?format=json` for the raw rows. When `OPENAI_API_KEY` is unset, the page shows a "lite mode" note explaining that capture is on (Claude Haiku classifier + normalized-content dedupe + persisted memory rows) but ranking is recency-only until an embedding provider is wired up. Returns up to 200 items, ordered by `updated_at DESC`.

  **Admin-gated dev override (`?dev_trial=<uuid>`):** when `NODE_ENV` is `development` or `test` (`isDevOrTestEnv()`; originally the check was `!== 'production'`) AND the session passes `isAdminSession(req)` (originally `req.session.customerEmail === process.env.ADMIN_EMAIL`) AND a UUID-shaped `dev_trial` query param is present, both `GET /lighthouse/table` and `GET /lighthouse/table/recall` look the trial up directly and override `req.harborTrial`, letting the admin (Ocean) revisit any past keeper conversation or recall page by link without juggling cookies.

  - **Hard-gated off everywhere except `development` and `test` (any other `NODE_ENV`, including unset, counts as production). Hard-gated off for non-admin sessions even in dev** so a third party who tunnels into a local dev server (or shares a screen) can never load another keeper's memory or chat by pasting a UUID, without admin auth, the override is silently skipped (logged as `[lighthouse-dev-trial] override REFUSED (non-admin)`) and the cookie identity stays.
  - Read-only: `POST /lighthouse/table/turn` and other state-changing routes don't honor the override at all (cookie-based identity stays authoritative for any state-mutating call).
  - The `/admin/harbor` master inbox links to dev_trial views as the canonical entry point.
  - The "what Haven remembers about you" link on `/lighthouse/table` opens the recall surface in a new tab via `target="_blank" rel="noopener noreferrer"` so the keeper never loses their conversation.
  - New gate covered by 3 tests in `web/tests/unit/routes.lighthouse.test.ts` (admin-honored override; anonymous-refused override; non-admin-logged-in-refused override).

  Mounted in `app.ts` only when `CAS_HARBOR_ENABLED=true` so a careless deploy never exposes the surface before it's ready.

  **Whose conversation a request speaks in** is decided in one function, `resolveCompanionIdentity`, which the conversation page and its notes panel, the turn route, the recall page and the template picker with its choice all ask.

  - An account session whose customer has a `keepers` row is that keeper (rows keyed by `keeper_id`); otherwise the browser that paid (`req.harborPaidKeeper`, only if its trial was promoted into that keeper: `trial_keepers.promoted_customer_id`) is the same keeper; otherwise the cookie's trial (`trial_id`). The account session wins when a browser holds both for different accounts.
  - Payment moves a trial's turns and notes to the keeper, so after it the trial id finds nothing: reading or writing by the wrong key was silent (an empty page, a turn stored where the next load did not look).
  - The crisis handler is the one writer that does not use it, because it answers before the session loads; it files its turn from the trial cookie alone (`fileCrisisTurn`).

  **Crisis messages are answered first.** `crisisFirst(pool)` in `routes/lighthouse.ts` is the first handler on `POST /lighthouse/table/turn`, and `app.ts` also mounts it directly after the body parsers when `CAS_HARBOR_ENABLED=true`, ahead of the session middleware.

  - It decides from the request body and the regex scan alone (`scanCrisis`, over at most the first 20,000 characters, flagging any text with more than 24 mentions it would have to weigh), writes the fixed crisis reply (the default companion name, 988 and the other resources) before the trial-cookie lookup, both rate limiters, the length check, the email gate and the cost caps, and so with the database down or hanging. Only afterwards, in the background, does it identify the sender (read only; no trial is minted), store the turn flagged for review and alert the operator.
  - Those two steps are bounded by `crisisSideEffects` in `companion/runtime.ts` because the path is not rate limited: one alert email per identity per 30 minutes and 10 per hour per process, 20 stored crisis turns per identity per 15 minutes, and 60 per process per one-minute window across all identities (`CRISIS_PERSIST_MAX_PER_MINUTE`), counters in process memory; past the limits the crisis is recorded in the server log only.
  - A sender with no usable trial cookie gets the same reply but the turn is not stored.
  - The cross-origin write guard still applies (a cross-site request is passed on to be refused).
  - `turn()` keeps its own crisis branch for requests that do not arrive through this handler.

- `src/routes/admin.ts`: `GET /admin/harbor` (added 2026-04-27; expanded 2026-04-28 with status filters + 4-card stats). Read-only master inbox listing every active CAS Harbor trial (`released_at IS NULL`) ordered by `last_seen_at DESC` with turn count, memory count, last-seen, opening keeper words, and a `READY` badge when `turn_count >= 8` OR Haven's last reply matches `/ocean[^.\n]{0,40}(will be in touch|will reach out|takes it from here)/i`.
  - **Status filters (`?status=`):** `all` (default), `active` (no `handoff_build_id`, no READY), `ready` (READY badge but not yet dispatched), `handed_off` (`handoff_build_id IS NOT NULL`); unknown values fall through to `all` defensively. Filter chips render as server-rendered links preserving query state.
  - **Stats grid is 4 cards** (was 3): Total trials, Ready to handoff, Handed off (emerald-400 badge color), Total turns; counts always reflect the unfiltered population so the operator sees the full picture independent of the active filter.
  - Dispatched rows show `fmtTs(handoff_at)` + `fmtRelative(handoff_at)` ("3h ago", "2d ago") under the DISPATCHED badge so Ocean can see how stale a handoff is at a glance.
  - `?status=keepers` (the "Paid keepers" chip) lists paid keepers instead: email, companion, turn count, note count, time of the last turn, opening words, subscription status and a link to the build, ordered by last turn, limit 200. The keeper query runs only for that filter, and `harborConversationSql(column, ownerId)` builds the conversation columns for both lists (`trial_id` or `keeper_id`, a `MemoryOwnerColumn`). Reading a keeper's turns is a SQL lookup by keeper id; the `dev_trial` links exist for trials only.
  - Each row deep-links into `/lighthouse/table?dev_trial=<uuid>` + `/lighthouse/table/recall?dev_trial=<uuid>`. `requireAdmin` gated.
  - When `CAS_HARBOR_ENABLED !== 'true'` the page renders a "harbor surface is dormant" affordance and skips the DB query entirely.
  - The Harbor entry in `_admin-nav.ejs` is gated on `res.locals.harborEnabled` (set globally in `app.ts` from `process.env.CAS_HARBOR_ENABLED === 'true'`), so the link only appears when the flag is on.
  - Tested by 14 cases in `web/tests/unit/routes.admin.test.ts` covering auth, dormant, full render, both READY paths, non-ready, empty state, SQL contract, 500 path, nav show/hide, 4-card stats grid + filter chips, `?status=ready`, `?status=handed_off` (with relative-time render), and unknown-status fallthrough.

- **CAS Harbor Make-it-public payment moment (added 2026-04-28).** The keeper journey is quality-triggered, not clock-triggered: conversation with Haven → spec is clear → build runs (free, in preview) → keeper walks around in the preview → "Make it public" CTA → Stripe Checkout (subscription mode) → webhook flips build to live + promotes trial-to-keeper + inserts Haven's blessing turn. Pricing: $39/month standard, $19/month sliding floor (`harborSubscriptionPrice` / `harborSlidingScalePrice` in `app.ts`). Site stays up on cancellation per harbor ethos.
  - **Routes (`src/routes/lighthouse.ts`):**
    - `GET /lighthouse/lamp/:buildId`, keeper-facing build status surface (state machine: queued/building | preview-pending | preview-changes_requested | preview-approved+CTA | live | failed). Renders `views/lighthouse/lamp.ejs`.
    - `GET /lighthouse/lamp/:buildId/make-public`, slider form ($19 to $39, stored in cents, sliding-scale attestation toggled on amount<default), the account's email address shown as text (an email field only when the build has no customer yet) and, for a trial, a checkbox confirming the address is the visitor's own, CSRF; renders `views/lighthouse/make-public.ejs`. Returns 409 + `views/lighthouse/changes-first.ejs` when `review_status='changes_requested'`. Redirects to /lamp when not preview+approved.
    - `POST /lighthouse/lamp/:buildId/make-public` (CSRF-gated), validates amount band + attestation + email;
      - settles the account the payment lands in before calling Stripe: the build's customer (or the keeper's own) decides the address, a different address in the form is refused (409 `email_mismatch`), a trial must tick the confirmation (400 `email_confirmation_required`), and a trial cookie pays only into the account for the address its conversation gave (409 `account_login_required`; the other account's address is not shown). `docs/THREAT_MODEL.md`, "The address a payment is tied to", has the rules;
      - passes the keeper's stored `keepers.stripe_customer_id` to Checkout if there is one, else that account's address as `customer_email`, so Stripe creates the customer when the payment is made (the earlier `createOrGetStripeCustomer`, which created a new Stripe customer on every POST without ever looking one up, was deleted; the route is rate limited per trial cookie and per address, ahead of CSRF, and a keeper who already has a subscription is redirected to `/builds/:id` instead of opening a second Checkout);
      - calls `createHarborSubscriptionCheckoutSession` (mode='subscription', recurring monthly, metadata `{kind:'harbor_make_public', build_id, trial_id|keeper_customer_id, monthly_amount_cents, sliding_scale_attestation}` mirrored into `subscription_data.metadata`);
      - 303 to Stripe URL.
    - `GET /lighthouse/lamp/:buildId/published`, Stripe success landing; settled state shows public URL + blessing pointer; almost-there state with `<meta http-equiv="refresh" content="3">` when webhook hasn't flipped yet.
    - `GET /lighthouse/lamp/:buildId/cancelled`, Stripe cancel landing.
    - `POST /lighthouse/lamp/:buildId/cancel-subscription` (CSRF-gated, keeper-only), calls `cancelHarborSubscriptionAtPeriodEnd(stripeSubId)` and mirrors `harbor_subscriptions.cancel_at_period_end=TRUE`. Trial owners get 403 (no subscription pre-payment). 303 redirect back to /lamp.
    - **Auth model (`resolveLampOwnership`):** A build is owned by an authed keeper session (`builds.customer_id === req.session.customerId`), by the browser that paid for it (`req.harborPaidKeeper`, which acts as the keeper for that one build, so it sees the subscription and can cancel it, and exists only if that browser's trial was promoted into the build's account: `trial_keepers.promoted_customer_id`), or by an active trial cookie linking via `trial_keepers.handoff_build_id`. Read routes accept all three; cancel-subscription is keeper-only (trial owners get 403).
      - The lamp, published and conversation pages link to each other ("Manage your website and subscription"), and the lamp page shows a "choose a password" link to `/forgot-password` to the paying browser that has no account session; completing a reset verifies the account.
  - **Webhook handlers (`src/routes/webhooks.ts`):** POST /webhooks/stripe dispatches `checkout.session.completed` on `metadata.kind`; `harbor_make_public` → `handleHarborMakePublic` (rest unchanged).
    - New events:
      - `customer.subscription.updated` (mirrors status + cancel_at_period_end + period dates into `harbor_subscriptions`; mirrors **status only** into `keepers.subscription_status`, storing Stripe's own word (`unpaid`, `paused`, `incomplete` and `incomplete_expired` are values of the column; only `active`, `trialing` and `past_due` count as subscribed, `PUBLISHING_SUBSCRIPTION_STATUSES` in `keeper_promotion.ts`). The `keepers` table does NOT carry `cancel_at_period_end` or period-date columns; those live on `harbor_subscriptions` and are read-joined when needed.),
      - `customer.subscription.deleted` (marks canceled; site stays up),
      - `invoice.payment_failed` (moves a keeper whose status is one of the publishing ones to `past_due`; it cannot lift `unpaid`, `incomplete` or `paused`; site stays up).
    - Account deletion asks Stripe to cancel at period end before its transaction opens and leaves a row in `harbor_subscription_tombstones` for 90 days, so that later events for those subscriptions are acknowledged instead of answered 500. All filter by `metadata.kind='harbor_make_public'` to avoid touching non-harbor subscriptions.
    - **`handleHarborMakePublic` pipeline** (the whole event runs in one transaction on one client: the `processed_webhooks` claim, the handler's work and COMMIT; a handler that throws rolls the claim back so Stripe's retry is processed from scratch):
      - validate metadata and `payment_status` → lock the build row `FOR UPDATE` → return if this session already took it live → decide whether it is publishable (`preview` + `review_status='approved'`) → resolve the customer (the build's own, or one created for the Checkout email) → `promoteTrialInTransaction` (trial path) or upsert the `keepers` row (keeper path) → guarded `UPDATE builds` preview→live, recording `stripe_session_id` → `recordSubscription` and `insertBlessingTurn` (WHERE NOT EXISTS) → COMMIT → fire-and-forget `sendHarborMadePublicEmail` after the commit.
    - Money that arrives for a build that cannot go live (a reviewer asked for changes while the payer was at Checkout, or another session already paid for it) is recorded in `harbor_subscriptions` and logged as an error; nothing publishes the site or refunds the charge.
    - Subscription events are matched to the keeper by subscription id, a `canceled` status is terminal, an event for a subscription with no local row is refused with a 500 for 72 hours and then dropped, and `event.created` ordering is applied through `harbor_subscriptions.last_event_created`.
    - The `POST /lighthouse/lamp/:buildId/make-public` success URL carries no Checkout session id.
  - **Service helpers:**

Constants: `HARBOR_SUBSCRIPTION_AMOUNT_MIN_CENTS=1900`, `MAX=3900`, `DEFAULT=3900`.

- `src/routes/admin.ts`: faithful-copy operator surfaces (2026-05-09). Three new admin-gated routes wrap the `services/site_copy_crawl.ts` crawler so Ocean can capture an existing customer site before clicking Dispatch.
  - (1) `POST /admin/harbor/:trial_id/crawl-source-site` (requireAdmin + validateCsrfToken + 503 on flag-off + 400 on bad UUID/missing-source-url/non-http(s)/+ 404 on trial-not-found + 409 when trial.released_at set + 502 on zero-page crawl)
    - calls `crawlSite(source_url)` with the SSRF guard active (public addresses only, ports 80 and 443 only, at most 3 same-site redirects, bounded header and decoded-body size, every request abandoned 15 seconds after it starts, and the HTML parsed by linear scanners (`services/site_copy_parse.ts`) in a worker thread that is killed on a deadline, never on the web process's event loop; see the header of `services/site_copy_crawl.ts`)

  - (3) `POST /admin/harbor/:trial_id/clear-source` (requireAdmin + validateCsrfToken) resets `harbor_meta_overrides` to NULL when the operator wants to drop a bad crawl.

- `src/routes/admin.ts`: `POST /admin/harbor/:trial_id/dispatch` (added 2026-04-28). Ocean's manual handoff trigger that pre-Stripe dispatches a v2 build for any trial keeper without first promoting them through Stripe.
  - Pipeline:
    - `requireAdmin` + `validateCsrfToken` + UUID-shape gate;
    - SELECT `trial_keepers` (404 if missing);
    - idempotency check on `handoff_build_id` (returns existing buildId without re-extracting);
    - 409 + `trial_already_promoted` when `released_at IS NOT NULL` (the trial→keeper migration already moved memory/turns to keeper-keyed rows so trial-keyed extraction would silently produce nothing);
    - resolve customer via `email_captured` falling back to `ADMIN_EMAIL`;
    - **race-safe customer create** via `INSERT ... ON CONFLICT (email) DO NOTHING RETURNING id` + re-SELECT (defends against UNIQUE(email) violation when a concurrent /signup or another dispatch creates the customer first);
    - `extractSpecFromConversation({trialId})` for the Opus call (~$0.18);
    - `translateExtractedSpecToV1`;
    - **tier coercion** to `['build','grow','scale']` with a warning if Opus hallucinated something else;
    - **transactional INSERT builds + UPDATE trial_keepers** wrapped in BEGIN/COMMIT with ROLLBACK + connection release on failure (defends against orphan builds when a process kill mid-handler would otherwise queue a build whose `handoff_build_id` never gets stamped, letting a second click create a second orphan);

- **Translator design (load-bearing, no AI inside):** `services/harbor_to_compose.ts` is a pure-TS deterministic mapper. Same input → byte-identical output.
  - Maps Opus's nested `pages[].sections[]` (variable shapes Opus invents per turn) into v1-shape (`{spec_version, app_name, description, tier, data_models, user_roles, pages, _seed_settings, _harbor_meta}`).
  - Section types pass through `SECTION_TYPE_ALIASES` (~50 known aliases for hero/cta/about/offerings/services/testimonials/gallery/newsletter/faq/visit/contact/booking/intake_form/payment/team/areas/upcoming_events/etc.).
  - **Lookup keys are normalized via `normalizeSectionType(rawType)` → lowercase + dashes → underscores** (added 2026-04-28 after an early build crashed because Opus emitted `quick-nav`, `photo-gallery`, `about-bio`, etc. as dashed strings and every section dropped against the underscore-keyed map; root cause was 8/8 sections silently dropped → barren spec → compose lint passed but app crashed post-deploy).
  - New aliases for `quick_nav`→cta, `featured_events`/`event_calendar`→upcoming_events, `photo_gallery`→gallery, `about_bio`→about.
  - Unknown types still drop with warning, but `SECTION_TYPE_EXPLAINED_DROPS` now distinguishes "recognized but no widget yet" (e.g. `event_detail` page-level concept; `video_gallery` no compose widget) from generic unknown.
  - **Barren-spec guard:** `extractFromPagesAndCopy` tracks `sectionsSeen` vs `sectionsHandled`; emits `BARREN_SPEC` warning when sections were emitted but 0 handled, `THIN_SPEC` when >4 seen and <25% handled. Admin/dispatch can refuse-or-flag before queueing on these warnings (currently advisory-only; future: refuse-to-dispatch).
  - Future-cast hooks: `booking` sections auto-emit a `BookingIntent` data_model + capture intents in `_harbor_meta.booking_intents` so admin can wire calendar later.
  - `intake_form` similarly emits a warning + `IntakeSubmission` data_model placeholder.
  - `payment` sections drop with warning (CAS Harbor doesn't process customer payments).
  - A custom page that names no `form_target` gets one from its slug (`/book` → BookingIntent / Booking / Session / Appointment by precedence; `/apply` → Application / Inquiry / ContactInquiry; `/intake` → IntakeSubmission / IntakeResponse / Intake), but never a model visitors can read: a candidate that is shown to visitors is passed over for the next private one, and when none is left the page gets no form, with a warning.
  - Every contradiction the compose engine refuses is resolved toward less exposure, with a warning (`dropPagesTheEngineWouldRefuse`, `holdPublicFormRowsBack`, `dropCopiedPagesAtProtectedPaths`, `modelSlugProblem`, `normalizeAllowedRoles`). An explicit public form into a model visitors can read gets a boolean `published` field, or loses its form when that is impossible; `ContactInquiry` and any `*Subscriber*` model lose `public_listing_path`; a protected page left with no usable role becomes `['admin']`; a protected page the engine would refuse is dropped.
  - `compose/tests/test_translator_output_builds.py` compiles the real TypeScript translator in node and runs its output through the engine (`translate_v1_spec`, `validate_spec`, `resolve_spec`, `compose_files`); it skips without node or `web/node_modules/typescript`.
  - 49 unit tests cover all 9 archetypes, all section aliases, edge cases (empty / missing / malformed / oversized / duplicate names / non-array types), determinism, and the healer end-to-end fixture.
  - **Build route at POST `/lighthouse/build` calls extractSpecFromConversation → translateExtractedSpecToV1 → INSERT into builds.spec; the worker auto-detects v1-shape + handles archetype + palette + font picking deterministically.**

- `src/services/keeper_promotion.ts`: `promoteTrialInTransaction(client, opts)` runs the promotion steps on a client already inside a transaction (the Stripe `checkout.session.completed` handler uses it, so the event claim, the promotion and the build going live commit together); `promoteTrialToKeeper(opts)` opens its own transaction around the same steps (the development payment bypass uses it).

**New modules (2026-04-27, Harbor Phase 1; lite-mode memory):**
- `web/src/companion/memory_capture.ts`: Persistent memory capture with two modes:
  - **Full** (OPENAI_API_KEY present) uses OpenAI text-embedding-3-small + semantic dedupe (cosine > 0.93) + JS-side cosine ranking at retrieval + recency boost.
  - **Lite** (OPENAI_API_KEY unset) uses normalized-content dedupe (case-insensitive trim, whitespace collapse) + recency-only retrieval. Real memory rows with `embedding=NULL` are persisted in lite mode.
  - Rationale: the operator can observe Haven's memory layer in dogfood without committing to an embedding provider yet (OpenAI / Voyage AI / self-hosted / skip-entirely remain open). No pgvector required locally.
  - `normalizeContent()` helper exposed; 5 new unit tests (`test_normalize_content_lowercase`, `test_normalize_content_trim_whitespace`, `test_equivalent_canonical_statements_dedupe`, `test_semantically_distinct_items_remain_distinct`).

Returns **HTML by default** (rendered via `web/views/lighthouse/recall.ejs`; warm-paper register with small rotated cards aesthetic from brand vision). Pass `?format=json` for raw rows. When `OPENAI_API_KEY` is unset, page displays "lite mode" affordance explaining recency-only retrieval. `schema.sql` query unchanged; response shape differs from prior json-only endpoint.
