# Worker env vars + v2 engine behavior (migrated from CLAUDE.md, 2026-07-03)

> Historical document from July 2026; the system was wound down in July 2026.

Full behavioral narrative for worker environment variables and the v2 compose engine's
worker integration (fix-loop skips, health checks, recovery probes, translator contract).
CLAUDE.md carries the condensed version; this is the detail archive. Trust the code over
this file. The current environment-variable list, grouped by component, is in the Environment variables section of `CLAUDE.md`; the web app's variables are in `web/.env.example`.

## Worker environment variables

- **Worker env vars:**
  - `DATABASE_URL`, `RESEND_API_KEY`, `GENERATED_APP_RESEND_API_KEY` (optional; the only mail key `deploy()` gives a generated app, as that app's `RESEND_API_KEY`; the platform key is never copied to an app) with `GENERATED_APP_RESEND_FROM_DOMAIN` (its sending domain, handed to the app as `RESEND_FROM_DOMAIN`),
  - `ADMIN_EMAIL`, `RAILWAY_API_TOKEN`, `MAX_CONCURRENT_BUILDS` (default 1), `DAILY_API_SPEND_CAP` (default 50 USD; 0 to disable),
  - `MONITOR_INTERVAL`, `OPS_DRY_RUN`, `OPS_SCAN_INTERVAL`, `OPS_CIRCUIT_BREAKER_LIMIT`, `OPS_MAX_CLAUDE_CALLS_PER_DAY` (caps ops fixer runs per day; the playbooks make no model calls),
  - `SENTRY_DSN`, `SEND_BUILD_PROGRESS_EMAILS` (default false), `DISABLE_BATCH_API`, `BLOCKING_DESIGN_REVIEW` (default off), `MAX_DESIGN_FIXES` (default 3),
  - `ANTHROPIC_ADMIN_KEY`, `USE_ADVISOR_FIX`/`_DEPLOY_FIX`/`_QA_FIX`/`_DESIGN_FIX` (Advisor Tool, all default disabled), `OPS_API_KEY` (web only, bearer for `/ops/api/*`),
  - `WIDGETS_ENABLED` (tri-state: unset = universal (every spec emits widget admin surfaces, since 2026-04-20), `"true"` = same as unset / explicit on, `"false"` = emergency kill switch that restores the pre-universalization legacy path; any other value raises ValueError; see `docs/internals/WIDGETS_AND_CONTRACTS.md`),
  - `CAS_BUILD_ENGINE` (code default `"v2"` as of 2026-04-27 = static-compose from `compose/build.py`, no AI in build path; `"v1"` = legacy Claude-per-build pipeline, opt-in only for repro / forensics; unknown values raise ValueError on the build-stage gate, fall back to `"v2"` on dispatch attribution, see the `compose/` directory; v1 source preserved in `cli/` with deprecation banner in `cli/__init__.py`).
- **The prod worker was set to `v2` as of 2026-04-22; all new customer builds go through Option A compose.**

## Stage behavior and health checks

- When `v2`:
  - validate stage auto-translates v1-shape intake specs (with `spec_version`/`user_roles`/`data_models` but no `archetype`) via `compose.intake.translate_v1_spec()` then validates against the v2 schema, preserving tier + admin_email + app_name from the original v1 spec;
  - build stage dispatches to `compose.build.build_app(spec_path, output_dir, tier=tier)` (tier recorded in compose-manifest.txt for audit, output does NOT vary by tier today; all tiers get the same archetype + widget composition, with tier-gated features like revision limits / Stripe / review SLA handled downstream by reading `builds.tier` from the DB);
  - testing-stage runs `_lint_v2_build_output(build_dir)` (fast, deterministic, required-files present, manifest valid, seed rows match spec counts, no raw `{Word}` italic-accent leaks, CSS carries required utility classes, no banned font/length tokens, every page view composed from widgets);
  - design-review + QA-fix + UI-test + deploy_fix loops are skipped (v2 is deterministic, no Claude in the loop);
  - deploy stage still runs (or `LOCAL_BUILD_GUARD1` marks preview when `RAILWAY_API_TOKEN` unset), but if the deployed v2 artifact crashes post-deploy the worker fail-fast with persisted crash logs (`reason="v2-deploy-crash-no-fix-loop"`) rather than running v1 `deploy_fix.py`, applying v1 Claude patches to v2 artifacts corrupts them (v2 emits `views/layout-public.ejs`, not v1's `views/layout.ejs`; `deploy_fix` also rewrites server.js / routers in ways that drop v2 public routes, observed 2026-04-22 on a sound-bath scheduler test build where `/sessions`, `/book` 404'd after attempt 1).
    - Correct remediation: fix the compose engine; see `TestV2DeployFixSkip` in `tests/test_worker_pg.py` for the regression guard.
- The v2 gate's RuntimeError carries a `[v2-deterministic]` tag which `_process_job`'s retry-decision path recognizes to skip the retry loop entirely (retrying a deterministic error on the same commit just creates another orphan Railway project, v2 is same-input/same-output by construction).
- `verify_health` in `cli/deploy.py` (shared v1 + v2) uses default timeout=120s (was 60s) to cover Railway edge propagation (30-90s) plus container boot; when no HTTP response arrives within the window the function returns `"infra"` (propagation) instead of `"failed"` (code bug), genuine crashes produce 502/503 from Railway's edge, so silence is specifically the "URL not yet routable" signal. Both timeouts are covered by `TestVerifyHealth` in `tests/test_deploy_health.py`.
- `deploy()` short-circuits with `health_check="failed"` when Railway's `wait_for_deployment` raises on a transient CRASHED status (`cli/deploy.py`); for v2, the worker runs a **recovery probe** that re-runs `verify_health(timeout=180s)` before firing the fail-fast gate, and promotes `health` back to `"ok"` on explicit healthy response (otherwise falls through to the original failed/infra path).
  - This catches Railway's frequent CRASHED→SUCCESS transition during post-migration container restart (observed 2026-04-22 on a wellness-studio test build where every route returned 200 minutes after deploy_result came back failed). See `TestV2DeployFixSkip.test_source_v2_has_recovery_probe_before_fail_fast`.
- `verify_routes` is also skipped for v2 (the intake translator drops original-spec pages that don't fit the chosen archetype, e.g. `/book` dropped when archetype=fitness-studio emits `/schedule` + `/classes`, and running verify_routes against the untranslated spec produces false 404s; v2 lint's "every page view composed from widgets" check already validates route emission deterministically upstream; see `TestV2DeployFixSkip.test_source_v2_skips_verify_routes`).
- `verify_auth` and `verify_data` are **also skipped on v2** (Group 0 cleanup 2026-04-22): verify_auth posts a default test password against v2 apps that seed admin with `password=NULL` + `password_set=TRUE`, producing a non-blocking warning that is pure log noise + ~20s latency; verify_data derives CRUD paths from `spec.data_models` (e.g. `Class → /class`) which v2's translator remaps to archetype names (e.g. `class_types`) so those paths 404 and produce false "missing data" warnings.
  - Guards: `TestV2DeployFixSkip.test_source_v2_skips_verify_auth` + `.test_source_v2_skips_verify_data`.
- **`wait_for_deployment` tolerates 1 transient CRASHED before raising** (2026-04-22): Railway briefly reports CRASHED during post-migration container restart before stabilizing to SUCCESS; prior impl raised on first CRASHED snapshot, short-circuiting `deploy()` with `health_check="failed"` on otherwise-healthy apps.
  - New impl requires 2 consecutive CRASHED/FAILED/REMOVED polls (with any intermediate non-terminal status resetting the counter) - `_MAX_CONSECUTIVE_TRANSIENT_FAILURES = 2` in `cli/deploy.py`.
  - This upstream fix shortens the need for the v2 recovery probe; both layers remain (belt-and-suspenders).
  - Guards: `TestWaitForDeploymentCrashedTransient` in `tests/test_deploy_health.py`.

## Static assets and caching

- **Static asset cache-busting + SVG ampersand escaping** (2026-04-25): Two image-rendering bugs fixed.
  - (1) **Cache collision across local-preview rebuilds:** localhost:4600 is shared across local-preview generated apps; browsers cache by URL and serve stale assets even with `Cache-Control: max-age=0`.
    - Fix: `_cache_bust_static_assets()` walks the file list at end of `compose_files()`, sha256-hashes each cache-sensitive asset (first 8 chars), appends as query param `?v=<hash>`, rewrites every `href=` / `src=` / SQL reference in `.ejs` / `.js` / `.html` / `.sql` files. Same content = same URL = correct caching; different content = different URL = fresh fetch. Deterministic across rebuilds.
    - Hashed assets: `/style.css`, `/js/cas-{form-validate,reveal,upload-zone}.js`, `/logo.svg`, `/favicon.{svg,ico}`, `/manifest.json`; seed.sql nav_logo_url also rewritten.
  - (2) **Invalid logo SVG from unescaped ampersand:** a "Wren & Rye" logo produced `<text>W&</text>`, unescaped `&` made XML invalid, browsers render broken-image placeholder.
    - Cause: initials extractor split on whitespace, took first letter of each of first two words; ["Wren", "&", "Rye"] → "W&".
    - Fix in `emit_public_assets()`: filter words to alnum start (skips `&`, `+`, `-`, `/`, etc.), run `xml.sax.saxutils.escape()` as backstop. "Wren & Rye" now produces "WR".
    - Tests: 4 new asserts in `compose/tests/test_build_pipeline.py` (content-hash detection, determinism across rebuilds, punctuation skipping + XML escape, other punctuation brands).
    - Verified end-to-end locally: chrome-devtools screenshot shows espresso WR monogram in nav, all responsive utilities applied, no dual-render. 341 pytest pass.
- **Above-the-fold hero lazy-loading bug + HTML Cache-Control headers + settings middleware always-set contract** (2026-04-26): Three browser-visible bugs fixed in v2 compose.
  - (1) **Hero images with `loading="lazy"` fail to render:** Above-the-fold hero images with lazy-loading never fire when CSS hasn't loaded yet (zero-height container). Changed to `loading="eager"` + `fetchpriority="high"` in `compose/widgets/hero/{centered,split-image}.ejs`.
  - (2) **Generated app HTML pages are cached despite rebuild:** New assets get new hash URLs (`style.css?v=<hash>`), but the HTML page itself has no cache-buster. On local rebuild, browser serves stale HTML pointing at old (now-missing) asset hashes, collapsing the layout.
    - Fix: `Cache-Control: no-cache, no-store, must-revalidate` middleware added **after** `express.static()` in generated server.js, so static assets with hash URLs are still independently cacheable.
    - Meta tags (`http-equiv="Cache-Control"` + `Pragma` + `Expires` set to 0) added as belt-and-suspenders to layout templates for defense-in-depth against proxy/firewall headers stripping. Applied to `layout-public.ejs` and extended to `layout-admin.ejs` (2026-04-26).
  - (3) **Settings middleware throws "nav_items is not defined" on first boot:** Catch block called `next()` without setting nav locals when DB isn't ready. Fix: extract nav arrays as module-level consts (`_NAV_ITEMS`, `_ADMIN_NAV_ITEMS`) and assign unconditionally after the try/catch.
  - 3 new tests: `test_hero_images_not_lazy_loaded`, `test_server_js_sets_no_cache_for_html_responses`, `test_settings_middleware_always_sets_nav_items`. **325 pytest pass.**

## Custom pages, navigation and `/set-password`: what the engine emits now

The header of `compose/build.py` is the authority; this is the summary.

- **Reserved names.** A page id or model slug may not be a name the engine uses itself (`_RESERVED_PAGE_IDS`: the built-in views, routers, routes and static directories, for example `login`, `privacy`, `set-password`, `error-404`, `layout-public`). The spec gate refuses it (`_page_id_reservation`), and `compose/intake.py` leaves a copied page with a reserved id out of the translated spec with a warning. A test compares the list with what a build actually emits, so a built-in view or route added later cannot be forgotten. Reserved custom page PATHS are dropped, not refused, because v1 specs routinely list `/login` and `/admin`.
- **Custom pages are classified once.** `_classify_custom_pages` decides which of the customer's `custom_pages` are emitted and records why each dropped one was dropped (eleven reasons: path not plain, parametric, already owned by an archetype page, a built-in or `/admin` route, a public page under `/admin`, a model's public listing, the mount of a private submission model, a spot below a model's mount or a listing page that their own routes answer first, or a duplicate of an earlier page or view file; the rule behind all of them is that a page is kept only if its own route is the first to answer its path); `_custom_page_warnings` turns that into `translation-warnings.txt`.
  - A form page at a private model's own path (a form at `/rsvps` that stores Rsvp rows) is kept: the model's router hands its GET and POST on to it.
  - Routes, views, the sitemap and the navigation are all built from the survivors, so a dropped page leaves no route, view or link behind, and the default navigation is built from `_sitemap_public_paths`.
  - A `nav_items` override keeps only links that stay on the site (`_NAV_HREF_RE`). A path that names another origin is refused by the gate (`_is_offsite_reference`).
- **One guard list per page.** Every route of an `auth_required` custom page (GET and the POST of a form page alike) carries the same middleware, built by `_custom_page_guards`; a test asserts that, for every path in every emitted router, all verbs carry the same guards.
  - A custom page never lists a model's rows. A page whose path is a model's name is an ordinary page and the model stays admin-only (`page_named_like_model` in the build report); a model is listed only where the spec sets `public_listing_path` on it (`_public_model_mount`), and that path must pass the same path check as any other (a model `Admin` cannot be mounted at `/admin`).
  - A page that is `auth_required` and whose path something else in the build would answer without a login (a page of the site, a model's public listing or public detail pages, a built-in public route such as `/privacy`, an earlier public custom page with the same path, the same path in another letter case) makes `resolve_spec` refuse the build (`_auth_required_page_errors`): a build is deployed to a public address as soon as it finishes, so a warning would be read after the page is already public, and the spec contradicts itself.
  - A protected page that is not emitted for another reason and whose path nothing public answers is recorded as `auth_required_page_not_emitted`; a protected page on a path that already asks for a login stays silent.
  - The check covers the routes the engine emits, not `slug_aliases` rows added later.
- **What a build publishes.** A model's rows are served without a login in exactly two cases: the spec sets `public_listing_path` on the model, or a page layout of the archetype reads the model's table (`_public_row_sources` is the one definition; `resolve_spec` no longer sets `public_listing_path` itself).
  - Absent, null and the empty string all mean "not listed" (`_public_model_mount` tests truthiness).
  - The tables the archetypes' layouts read are a fixed list, enumerated per archetype in `CURATED_PUBLIC_TABLES` in `compose/tests/test_spec_hardening.py`; it never includes contact inquiries or newsletter subscribers.
  - A spec model that redefines the archetype's model of a name a layout reads is what the archetype's page shows; the build report says so (`spec_model_shown_by_archetype_page`) and nothing refuses it.
  - Related rows on a public detail page are read only for a child model that is public itself (`_related_child_info`). The `published` column is recognized in any letter case (`_model_column`), and only a BOOLEAN one (a type written `boolean` or `bool`, `_sql_type_kind`) is the publication flag (`_publication_column`).
  - Publication warnings are the first `warning: ` lines of `compose-manifest.txt` and `translation-warnings.txt` (`_ENGINE_WARNING_PRIORITY`: `spec_model_shown_by_archetype_page`, `auth_required_page_not_emitted`, `page_named_like_model`, then the rest in the order they were recorded); they do not block the build.
  - "Published" has one definition, `_published_condition` (the flag is TRUE): a row whose flag has no value is not published, and the resource router, the composed lists and details and the related-rows query all apply it. A seed row that does not say is published; a SERIAL column takes its DEFAULT.
  - A visitor sorts a public list only by a column the list view prints (`_public_sort_columns` over `_PUBLIC_LIST_COLUMNS` by `_public_listing_kind`), plus the key and, where the view prints a date, the creation time; any other `?sort=` gets the default order. The admin sorts by every column that has an ordering (`_admin_sort_columns`; json has none).
- **A visitor's row is not public until the owner publishes it.** Every unauthenticated INSERT into a model table (custom form pages, `POST /contact`, `POST /newsletter-signup`) stores `published = FALSE` when the model has a boolean `published` column (`_public_insert_sql`), and the resource router, the composed listings and detail pages and the related-rows lookup all leave such a row out. `resolve_spec` refuses a spec whose public form stores into a model that is shown to visitors and has no boolean `published` column (`_public_form_errors`). A visitor cannot tick `published` or another system column on a form, in any letter case.
  - Only a BOOLEAN column named `published` is the flag (`_publication_column`). A column of that name with another type (the date a book came out) is an ordinary column: comparing it with TRUE would make every public page of the model answer 500.
  - A custom form page that is not behind a login names the columns a visitor may fill in (`allowed_fields`), or the spec is refused (`_public_form_field_errors`); the form, the POST handler and the INSERT use that list and no other column. A form page behind a login keeps every column by default, and the contact form has its own list (`_contact_form_fields`), unchanged.
- **Public forms validate.** `processPublicForm` in the emitted `middleware/fields.js` checks each submitted value before the INSERT: strings only, a length limit (the smallest of the field type's maximum, the width of a VARCHAR column and 10,000 characters), the field type's pattern and what the column can hold (range, date, time, option). A rejected submission stores nothing; the form comes back with one message per field and the typed values (cut to the limit). Custom forms infer the field type from the field name as the admin forms do (`email`, `phone`, `state`).
- **The newsletter signup stores an address once.** One `INSERT ... SELECT ... WHERE NOT EXISTS` statement. The table has no unique constraint, so two simultaneous signups with one address can both be stored.
- **Emitted CSS and JavaScript parse.** `compose/tests/test_emitted_css_js_syntax.py` builds a site for every fixture, for every archetype with every template family (and with the readability bump), and for every layout variant, checks braces and parses the CSS with PostCSS, runs `node --check` on every emitted `.js` file of every shipped fixture, and compiles inline `<script>` blocks.
- **Roles.** A page lists the roles that may open it (`allowed_roles`): one role gets `requireRole('x')`, several get `requireAnyRole([...])` (any one listed role passes), and `user` in the list means any signed-in account.
  - A page that lists only `["member"]` does not admit the admin.
  - The role is copied into the session at sign-in from `users.role`, so changing or deleting a `users` row does not affect sessions already open.
  - The site has no sign-up and no user management: an account other than the seeded admin exists only if the operator inserts a row into `users`; such an account lands on `/` after sign-in (the admin lands on `/admin`), and the admin sub-navigation is shown to the admin only.
  - The gate refuses role entries that are not strings, are blank or are over 50 characters. Role names other than `admin` and `user` are compared exactly, so `Editor` does not match a stored `editor`.
  - A page that lists `allowed_roles` without `auth_required` is a protected page: `resolve_spec` sets `auth_required` on it and records `allowed_roles_imply_login` (`_roles_imply_login`). `translate_v1_spec` does the same, or leaves out a roles-only page that sits at an archetype's default page path (`allowed_roles_page_dropped`).
- **Fields come from the model, not from the page copy.** The contact form's fields, the `POST /contact` handler and the table it writes to come from one field list (`_contact_form_fields`), so page copy cannot add or drop a column; a public listing is ordered by a column the model has (`_listing_order_by`: `published_at` if present, else the first DATE or TIMESTAMP column, else `id`), whatever the model is called. `POST /contact` and `POST /newsletter-signup` are emitted only when a page shows the form; both forms carry the honeypot field `website_url_hp`, and a submission that fills it gets the normal answer and stores nothing. Identifiers go through `_sql_ident`, the emit-side restatement of the gate's field-name rule.
- **The access log carries no query strings.** The emitted `middleware/logging.js` writes the request line and referrer without their query strings for every route (`pathOnly`), the CSRF-mismatch line logs the path only, and a request body the parsers reject is logged by error type and answered with the parser's 4xx. The one deliberate log of a login token is `POST /request-magic-link` when `RESEND_API_KEY` is unset. GET and HEAD on `/magic` never consume a token; `POST /magic/consume` does, and it is what the worker's login probe calls. HEAD and GET `/magic` share a limit of 60 per 15 minutes per address (`magicLinkOpenLimiter`). The emailed login link and a form notification's "View in admin" link are built on `linkOrigin()` (the `SITE_ORIGIN` that `deploy()` sets, else the stored `site_url`), never on the request's `Host`; with neither, the link is not emailed.
- **A spec's shape and size are the validator's job.** A spec is JSON written by a model, so any value can stand where another type was meant. `validate_spec` runs the gate and then `resolve_spec` on a copy (`_resolution_errors`), so a spec it accepts is one `resolve_spec` accepts. `build_app` bounds the whole decoded document first, unknown keys included (`_document_size_errors`), and `_spec_size_errors` bounds the containers the same way (nesting 32, 200,000 values, 100,000 characters in a string or key, 4,000,000 in all, 300 custom pages, 100 models, 100 fields per model, 100 roles; a spec file over 32 MiB is refused unread). Each key an emitter reads has one accepted type (`_kind_problem`, the `*_KEY_KINDS` tables), and the allowlist patterns are compiled with `re.ASCII`.
  - Page data reaches a view only through the parameters its widget declares in `compose/data/widget-registry.json` (`_spec_widget_data`): a number where text is declared becomes its text, an undeclared key is left out without a warning, null and an empty string mean absent, and anything else is refused (`_page_data_errors`, reported by `validate_spec` too).
  - `translate_v1_spec` refuses a v1 spec with wrong-typed values (`_v1_shape_errors`, the same size bounds) with "Spec validation failed" instead of raising `AttributeError` or `TypeError`.
- **The build report keeps the engine's words apart from the spec's.** This is the one statement of the manifest's shape; the other documents point here.
  - `BuildSpec.engine_warnings` is written only by `_engine_warning` and becomes `warning: <reason>: <detail>` lines, first, with the publication warnings ahead of the rest; a line is at most 991 characters. What the spec carried under `_translation_warnings` becomes `spec-warning: ...` lines after them, at most 40, each at most 396 characters.
  - Every line is one physical line of printable text. `_report_text` turns each run of control, format, line-separator and lone-surrogate characters into one space and cuts a long value (a reason at 80 characters, a detail at 300 for the spec and 900 for the engine), so a spec cannot add, remove or imitate an engine line, or start a header line.
  - Header lines, once each and in this order: `archetype`, `palette`, `font_pair`, `tier` (at most 40 characters), `files`, `sha256`, `translation_warnings_count` (the number of warning lines written), `engine_warnings_count`, `spec_warnings_count`, `spec_warnings_omitted` and `external_url_lint` (`skipped`, `ran` or `failed`). Then the engine lines, then the spec lines, and nothing after them. The number of engine lines has no constant of its own; it follows the size limits on the spec.
  - `translation-warnings.txt`, written only when there is at least one warning line, holds `# ` comment lines, a blank line and the same lines in the same order. What the worker reads and copies is in `docs/internals/worker.md`, "Manifest warnings"; what the review page shows is in `docs/THREAT_MODEL.md`.
- **`/health` answers ok only when the home page rendered.** The emitted `services/health.js` requests `/` once over loopback when the listener comes up (3 seconds, body discarded). `/health` is 200 `ok` when the database answers and that check passed (a status from 200 to 499), 503 `db_error` when the database does not answer and 503 `home_page_error` otherwise. A pass is remembered for the life of the process and a failure is tried again by a later probe at most every 10 seconds. `verify_health` reads `home_page_error` as `"failed"`, not `"infra"`.
- **Columns the engine reads with a fixed meaning.** `id` must be an integer or serial type (a declared `id` is dropped, because the engine adds the key), `created_at` a date or timestamp (the dashboard compares it with `NOW() - INTERVAL '7 days'`), `published_at` any type but json (public listings are ordered by it), the link to a parent model (`belongs_to`) a whole-number column that is not one the engine adds, and the newsletter signup's email column a text type (`_ENGINE_COLUMN_KINDS`, `_engine_column_type_errors`, `_engine_column_errors`, `_without_engine_id`).
  - Tables are created parent first (`_models_in_creation_order`: schema, seed, the dashboard's clearing and the regen script); models that belong to each other in a ring are refused, a self-reference is allowed. A detail lookup by slug compares `slug::text = $1 OR id::text = $1`, whatever type the slug has.
  - A new column that the engine reads with a fixed meaning belongs in `_ENGINE_COLUMN_KINDS` and in `ENGINE_COLUMN_POSITIONS` of `compose/tests/test_spec_shape_matrix.py`.
- **Seed values and column defaults are put to Postgres.** `_stored_value_problem` and `_default_problem` say whether a column of that type takes a value (a test asks Postgres about every case). A seed row with a value its column cannot store is left out and reported as `seed_value_unfit` (when every row is out, the model's seed is skipped with a comment); a default the column rejects is left off and reported as `column_default_ignored`. The engine also refuses a few things Postgres takes: dates and times in any form but ISO, a date in front of a time, arrays of more than one dimension, and a timestamp longer than 64 characters (`_STORED_TIMESTAMP_MAX_CHARS`, `_stored_value_problem`).
- **A stock photo of a specific person or place is never used.** `_personal_stock_photo_errors` refuses a spec that names a file under `/images/stock/` that shows one (every string of the spec, iteratively; the same path after a host name is another site's address and not a reference, `_STOCK_PHOTO_REF_RE`). The copy step also skips such a file that got past the gate, with the warning `stock_photo_not_copied`; `stock_photos.is_personal_photo_name` reads the manifest entry of the file, else its name.
- **Two files never land on one path.** `_write_build_files` raises before writing anything when two emitted files share a path (compared case-insensitively) or one uses a name `build_app` writes itself (`compose-manifest.txt`, `translation-warnings.txt`).
- **`/set-password`.** Replacing an existing password needs the current one, except for an account that has no password yet or a session started by a login link less than 15 minutes ago (`passwordChangeRule`; `loginLinkAt` is stamped only by the single-use `/magic/consume`, and is deleted when the password is saved). The route is behind `authLimiter` (10 attempts per 15 minutes per address) and the view shows the current-password field when it is required. An account with no password can still set one from any signed-in session. A saved password ends the account's other sessions (`endOtherSessions`), here and in `/admin/change-password`.
- **The translator's output builds.** `compose/tests/test_translator_output_builds.py` compiles `web/src/services/harbor_to_compose.ts` in node with `web/node_modules/typescript`, translates extracted specs, then does what the worker does (`admin_email`, `translate_v1_spec`, `validate_spec`, `resolve_spec`, `compose_files`; `build_app` to disk for the review cases). It skips without node or that package.
- **Generated-site tests.** Five modules in `compose/tests` boot a generated site against a throwaway database: `test_compose_end_to_end.py` (which defines `boot_generated_app`), `test_smoke_suite.py` (which reuses its fixtures), `test_generated_app_guards_e2e.py`, `test_generated_site_publication_e2e.py` (what a visitor can read and store: a page named like a model, unpublished visitor rows, public form validation, the newsletter signup) and `test_generated_site_security_e2e.py` (token logging, role guards, CSRF on public and admin writes, login link single use and expiry, cookie flags, session fixation, drafts, uploads, the per-address login limit and the CSP nonce); they skip unless `builds/sample-healer/node_modules` exists (`tests/README.md` has the commands).
  - The home-page check behind `/health` has its own file, `test_site_health.py`, which runs the emitted module under node, and a booted-site case in `test_compose_end_to_end.py`. The wrong-type matrix, `test_spec_shape_matrix.py`, needs node and `web/node_modules`; two of its tests, like `test_engine_columns.py` and `test_stored_values.py`, also run built sites' SQL on a real PostgreSQL (`_scratch_pg.py`) and skip without a local server.
  - `CAS_COMPOSE_TEST_DATABASE` names one database for every booted site and for those SQL tests to use instead of creating one each: each booted site gets a schema of its own in it, and the column tests replace its `public` schema, so name one that holds nothing else.
- **External-link lint.** `compose/lint_external_urls.py` (`CAS_LINT_EXTERNAL_URLS`: `warn` by default, `skip`, `error`) sends the worker a HEAD request for each external URL in the spec, so every URL is treated as hostile input: only http and https on the default ports with no credentials (`_url_precheck`), connections only to public unicast addresses (`_guarded_create_connection`), environment proxies ignored, and no response body read, including the body of a redirect. Every redirect target passes the same precheck as the first URL. The wall-time budget is enforced on every connect and every read of response headers, and a check cut short counts as unchecked, not dead. The budget does not cover the DNS lookup, and a TLS handshake or request send already in flight runs to its own timeout.
  - A destination the guard refuses is reported as "refused: resolves to a non-public address" (`BLOCKED_DESTINATION_TEXT`): the warning names the URL the spec supplied and never the address it resolved to. The lint's findings are engine warnings (`warning: ` lines).
  - The walk over the spec is iterative (a deep key cannot exhaust the stack). The manifest's `external_url_lint:` line says `skipped` when `lint_mode()` is `skip`, `ran` when it ran (no warning line then means it found nothing) and `failed` when the lint itself raised, so no URL was judged; the warning `external_url_lint_error` says why.
