# Monitor, ops, scripts, executor

> Historical document from April 2026; the system was wound down in July 2026.

> **Scope:** modules outside the build pipeline, health monitor, self-healing ops agent, developer scripts, and the local roadmap executor. Extracted from CLAUDE.md to keep the root context file focused on load-bearing decisions.

## `monitor/`: Health monitoring and self-healing

- `ping.py`: Tier 1+2 health checks (HTTP ping with retry), latency degradation detection (>2x baseline warning).
  - `check_app` is the one place a check cycle is counted: `down` adds one to the app's `consecutive_failures`, and `healthy` or `degraded` (the app answered, at once or on a retry) reset it to 0.
  - `run_checks` removes an app from the registry when the counter reaches 10 (about 2.5 hours at the default 15-minute interval) and logs that at ERROR, because the app's daily database dumps stop at the same moment: `monitor.backup.run_daily_backups` iterates the registry, so an app that is not registered is not dumped. The log line is the only signal.
  - `run_checks` is meant to run forever: a failed check of one app is logged and the cycle moves on, and a failed registry read (the database restarting, a dropped connection) is logged and retried after a backoff that starts at 30 s and doubles up to the interval (`TestMonitorLoopSurvivesADatabaseError` in `tests/test_probe_guard.py`); the worker's wrapper starts the loop again should it return.
- **URL guard (also in `ping.py`).** The probes' URLs come from database rows and Railway responses, so they are checked twice.
  - `probe_url_problem` reads a URL with urllib3, the parser `requests` sends with, and refuses any URL that the standard library reads differently (a backslash or a percent-encoded host, for example: `http://127.0.0.1\.evil.example` once passed the check while the request went to `127.0.0.1`), host names with characters outside letters, digits, dots and hyphens, credentials, non-http(s) schemes, internal and unqualified names, legacy numeric spellings of an IPv4 address, and literal addresses that are not public unicast. That is a check of the text only.
  - `guarded_session()` is the transport: a `requests.Session` whose connections resolve a host once, refuse unless every address is public and connect to the addresses they checked (`connect_checked` does the same for a raw socket, used by the certificate check), whose every redirect hop is checked, and which ignores proxy and `.netrc` settings.
  - `ping` and the `cli/deploy.py` probes (`verify_health`, `verify_routes`, `verify_auth`, `verify_data`, the login probe) send through it; `monitor/diagnose.py` checks a certificate with `connect_checked`; `queue/watchdog_probe.py` and the security agent send through `guarded_session()` too.
  - Every request `guarded_session()` sends is one bounded exchange (`monitor/bounded_fetch.py`): the `timeout` a caller passes is a deadline for the whole exchange (name lookup, connect, TLS, request, headers, body and at most 5 redirect hops), not a per-read timeout, and only a fixed number of decoded body bytes is kept (64 KiB for a health check, 2 MiB for a page probe, 4,096 bytes for the watchdog probe). A gzip or deflate body is inflated by a decompressor that is never asked for more than the room left, any other `Content-Encoding` is refused, and at the cap the connection is dropped. The numbers per call site are in `docs/THREAT_MODEL.md`.
  - Provider calls (Railway, Resend, the Anthropic cost report, the backup run's Railway query) go through `provider_post` and `bounded_urlopen` in the same module, with a 4 MiB cap on the answer unless the call site sets a smaller one.
  - Limits: the review browser is not covered by the address guard (Chromium resolves a name itself, and WebSocket and WebRTC traffic does not pass the guard; it has its own page and navigation timeouts instead, and its memory is not capped). The https side is tested against a loopback TLS listener with a certificate made for the test run. The name lookup of a bounded exchange runs on a helper thread that is abandoned at the deadline.
  - Tests: `tests/test_probe_guard.py`, and `tests/test_bounded_fetch.py` (a dripping body, a huge body, a gzip bomb, a redirect chain, a slow handshake, and a scan that fails on any other outbound client in `monitor/`, `queue/`, `coordinator/`, `ops/` and `cli/deploy.py`).
- `diagnose.py`: Tier 3+4 diagnosis; escalation emails via Resend. Tier 3 asks Haiku for a structured finding, tier 4 (`TIER4_MODEL`, currently Opus) reads the last 50 deployment log lines, wrapped as data with `coordinator.untrusted.wrap_untrusted` (at most the most recent 64,000 characters, redacted, cut to 8,000, every `<` replaced so the text cannot close the block), and decides whether a fix is within the self-healing allowlist (`apply_fix()`: restart, redeploy; a missing env var is alert-only).
  - A model reply can add one allowlisted fix and cannot remove the notification: every run of `run_diagnosis` ends in `_escalate`, fix or not.
  - Every model call is counted against a rolling 24-hour cap, `MONITOR_MAX_LLM_CALLS_PER_DAY` (default 60); at the cap the ladder skips the model tiers and escalates to a human.
  - `_escalate()` has a 2-hour per-app cooldown (`_last_escalated` dict) to prevent email floods for persistently down apps.
- `backup.py`, Database snapshots (pg_dump), restore, daily backups, pruning (`prune_backups`, keep=7).
  - Dumps go to `monitor/backups/<app name>__<registry id>/` (`backup_key(app)`; `app_name` alone is not unique, so two customers' same-named apps would otherwise share a directory and be pruned together) or the same directory name under `CAS_BACKUP_DIR` (set it to a mounted volume, since the default location is lost on every redeploy); each pg_dump or psql run has a wall-clock limit of `CAS_BACKUP_TIMEOUT_S` (default 900).
  - `snapshot()` runs `pg_dump` in the worker process against the `DATABASE_URL` that Railway's variables query reports for the app's service, and writes a plain SQL script taken with `--clean --if-exists`, so `restore()` can replay it onto the database it came from. Before each dump attempt `check_pg_dump_is_new_enough` compares `pg_dump --version` with the server's version (15 seconds each, for running `pg_dump` and for connecting to the server) and fails the snapshot, with both versions named and no retry, when the client is older; a version it cannot read is logged and left to `pg_dump`.
  - `restore()` runs `psql` with `ON_ERROR_STOP=1` in a single transaction: the first failing statement aborts it, the function raises, and the database is left as it was. It refuses a file that is not a complete dump, and it still holds the uncompressed dump in memory.
  - A dump is written under a temporary `*.partial` name, flushed and fsynced, checked by `dump_problem()` (gzip integrity, pg_dump's header and its "dump complete" line in the last 512 bytes: completeness, not content), renamed into place, and the directory is fsynced. Pruning counts and deletes only complete dumps and never the newest; a `*.partial` file older than twice `CAS_BACKUP_TIMEOUT_S` is removed. `snapshot()` streams to disk with no size cap. The pg_dump error text kept is at most 8,192 bytes. A diagnosis that takes a pre-fix snapshot can hold the health loop for up to `CAS_BACKUP_TIMEOUT_S` per pg_dump attempt, three attempts at most.
  - Up to 3 attempts for failures that can clear themselves (a rejected password, the database still starting up, too many connections), fetching the URL again each time (10s then 20s backoff); anything else fails at once. A failed dump is always logged at ERROR and reported in the result.
  - Not established by this repository: `deploy()` sets each customer app's `DATABASE_URL` to the private host `postgres.railway.internal` (the same name for every app), so whether the worker can reach each customer database that way, and whether the variables query returns the URL after a deploy, depends on Railway and cannot be told from the code; there is no other backup route.
  - `provision_postgres` in `cli/deploy.py` creates each customer database as a `POSTGRES_IMAGE` service (`postgres:15`, built from `POSTGRES_SERVER_MAJOR` in `cli/deploy.py`) with `PGDATA` set and never creates or attaches a Railway volume.
  - **`run_daily_backups()` graceful-skip:** when `RAILWAY_API_TOKEN` is missing/empty in the worker env (e.g. intentional safety pause during a cost-incident response), returns a single `{skipped: True, reason: "RAILWAY_API_TOKEN not set"}` marker instead of iterating apps and raising per-app, prevents Sentry spam for what is a config state, not a bug.
    - The worker's backup thread logs the skip once at info level. Shipped after a safety pause temporarily unset the token and the 03:00 UTC backup fired per-app Sentry alerts.
- `registry.py`: PostgreSQL registry of monitored apps (migrated from SQLite for Railway persistence). Tracks `baseline_latency_ms` and `last_latency_ms` with EMA (alpha=0.2). `update_status(app_id, status, ..., check_result=True)` keeps `consecutive_failures` as a count of health-check cycles in which the app did not answer: `down` adds one, `healthy` and `degraded` reset it. With `check_result=False` the status is recorded and the counter is left alone; `monitor/diagnose.py` passes that, because it runs after a failed check that was already counted and its own `degraded` ("a fix was applied") or `down` ("escalated") is not another failed cycle.
- `cli.py`: CLI: register, list, check, diagnose, backup, restore, run.

## `ops/`: Autonomous ops agent (self-healing, legacy path)

> Replaced by `coordinator/` when `COORDINATOR_ENABLED=true`. `queue/worker_pg.py` starts the ops agent thread only when the coordinator is not enabled, and it stays in dry run unless `OPS_DRY_RUN=false`.

- `agent.py`: main loop: scan builds table, match playbooks, apply fixes (30-min interval).
- `scanner.py`: query failed builds, group by normalized error signature, classify category by regex (`_CLASSIFICATION_PATTERNS`). The `railway_crash` category's playbook (`ops/playbooks/railway_redeploy.py`) redeploys the worker service, so its patterns are whole words and specific phrases (`\boom\b`, `\boomkilled\b`, `signal 9`, `killed by signal`, `process killed`, a line that is only `killed`, `enospc`, `enomem`, `service ... crashed`): a bare `oom` or `killed` would also match "room", "zoom", "skilled" and the admin kill route's own "Force-killed by admin".
- `playbook.py`: registry of known fixes with fixer module references.
- `guardrails.py`: circuit breaker (3 fixes/hour), cost guard (caps fixer runs per day, default 20; the playbooks are deterministic and make no model calls, so the `OPS_MAX_CLAUDE_CALLS_PER_DAY` name and the `claude_call` audit rows are historical), severity filter.
- `audit.py`: PostgreSQL audit log of all ops actions (migrated from SQLite for Railway persistence).
- `alerter.py`: escalation emails via Resend (fix applied, circuit breaker, unfixable). `alert_unfixable()` has 4-hour per-category cooldown (`_last_unfixable_alert` dict) to prevent repeated emails for persistent patterns with no playbook.
- `fixer.py`: applies playbook fixes on Railway only (a redeploy of the platform's own web or worker service, and one of three variables); there is no GitHub client. Reused by coordinator actuators, and its limits hold for every caller.
- `playbooks/`: fix implementations: env_config and railway_redeploy. Failures classified `version_mismatch`, `missing_dep`, `missing_tool` or `dockerfile` are reported and not fixed.

**Env vars:** `OPS_DRY_RUN` (default true), `OPS_SCAN_INTERVAL` (default 1800), `OPS_CIRCUIT_BREAKER_LIMIT` (default 3), `OPS_CIRCUIT_BREAKER_WINDOW_MINUTES` (default 60), `OPS_MAX_CLAUDE_CALLS_PER_DAY` (default 20; counts fixer runs, not model calls), `OPS_DIGEST_INTERVAL`.

**Safety:** Starts in dry-run mode. Never touches app logic. The legacy ops agent does not go through `coordinator/actuators.py` and has no permission table: what bounds it is `OPS_DRY_RUN` (on by default), the severity filter (two categories), the circuit breaker (3 fixes per 60 minutes), the daily cap on fixer runs (20) and the limits inside `ops/fixer.py` that hold for every caller. It cannot commit, queue a build, touch a customer's service or write a review verdict.

**Integration:** Runs as daemon thread in `worker_pg.py` alongside health monitor and backup threads. Not started when `COORDINATOR_ENABLED=true`.

## `scripts/`: Developer and ops utilities

- `wait_for_deploy.py`: Polls `/health` on both web+worker until `git_commit` matches `origin/master` (a 2026-04-16 fix: it was comparing against local HEAD, which goes stale after a feature-branch push and caused spurious auto-redeploys). Falls back to local HEAD if the origin ref can't be resolved, and to a manual Railway redeploy if auto-deploy never starts. Needs `CAS_PROD_URL`; the redeploy fallback also needs `RAILWAY_API_TOKEN`, `RAILWAY_WEB_SERVICE_ID`, `RAILWAY_WORKER_SERVICE_ID` and `RAILWAY_ENVIRONMENT_ID`. `--staging` switches to `CAS_STAGING_URL` and the `STAGING_*` ids.
- `wait_for_worker.py`: polls the ops API (`CAS_PROD_URL`, or `CAS_OPS_BASE_URL` when the ops API lives elsewhere; key from `OPS_API_KEY`) until no active builds (45-min stale threshold). Not used by the pre-push hook (the worker is resilient to mid-build redeploys); `.claude/settings.example.json` runs it as a warning before a push that touches worker paths.
- `qa_cas_web.py`: QA script for the CAS web platform itself.
- `run_worker_local.sh`: run the Python worker locally for dev/testing.
- `doc_update_check.sh`: check if CLAUDE.md needs updating after code changes.
- `honest_completion_audit.py`: the Claude Code Stop hook behind the honest-completion protocol in `CLAUDE.md`.
  - It is a phrase tripwire: when the final message contains one of a short list of overconfident phrases (`CLAIMS_RE`: "production-ready", "all green", "all tests pass", "works perfectly", ...) and no not-verified enumeration (`GAPS_RE`, or the explicit "Gaps: none, observed end-to-end: ..." form that must list its observations), it exits 2 and sends the message back once.
  - A label with nothing after it ("Not verified: none"), or a denied phrase ("no gaps"), does not count as an enumeration.
  - A plain "done" or "fixed" is not a claim phrase and passes; the hook cannot tell whether a listed gap is real; it blocks at most once per stop (`stop_hook_active`) and fails open on any error.
  - Of the six hooks in `.claude/settings.example.json` it is the only one that can block: the `git push` PreToolUse hook warns when a push would redeploy the worker during an active build, and the four PostToolUse hooks only print reminders.
  - `tests/test_honest_completion_audit.py` runs it as a process.
- `curate_stock_photos.py`: stock photo curation and categorization.
- `smoke_prod.py`: production/staging smoke tests hitting key CAS endpoints + one authenticated endpoint.
- `promote_staging.sh`: manual promotion from staging to production (pre-flight checks, visual regression, rollback tag).
- `capture_cas_screenshots.py`: full-page screenshots of key CAS pages via Playwright (used by `promote_staging.sh`).
- `classify_risk.py`: risk classification for executor tiered governance (reads file paths from stdin, prints high/low).
- `generate_changelog.py`: generate changelog entries from git commits since last tag; prepends to a `CHANGELOG.md` (created on first run; none is shipped in this repo).
- `bump_version.py`: semantic version bumping (patch/minor/major).
- `check_destructive_ddl.py`: rejects unacknowledged destructive DDL and row changes in `schema.sql`; invoked by `.githooks/pre-commit` (which checks the staged content, not the working tree) and CI.
  - It reads the file with a tokenizer (comments, strings including E strings, quoted identifiers, dollar quotes, statements) and flags DROP TABLE, COLUMN, SCHEMA, DATABASE and OWNED, `ALTER TABLE ... DROP col` with or without the word COLUMN, `ALTER COLUMN ... TYPE` and `SET DATA TYPE`, every `TRUNCATE`, and a `DELETE FROM` with no WHERE or with a WHERE that names no column (`WHERE true`, or a constant branch of an OR); `DROP CONSTRAINT` is not refused here.
  - DO and function bodies and strings handed to EXECUTE are read too, so a statement inside a DO block needs the `-- SAFE:` comment above it or above the DO. Because the file runs at every boot it also refuses, at any depth, `UPDATE`, `INSERT INTO`, `DELETE FROM`, `MERGE INTO`, `COPY ... FROM` and an `EXECUTE` of anything but one string literal unless a `-- SAFE:` reason is on the statement's own line or directly above it (a reason above the DO does not count for these).
  - A row change or dynamic `EXECUTE` that names the string `live`, and any column `DEFAULT` of `live`, is refused whatever comment is above it (`NAMES THE STATUS live`): three statements of the web application write that status and the schema file is not one of them. A statement over 2000 tokens is refused as unreadable.
  - SQL it cannot read is refused, and an unreadable file or one over 8 MiB exits 2. It does not evaluate expressions (`WHERE id = id` passes), does not follow a value through a variable or a call, and does not decode strings (`E'\x6c...'`, concatenation).
  - Add `-- SAFE: <reason>` above the DDL to acknowledge. The comment satisfies this check only: `web/tests/unit/schema.idempotency.test.ts`, which the pre-push hook runs, refuses a top-level DROP TABLE/COLUMN/CONSTRAINT, TRUNCATE, DELETE, UPDATE or INSERT whatever precedes it, reads the file with its own tokenizer (held to the same corpus, `web/tests/unit/fixtures/sql-scan-corpus.json`) and lists the nine row changes the file may contain.
- `check_schema_drift.py`: detects schema drift between PostgreSQL environments (local vs prod) by introspecting table/column definitions; exits 1 on drift, 2 on connection error.
- `verify_hooks.sh`: guardrail drift checker. Exit 1 on any drift:
  - `core.hooksPath` points at `.githooks` (skipped in CI);
  - the required hook files (`pre-commit`, `pre-push`) exist;
  - they are executable;
  - both hooks are run in a throwaway repository, 18 accept-or-refuse checks, about 2.5 s: the hooks' own checks for DDL, JSON, brand voice, the bless gate and the staging gate are real; for the audits, the web tests and the SEO lint the three pre-push scripts and the lint are stand-ins, so what is verified is that the hook runs them and stops on failure, not what they find (the script header lists exactly which). A hook that is an empty stub fails, and so does one gate switched off;
  - `.githooks/` holds nothing but those two files, because a file there named after a git hook runs for everyone who enabled the hooks.
  - It is invoked locally (`make verify-hooks`) and by `.github/workflows/hook-integrity.yml` as the server-side backstop for `--no-verify` / `chmod -x` / `core.hooksPath` drift.
- `classify_push.py`: decides whether the commits a push would send are fast-path-safe (docs, scripts, CI, hooks, tests) or need the staging path (`web/`, `cli/`, Dockerfiles and so on). Nothing calls it automatically.
- `sync_staging_from_master.sh`: idempotent script that merges `master` into the `staging` branch and pushes it, so that fast-path pushes do not leave staging behind. It is run by hand; nothing in this repository calls it.
- `run_web_tests.sh`: runs the web unit tests once (`npm test` in `web/`) after checking that `web/node_modules` exists, so a fresh clone gets an install hint instead of "vitest: command not found". Called by `.githooks/pre-push`. (It replaced `run_web_tests_parity.sh`, which ran the suite twice under a `BETA_MODE` variable that no code reads.)
- `run_dep_audit.sh` and `run_python_security_audit.sh`: the npm audit (web/, prod dependencies, high and above) and the Python audit (bandit at medium severity and confidence over `cli/ queue/ coordinator/ monitor/ ops/ compose/ scripts/`, plus pip-audit). bandit runs with no baseline file; any finding at those thresholds fails. Both honor `CAS_SKIP_AUDIT=1`. Called by `.githooks/pre-push`; CI runs them in an advisory job.

## `scripts/`: Roadmap Executor (local autonomous agent)

- `cas-roadmap-loop.sh`: main executor loop. Runs via launchd (plist template: `scripts/com.cas.roadmap-executor.plist.template`). Picks items from `coordinator/roadmap.json` and invokes Claude Code in git worktrees. Per item it:
  - checks that the session left a committed change and a clean worktree, and applies the merge guard (`scripts/cas-merge-guard.py`);
  - runs the tests (`npm test` and `pytest tests compose/tests`) on a fresh checkout of the one commit the session left;
  - waits (up to 45 minutes) until the ops API reports no build queued, building, testing or deploying;
  - applies the guard again, checks the branch is still that commit and merges that commit to master;
  - commits the item's `completed` mark as one change to `coordinator/roadmap.json`, pushes, and reports results to the ops API.
  - It starts no session and pushes nothing when the ops API does not answer its build counts or today's spend, or when the cost report is incomplete: only a JSON object with `platform_costs_partial` exactly false and a finite, non-negative, numeric `today_total` under the ceiling starts a session, so the web app needs `ANTHROPIC_ADMIN_KEY` (without it the report is always partial and an enabled executor starts nothing).
  - An interrupted merge is settled first: the merge section writes a journal (`logs/executor/merge-in-progress`) before the stash, the merge and the push, and the next cycle (or the way out of a signal) keeps the merge if the remote has it, takes it back with `git reset --keep` if the remote lacks it, and starts no session when the remote cannot be asked, a person has committed on top, the checkout is on another branch or taking it back would overwrite a person's edit (`take_back_merge`, which the two places where a run gives up on its own merge use as well).
- `cas-merge-guard.py`: the merge guard's rules (`PROTECTED_PATHS`, `TEST_DIRS`, the ASCII and symlink rules), run by the loop as `LC_ALL=C python3 -I`.
- `cas-pick-item.py`: item picker. Filters by status, priority, dependencies, daily failure count, total failure count, and complexity. `--list` shows eligible items with markers (BLOCKED, COMPLEX, FAILS:N). `--build-prompt ITEM_ID` generates Claude Code prompt from template.
- `cas-executor-config.json`: live config (read every cycle, no restart needed). Ships with `enabled: false`. Fields: `enabled` (a missing key also means disabled), `interval_minutes`, `max_parallel`, `max_items_per_day`, `max_budget_per_item_usd`, `daily_spend_ceiling_usd`, `pause_until` (ISO timestamp), `max_total_failures_before_defer` (4), `skip_complex_items` (true), `target_branch`, `use_staging_workflow` (read by the pre-push hook), `tiered_governance` (on for any value but JSON false). Only a JSON `true` for `enabled` enables the loop, the watchdog and `cas-exec status` alike (`executor_enabled` in `cas-pick-item.py`); a `pause_until` that is not a time is a pause, and a value of the wrong kind stops the cycle with the key named. See `docs/LOCAL_EXECUTOR.md` for the shipped values.
- `cas-executor-prompt.md`: Claude Code prompt template. Injects `{{ITEM_JSON}}` and `{{ITEM_ID}}`. Safety boundaries: exits cleanly if uncertain about customer-facing/billing/security changes. Efficiency guidelines: max 5 files, early test runs, 10-min time budget.
- `cas-exec`: CLI control tool. Commands: `start|stop`, `fast|slow|normal` (interval), `parallel N`, `pause|resume|pause-until T`, `status`, `run-once`, `logs [item-id]`, `queue`, `failures`, `deferred`, `config`.

**Failure handling:** items failing 3+ times today are skipped. Items reaching `max_total_failures_before_defer` (4) across all days are auto-deferred in `roadmap.json`. Failure tracker at `cas-executor-failures` in the state dir (`CAS_EXECUTOR_STATE_DIR`, else `$TMPDIR`, else `/tmp`; 7-day retention).

**Retry logic:** transient git operations (fetch, pull, push) retry with exponential backoff (3 attempts for fetch/push, 2 for pull). Non-transient operations (worktree creation, Claude Code, tests) do not retry.

**Per-stage timing:** each run logs worktree/claude/test/merge stage durations. Included in ops API result posts.

**Cost tracking:** parses `Total cost: $X.XX` from Claude Code output; falls back to duration-based estimate ($0.10/min). Reported to ops API per item.

**Complexity detection** (`estimate_complexity` in `cas-pick-item.py`): an explicit `complexity` field wins; otherwise keywords in the title ("redesign", "overhaul", "rewrite", "comprehensive", "migration"), overhaul markers in the description ("deep plan", "top to bottom", "bulletproof", ...) or a >800-character description with 5+ numbered steps classify an item as "complex", and it is skipped when `skip_complex_items` is true.

**Safety:**
- Lockfile single-instance enforcement (locks are created by hard link to a file that already holds the process id, and a stale one is removed only under a `mkdir` guard after the owner is read again; they identify an owner by process id alone), 20-min per-item timeout, merge lock serialization, `git merge --no-ff` merges. Every timed job is a process group: on a timeout or a signal the loop signals the group and the process tree, then SIGKILL after 2 s.
- It waits for active customer builds before merging (45 min at most) and fails closed: the build counts come from `GET /ops/api/v1/builds`, and if they cannot be read it pushes nothing. Preflight likewise starts no session when the counts or today's spend cannot be read.
- Every ops API request, `git fetch`/`pull`/`push`, `gh pr create`, the session and the gate's three commands (`npm install`, `npm test`, `pytest`) run under a time limit (`CAS_OPS_TIMEOUT_SEC`, `CAS_EXECUTOR_NET_TIMEOUT_SEC`, `CAS_EXECUTOR_PUSH_TIMEOUT_SEC`, `CAS_EXECUTOR_GATE_TIMEOUT_SEC` for each gate command, default 1800). The watchdog's Claude probe has one too (`CAS_WATCHDOG_PROBE_TIMEOUT_SEC`, 30). The per-item log file has no size limit.
- The only commit besides the merge is an item's status change (`record_roadmap_status`), made through the pre-commit hook. It tolerates, and never commits, edits to `failure_kb.json`, `cas-executor-config.json` and `CLAUDE.md`.
- It yields the tick if `coordinator/roadmap.json` differs from HEAD, if `PROJECT_DIR` has other dirty tracked files (instead of auto-stashing) or if `PROJECT_DIR` is not on the target branch. It does NOT yield on untracked files (`^??`).

**Change check and merge guard:** the guard runs in two places, and a run that fails either is discarded (worktree and branch removed, failure recorded), with the failure posted to the ops API as `"No committed change"` or `"Protected file"`.

- *Change check,* after the Claude session exits and before anything is tested: the worktree must still be on `auto/<item-id>`, hold no uncommitted or untracked files (the `web/node_modules` link the loop made is the one expected entry), and the branch must differ from, and descend from, the commit the worktree was created from (`base_sha`, recorded by hash before the session ran, not a ref the session can move).
  - The branch tip is read once at this point (`tested_sha`) and that one commit is carried through everything below.
  - A session that did nothing, or that left an edit uncommitted, would otherwise be merged as "Already up to date" and its item marked completed, or have its tests pass on code that is not what gets merged.
  - The prompt (`scripts/cas-executor-prompt.md`) tells the session to commit and to leave `git status` clean.
- *First pass,* before the tests (so the test commands that run are the target branch's, not ones the session rewrote) and before the tiered-governance path can push the branch anywhere: `guard_report` reads `git diff -z --raw --no-renames --ignore-submodules=none <base_sha>...<tested_sha>` and hands it to `scripts/cas-merge-guard.py`, which refuses any added, modified, deleted or renamed path in its `PROTECTED_PATHS`. A listing the helper cannot read (cut short, an unknown status, over 16 MiB, the helper missing or failing) exits 2, which the loop treats as a refusal.
  - The set is:
    - any `CLAUDE.md` or `CLAUDE.local.md`, `.claude/`, `.mcp.json`;
    - `coordinator/roadmap.json`;
    - everything under `scripts/`;
    - `.githooks/`, `.github/`, `.gitleaks.toml`;
    - what `npm install` and `npm test` read or run before a test (any `package.json`, lockfile or shrinkwrap, any `.npmrc`, anything under a `node_modules`);
    - what Vitest evaluates before a test file (`web/vite*` and `web/vitest*` config, the PostCSS configuration, the setup file `web/tests/unit/setup-no-dotenv.ts`);
    - every `conftest.py` and pytest configuration file (`pytest.ini` and `pytest.toml`, with or without a leading dot, `pyproject.toml`, `tox.ini`, `setup.cfg`);
    - what pytest imports before it collects (top-level Python modules, source and bytecode and extension modules, the `__init__.py` of top-level packages such as `tests/`, top-level `*.dist-info` and `*.egg-info`);
    - the Tailwind and Playwright configuration (`web/tailwind.config.*`, `web/playwright.config.*`);
    - every Dockerfile, `.dockerignore`, the Railway and nixpacks configuration, every `requirements*.txt`;
    - the `Makefile` and any compose file with its overrides;
    - `web/src/db/schema.sql` and `web/src/db/migrate.ts`;
    - and the files a version-manager shim reads.
  - Separately, a branch may add and edit files under any directory named `tests`, `test` or `__tests__` but may not delete or rename one (`tests/test_executor_loop_behavior.py` walks the repository and fails when a test file lives somewhere the rule does not cover), and a branch that leaves a symlink (mode 120000) or a submodule link (160000) is refused.
  - A path with a byte outside printable ASCII (0x20 to 0x7E), or that is not valid UTF-8, is refused, because on a filesystem that folds case and Unicode normalization (APFS) a name spelled with U+212A for the k is the same file as `.githooks/`; such a path is reported with what it folds to.
  - Paths are compared as bytes, ASCII letters without regard to case, under `LC_ALL=C`; the guard no longer uses `grep`, whose folding follows the locale.
  - `--no-renames` matters because with rename detection `git mv .githooks/pre-push docs/x` is listed under the new name only; `-z` matters because git quotes a path with a non-ASCII byte.
  - The target branch is resolved with full refs (`refs/heads/T`, `refs/remotes/origin/T`, fetched with an explicit refspec), so a tag named like the branch changes nothing.
  - The tiered-governance risk classifier is also fed `--no-renames` output, so renaming a high-risk file does not hide it.
- *The test gate* (`run_test_gate`), between the two passes: the tests do not run in the session's worktree, which can hold ignored files, a `.gitignore` edit that hides a file from `git status`, or an edit to a tracked file hidden with `git update-index --skip-worktree`.
  - They run on a fresh detached checkout of `tested_sha` at `.worktrees/gate-<item-id>` (removed afterwards, and by the watchdog and `cleanup_worktrees` if the run died), with the `web/node_modules` link.
  - `npm install` and `npm test` run the commit's own commands, which the guard has pinned to the target branch's.
  - pytest is started as `python3 -P -m pytest -c <file written by the loop> --rootdir --confcutdir --disable-plugin-autoload -p no:cacheprovider tests compose/tests -q` with `PYTHONPATH`, `PYTEST_ADDOPTS` and `PYTEST_PLUGINS` unset: `-P` keeps the working directory off `sys.path` so a top-level `pytest.py` cannot replace the installed one, the configuration file is the target branch's `pytest.ini` (or an empty one), and no installed plugin loads.
  - The gate needs python3 3.11 or newer and pytest 8.4 or newer and fails closed without them; a pytest configuration kept in `pyproject.toml`, `tox.ini` or `setup.cfg` is not read by the gate.
- *Second pass,* the same rules applied to what the merge is about to bring into the local target branch (`tested_sha` against the commit it is merged into, which differs from the first pass's base whenever the branch has moved on, a pull or a script another clone pushed, for example), just before `git merge --no-ff`, after the merge lock and the build wait, and then a check that `auto/<item-id>` still points at `tested_sha`: if the branch moved after its tests ran, the run is refused ("The branch moved after its tests ran").
  - What is merged, or pushed as a draft pull request, is the tested commit by its hash.
  - `scripts/cas-roadmap-loop.sh --guard-check` runs only the path rules (a diff on stdin, the refused paths on stdout) and exits without starting a loop; `tests/test_executor_loop_behavior.py` drives the real loop against a throwaway repository (a shadowing `pytest.py`, an `.npmrc` under `web/`, a hidden test command, a commit made after the tests, a moved base ref, a branch rebuilt on an older commit, a Unicode spelling of `.githooks/`, a deleted test outside `tests/`, a submodule link and a tag named like the branch are each a case there), and `tests/test_executor_loop_recovery.py` kills the loop with SIGTERM and SIGKILL at each step of the merge section.

Rationale: an unattended agent must not be able to loosen the limits, hooks, CI or test gate that constrain the next run, remove a test, queue more work for itself, or rewrite the context every Claude Code session reads, and what is merged must be the thing that was tested.

Limits: the session is not sandboxed and can write outside its worktree, so the guard and the gate bound what a branch can get merged, not what a session can do; the guard reads the commit's diff and cannot see what a session did outside git; a branch may still weaken a test, or code a test imports, that it is allowed to edit; and a test file or imported module that exits the process with status 0 still passes the gate. The gate runs `tests` and `compose/tests` but not Playwright (`web/tests/ui` is protected from deletion and not run).

**Concurrency rule:** one interactive Claude Code session per `PROJECT_DIR` at a time. For parallel work use `git worktree add ../cas-session-N -b topic` and run the second session there. The executor counts as a session for this rule; unload the executor LaunchAgent for full isolation during long interactive work (not just `cas-exec pause`, which still runs the housekeeping loop).
