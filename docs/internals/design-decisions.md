# Key design decisions: reference detail

> Historical document from July 2026; the system was wound down in July 2026.

> **Scope:** secondary/descriptive Key Design Decisions extracted from CLAUDE.md. The top-level CLAUDE.md keeps only the behavioral contracts that are frequent bug sources (CSRF, EJS escaping, session.save, SE Review Gate, etc.); everything else lives here for reference. Statements below are checked against the code as of the final review round; entries under the dated "Migrated from CLAUDE.md" heading are historical records of shipped features.

## Security & auth

- **trust proxy:** `app.set('trust proxy', n)` in `web/src/app.ts`, where `n` is `TRUST_PROXY_HOPS` (`resolveTrustProxyHops`). Unset, empty or not a whole number means 1 (the single Railway edge proxy) and logs a warning at boot; `web/.env.example` ships 0, for a local run with nothing in front. It is required for secure cookies and for the client address used by the rate limiters. Too high a value on an app that is exposed directly lets any client forge `X-Forwarded-For` and walk past every per-address limit; too low behind a proxy makes all visitors share the proxy's address and stops the Secure session cookie from being issued. Set 0 when nothing proxies the app, 1 behind one proxy such as Railway.
- **Admin support-kb clear:** POST `/admin/support-kb/clear`, one-click cache clearing with CSRF + admin gate.
- **Account deletion:** GET `/account/delete` shows confirmation page, POST `/account/delete` requires password confirmation. In one transaction it deletes the account's intake messages, feature requests and their messages, beta feedback, scheduled emails and Haven trials (the trials' turns and notes cascade from the trial row), then the customer row (password reset tokens, the keeper row with its turns and notes, and subscription rows cascade from it); a Stripe cancellation at period end is requested first, and subscription ids are kept as tombstones for 90 days. Builds are kept with their customer link removed (queued ones are marked failed first). GDPR right to erasure. Requires auth.
  - A trial is the account's when it is stamped with one of the account's builds, or carries the account's address and no other account's build is stamped on it (`ACCOUNT_TRIALS_SQL` in `routes/auth.ts`); the address is cleared from any other trial that still carries it.
- **Customer data export:** GET `/export-data`, JSON download of customer profile, builds, intake conversations, and feature requests. "Export Data" button on dashboard. GDPR compliance.
- **Source code export:** GET `/builds/:buildId/download-source`, downloads the build artifact (tar.gz). Requires auth + ownership. The owner gets it for a `live` build, or for a preview the owner could publish right now (`OWNER_SOURCE_DOWNLOAD_SQL`: at `preview`, reviewed and `approved`, and, for a Harbor build, with a publishing subscription), because the terms assign the source to the customer "upon successful delivery"; the status page shows the link only when the route would serve it. The admin can download any preview or live build. Build artifacts are kept in `builds.build_artifact` BYTEA column after deploy (no longer cleared). Artifacts exclude `node_modules` and `.git`, typically 1-5MB.
- **Email validation:** Server-side regex (`/^[^\s@]+@[^\s@]+\.[^\s@]+$/`) on signup and login POST routes, in addition to client-side HTML5 validation.

## Intake flow

- **Logo upload:** POST `/intake/:buildId/logo`, multer file upload (2MB limit, PNG/JPEG/SVG/WebP), processed with sharp. Extracts dominant colors via pixel sampling, auto-populates `spec.design`. Logo stored as base64 data URI in spec.
- **Intake complexity guardrails:** `checkSpecSimplicity()` in `services/spec-validation.ts` warns if the app is too simple (`MIN_COMPLEXITY` in `types/index.ts`). The per-tier limits (`TIER_LIMITS`, `validateSpecForTier()`, `suggestTierForSpec()`) were removed on 2026-05-01 with the tier system.
- **Content moderation:** Two-layer system. Layer 1: CONTENT POLICY section in intake system prompt instructs Claude to decline prohibited app categories (illegal goods, fraud, phishing, gambling, harassment, exploitation, spyware, IP infringement, violence). Graceful decline with suggestion of legitimate alternatives. Layer 2: `checkProhibitedContent()` in `spec-validation.ts` scans spec fields (`app_name`, `description`, `pages`, `models`, `actions`) against a keyword blocklist. Called at POST `/intake/:buildId/confirm` before tier validation; blocks the build before it enters the queue.
- **Payment scope management:** PAYMENT PROCESSING GUIDANCE in intake system prompt. Claude declines full Stripe checkout/subscription requests and recommends Stripe Payment Links.
- **Intake abandon detection:** Periodic check in web process (setInterval, configurable via `ABANDON_CHECK_INTERVAL_MS`, default 15m). After 24h of no intake messages, marks build as `abandoned` and sends nudge email with resume link. After 7 days abandoned, auto-deletes with full cascade. Visiting `/intake/:buildId` for an abandoned build transparently resumes it (flips status back to `intake`). `abandoned_at` column tracks when abandonment happened; `abandoned_email_sent_at` prevents duplicate emails. Service: `services/abandon-check.ts`.

## Build pipeline UX

- **Pre-fix snapshots:** Worker copies build directory before test-fix and deploy-fix attempts for rollback capability.
- **Build log viewer:** Real-time pipeline logs on the status page. Worker writes curated messages to `build_logs` table via `_append_log()` (the web tier also writes the `manual_retry` and `admin_retry` stages when a build is retried). Frontend polls `/api/builds/:buildId/logs?after=<cursor>` alongside status polling. Terminal-style dark panel with stage headers. ~10-15 entries per build.
- **Status page polling:** `web/public/status.js` polls `/api/builds/:buildId` (and the log endpoint while the build is active) and keeps polling at a slower interval after a terminal state, so a requeue or rebuild is noticed.
  - It updates the progress steps and status badge in place for active states.
  - It does a full `window.location.reload()` on: a terminal state (`failed`, `preview`, `live`) being reached, a terminal build going back to an active state, a change of `review_status` (so the server-rendered preview panel picks up the reviewer's notes), and a 30-minute safety timer for a page that never reaches a terminal state.
  - A reload is skipped while a form is navigating away (the approve submit).
  - The server renders the preview and live banners (including the CSRF-protected approve form) in `views/status.ejs`; an earlier version injected them from script, which is no longer the case.
- **Login to the built site:** the generated app has no seeded password. The worker's preview-ready email (`send_preview_ready` in `queue/mailer.py`) carries a single-use, 24-hour magic-link login URL for the customer's built site; after logging in the customer sets their own password. (`send_app_live` in the same module can carry one too, but nothing in this repository calls it: the app-live email that is sent is the web tier's `sendAppLiveEmail` on approve, which takes no login link. The web tier's `sendPreviewReadyEmail` accepts an optional `magicLinkUrl`, but its only caller, the optional `POST /webhooks/build-status` hook, does not pass one.) The admin email comes from `spec.admin_email` (persisted by the worker to `builds.spec` JSONB after injection), with fallback to the session email.
- **Visual verification screenshots:** Pipeline captures screenshots during test phase (login + up to 5 auth pages) and after deploy (login + up to 3 auth pages via live URL). Stored in `{build_dir}/screenshots/` and `screenshots/deploy/`, paths saved to `builds.screenshots` JSONB column. Served via `GET /api/builds/:buildId/screenshots/:filename?subfolder=deploy`. Gallery shown on status page for preview/live builds. Best-effort: failures never block the pipeline.

## Rebuilds & revisions

- **One-Click Rebuild:** POST `/builds/:buildId/rebuild` creates a new build from an existing live or failed build's spec. Optional `rebuild_request` text for change descriptions. No re-payment required. New build goes straight to `queued`. Tracks lineage via `parent_build_id` column. Modal UI on dashboard and status page. Worker injects `rebuild_request` into spec so `build.py` can use it as a priority section in the Claude prompt.
- **Customer Revision Loop:** GET `/builds/:buildId/revision` shows interactive AI scoping chat (multi-turn conversation builds a REVISION SUMMARY).
  - POST `/revision/message` handles AI turns.
  - POST `/revision/confirm` submits the finalized revision description and queues a new build.
  - POST `/builds/:buildId/revision` (legacy submit path also preserved).
  - There is no per-tier revision allowance any more (`TIER_REVISION_LIMITS` was removed on 2026-05-01; the product promises unlimited revisions).
  - Abuse bounds in `services/build-start-limits.ts` instead: `MAX_ACTIVE_BUILDS_PER_CUSTOMER` (2), `MAX_BUILD_STARTS_PER_DAY` (10 per rolling 24 hours across a conversation's first build, rebuilds, revisions and manual retries) and `MAX_MANUAL_RETRIES_PER_BUILD` (3), counted from the database (`builds` and `build_start_events`) under a per-customer advisory lock; the admin is exempt.
  - The retry, rebuild and revision routes in `routes/builds.ts` use that module, and so does the Harbor dispatch (`dispatchHarborTrialBuild`, `dispatchHarborKeeperBuild` in `services/harbor_dispatch.ts`): a conversation's first build takes the same lock, is refused at the same two limits (`build_limit`, a 429 from `POST /lighthouse/build`) and writes a `build_start_events` row of kind `dispatch`.
  - The kinds are `retry`, `rebuild`, `revision` and `dispatch`; every kind counts toward the daily total, and the two readers that count one kind per build id never count a dispatch (the coordinator's lineage count reads only `rebuild` rows filed under the root's id). The coordinator's automatic rebuild repeats the lock key and the two counts in Python (`Actuators.queue_rebuild`). The operator's dispatch route in `admin.ts` is exempt, like the admin's rebuilds.
  - The checks that can refuse a dispatch (a verified account, the limits, the anonymous share of the model-call budget) run before the extraction, so a refused request costs no model call.
  - Revision lineage is tracked via the `is_revision` boolean column and `parent_build_id`.
  - The counts come from the `build_start_events` ledger (one row per accepted start; it has no foreign key to `builds` because the worker prunes a customer's older failed builds and their logs, which would hand the budget back).
  - `POST /builds/:buildId/retry` additionally writes a `build_logs` row with stage `manual_retry` (owner) or `admin_retry` (admin) as an audit trail.
  - Revision feedback injected as "REVISION REQUEST (HIGHEST PRIORITY)" section in build prompt. View: `revision.ejs`.

## AI / Claude service

- **Claude API circuit breaker:** Module-level state machine in `services/claude.ts`. 5 failures in 60s window opens the circuit for 30s. Half-open allows one probe call. Greeting functions return fallback strings when open; message functions throw `CircuitBreakerOpenError`. Exports: `getCircuitState()`, `resetCircuit()`.
- **No artificial reply delay:** an earlier version held every intake, revision, feature and support reply for a random 0.8 to 2.4 seconds (`withMinThinkDelay` in `services/claude.ts`, with a `DISABLE_MIN_THINK_DELAY` switch) so that AI replies would not feel instant, while the chat page showed typing dots during the hold. That imitated a person composing a reply, beside a persona that is meant to be honest about being an AI, so the function, its six call sites and the switch were removed. Replies go out as soon as the model answers; `replies are not held back to imitate human typing speed` in `web/tests/unit/claude.service.test.ts` fails if a delay comes back.
- **Support chat:** Floating widget on all pages (except `/intake/`). AI-powered via Claude Sonnet (`SUPPORT_MODEL` in `routes/support.ts`). Requires authentication (`requireAuth` middleware on POST `/api/support/chat`). A cached answer from the `support_kb` table is returned when its question matches by word overlap (`SIMILARITY_THRESHOLD` 0.6, scanning the 500 most-used rows).
  - **The route never writes to `support_kb`:** an answer generated for one customer is returned to that customer only, because the table is shared and a stored answer could be steered by text the sender controls. Rows come from operator-side jobs (the coordinator's knowledge sync and the weekly topic sweep in `cron/topic_kb_sweep.ts`), which filter content before inserting.
  - Rate limited to 10 msgs/min per user. Multi-turn conversation (sends at most the last 20 messages, 20,000 characters, as history). Max 2048 tokens per response.
- **Support knowledge:** `services/support-knowledge.ts` (`generateKnowledge()`) builds the support chat's system-prompt knowledge. Feature-request prices and size labels come from `types/index.ts` (`FEATURE_DISPLAY_PRICES`, `FEATURE_SIZE_LABELS`); the Harbor prices are literals in that file that mirror `harborSubscriptionPrice` and `harborSlidingScalePrice` in `app.ts` and must be kept in sync by hand.

## Webhooks & payments

- **Stripe webhook idempotency:** Atomic INSERT-first pattern in `processed_webhooks` table. Each event runs in one database transaction: the claim `INSERT ... ON CONFLICT DO NOTHING RETURNING event_id`, the handler's work and COMMIT. A handler that throws rolls the claim back with everything else, so Stripe's retry is processed from scratch instead of being answered as a duplicate; a second delivery that arrives while the first is in flight waits on the claim's primary key. Emails are sent after the commit. Periodic prune of records older than 7 days (at most once per hour).
- **Resend webhooks:** POST `/webhooks/resend` handles email delivery, bounce, and complaint events with Svix signature verification. Updates `email_log` status.
- **Feature requests:** Customers with live apps can request new features via `/projects/:buildId/features`. AI scoping chat (Claude Opus), tiered pricing, `STRIPE_BYPASS` supported. Tables: `feature_requests`, `feature_messages`.

## Observability & ops

- **Error diagnostics:** In-memory buffer of last 20 server errors, exposed via GET `/ops/api/v1/errors`. Captures method, path, message, and stack trace.
- **Dead letter queue:** Failed builds are recorded in `dead_letter_builds` with error classification (transient, timeout, infra, code_error). DLQ insert and status update happen in a single transaction with fallback. Error messages truncated to 4000 chars.
- **Deep health check:** GET `/health` returns DB connectivity, latency, memory stats, and pool stats. Returns 503 with `status: degraded` on DB failure.
- **Graceful shutdown:** `server.ts` handles SIGTERM/SIGINT: stops accepting connections, drains DB pool, exits cleanly. 30s forced timeout as safety net. Critical for Railway deploys.
- **Stage timing metrics:** Worker tracks building/testing/deploying stage durations via `_start_stage()`/`_end_stage()` closures. Saved to `builds.stage_timings` JSONB column. Format: `{"building": {"start": "iso", "end": "iso", "duration_s": N}, ...}`.
- **UTM tracking:** Signup form captures `utm_source`, `utm_medium`, `utm_campaign` from query params (stashed in session to survive POST). Stored on `customers` table. Page view middleware in `app.ts` records every request to `page_views` table with UTM params, the referrer as a path (no query string or fragment), session ID, and customer ID. Analytics endpoint at `GET /ops/api/v1/analytics` aggregates funnel metrics.
- **Health badges on dashboard:** Live builds show a colored health indicator dot (green=healthy, red=down with failure count) on the dashboard. Data sourced from `monitor_apps` table joined to builds via `health_status` and `health_consecutive_failures`.

## Beta & feedback

Submits to `POST /feedback` (JSON API with header-based CSRF). Rate limited to 5/min per user. Admin view at `GET /admin/feedback` with category filter and pagination. Table: `beta_feedback`.

## UX niceties

- **Static asset caching:** `express.static` serves `/public` with `maxAge: '1d'` (`Cache-Control: public, max-age=86400`).
- **Double-submit guard:** Global script in `layout.ejs` disables submit buttons and shows "Processing..." on form submit. Forms that need a confirmation dialog use `data-confirm="message"` attribute (NOT inline `onsubmit`), which is checked in the same event listener before disabling the button. Cancelling the confirm dialog prevents the "Processing..." state. Forms can opt out with `data-no-submit-guard`.
- **npm audit in pipeline:** Advisory `npm audit --audit-level=high --json` runs in `setup_app()` after `install_deps()` succeeds. Logs high/critical vulnerability counts but never blocks builds. Wrapped in try/except for safety.

## Admin surface

- **Admin coordinator page:** `GET /admin/coordinator` shows coordinator tick history with agent/status/date filters, pagination, and 30s polling. JSON API at `GET /admin/api/coordinator`.
- **Admin approvals page:** `GET /admin/approvals` shows pending approval requests from coordinator agents. Approve/reject individual requests (POST with CSRF) or batch process. Status filter (pending/approved/rejected/all). Table: `approval_requests`.
- **Admin executor page:** `GET /admin/executor` shows executor run history and pending questions. Admin can answer blocking questions via POST `/admin/executor/answer/:id`. Real-time status updates. Tables: `executor_runs`, `executor_questions`.
- **Admin settings page:** `GET /admin/settings` shows the coordinator's settings as the worker will read them. POST `/admin/settings/coordinator` writes the settings that were changed to the worker service's Railway variables through the GraphQL API.
  - It writes one service only (`RAILWAY_WORKER_SERVICE_ID` in `RAILWAY_PROJECT_ID` and `RAILWAY_ENVIRONMENT_ID`, with `RAILWAY_ADMIN_TOKEN`) and only twelve names from a list in `services/coordinator-settings.ts`: `COORDINATOR_ENABLED`, `COORDINATOR_DRY_RUN`, `COORDINATOR_DAILY_BUDGET` (0 to 500), `COORDINATOR_INTERVAL_S` (whole seconds, 300 to 7200) and eight `AGENT_*_ENABLED`.
  - Each switch is drawn in the state the worker reads from the stored text (`utils/env-switch.ts` holds the same word lists as `coordinator/envflags.py`; a variable that is not set shows as its default), a variable is written only when the form carried it and its value differs from what the page showed, and only `true` or `false` is written. Changes toward the safe state go first, and the save stops at the first Railway failure.
  - A save that turns `COORDINATOR_DRY_RUN` off or `COORDINATOR_ENABLED` on is refused, and writes nothing, unless the form carries the typed phrase `go live`. The write is gated by `isRailwayWriteEnabled()`, `requireAdmin` and the CSRF token. Variables that cannot be read are not drawn and nothing can be saved.
- **Admin reviews page:** `GET /admin/reviews` shows pending builds awaiting SE review with stat cards (pending, reviewed today, total reviewed). `GET /admin/reviews/:buildId` shows build detail with approve/request-changes forms. JSON API at `GET /admin/api/reviews` for polling. Admin nav entry and stat card on `/admin/builds`.

- **Faithful-copy mode:** opt-in path that mirrors a customer's existing live website verbatim instead of stamping archetype defaults on top of it.
  - Driver: on a faithful rebuild of an existing site, archetype defaults added invented "trust badges" + "Ready to begin?" CTAs + an offerings grid the source never had.
  - Pipeline:
    - (1) admin/dispatch path runs `web/src/services/site_copy_crawl.ts:crawlSite(url)` (pure-fetch plus single-pass HTML scanners in `site_copy_parse.ts`, no Playwright; same-origin link discovery; max 6 pages; a 60s deadline for the whole crawl and 15s for any one request, counted from when it starts and enforced wherever the request is by then, the DNS check, a redirect hop or the body read; 2 MiB cap on the decompressed body, 16 KiB on response headers; page paths of at most 200 characters and media URLs of at most 2048).
      - The scanners replaced a set of regular expressions that were quadratic or worse on hostile input (a page of repeated `<!--` or `<script ` froze the web process for minutes, timers and the crisis handler included), and nothing the remote site sent is parsed on the web process's event loop: the HTML is parsed in a `worker_threads` worker (`ParseWorker` in `site_copy_crawl.ts`, entry `site_copy_parse_worker.ts`) that is killed after 10s or what is left of the crawl deadline and capped at 256 MB of heap, so a non-linear pattern added later costs one abandoned crawl, not a frozen server.
      - The kill is the backstop; the scanners' linearity is the guarantee (`services.site-copy-crawl.linear-time.test.ts`).
      - Because the URL is typed by an admin and redirect targets come from the remote site, every request, including each redirect hop, must be http(s) without credentials, on port 80 or 443, to a host whose every resolved address is public; the connection is opened to an address that was just validated (no second, unchecked resolution).
