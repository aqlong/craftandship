# Known limitations

What the code does not defend against or does not do, grouped by area. [SECURITY.md](../SECURITY.md) has the status of this repository and the definitions of "preview", "review" and "live"; [THREAT_MODEL.md](THREAT_MODEL.md) has the controls.

Each is true of the code as published; the file named is where to look.

## Preview, review and live

- A preview is a public, crawlable site, and the customer holds its address and an admin login before any review ([worker_pg.py](../queue/worker_pg.py), [compose/build.py](../compose/build.py)). The review and the subscription gate the `live` status in the platform database, not the site, and what the owner's publish requires is a recorded verdict (`review_status = 'approved'`), not a particular reviewer. The web app's customer copy was rewritten to say that and to name no reviewer. The worker's build-failed email still says more than the code does ([mailer.py](../queue/mailer.py)): it promises a personal follow-up within 24 hours and a full refund, neither of which any code carries out. The preview-ready emails of the worker and of the web app no longer tell the customer to click before the review; they say the button appears when the review is done.
- A review verdict covers the build as deployed. The customer can edit the site's content through its admin before and after the review, and nothing re-opens the review when they do.
- Nothing takes a deployed site down because changes were requested, a revision superseded it, its subscription ended or it was never approved. A customer's Railway project is deleted in four ways: by the worker attempt that created it, when that attempt ends without reaching preview; by an admin delete of the build with Railway writes enabled; by the orphan sweep that ships off; or by an operator script.
- The automated review mode (`CAS_HARBOR_AUTO_REVIEW`) leaves a build in `ai_review_queued` with no admin email; the loop that consumed that state is not in this repository, and the repository does not record which production builds were reviewed by a person.
- A reviewed build that is not a Harbor build (queued by the operator or the coordinator, or from the legacy intake) can be taken live by its owner without payment; nothing in this application charges for those ([builds.ts](../web/src/routes/builds.ts)).
- Harbor origin is recorded per build from the moment the `is_harbor` column exists. The backfill for older rows reads the `handoff_build_id` stamps and `parent_build_id` links that are still there ([schema.sql](../web/src/db/schema.sql)); a build whose Harbor ancestor had already been deleted is not marked, and its owner can take it live without a subscription once it is approved.
- One subscription covers every Harbor build on the account: the gate asks whether the build's owner has a subscription, not which website it was bought for ([builds.ts](../web/src/routes/builds.ts)).
- Under the default v2 engine a revision does not change the site. The revision routes queue a new build that carries the same spec plus the customer's text and the reviewer's notes in `builds.rebuild_request`, and only the v1 engine reads that column ([builds.ts](../web/src/routes/builds.ts), [worker_pg.py](../queue/worker_pg.py)).
- The review page reads at most 400 warning entries of a build's latest lint run and says so when it reaches that number. The worker's lint reads at most 256 KiB of the manifest; `translation-warnings.txt` in the artifact holds the same warning lines, so a line past that point is there. Spec notes past the engine's 40 are counted in `spec_warnings_omitted` and written nowhere ([admin.ts](../web/src/routes/admin.ts), [worker_pg.py](../queue/worker_pg.py)).
- The latest lint run is recognised by the worker's start-of-lint log entry ("Running v2 build-output lint"); a build whose log has none gets every warning entry it has, from all attempts, with exact repeats shown once.
- The build's owner is sent the warning lines by the log API (`GET /api/builds/:buildId/logs`; they describe the owner's own site and their own spec text), and only the status page's activity card hides them. The build detail page and the review page's log tail show them raw, and a packed entry appears there as one long line.
- Build-log entries, which can include text copied from the spec, go to a model in two places: the admin's "analyze build failure" request (`POST /admin/builds/:buildId/analyze`) sends the build's error, its newest 50 log entries, the QA failures and the design issues (at most 4,000, 24,000, 8,000 and 8,000 characters), and the coordinator's failure triage sends the last 500 characters of the log. Both fence the text as data, with every `<` replaced so the block cannot be closed and a notice that it is data (`wrapUntrustedBuildText` in [claude.ts](../web/src/services/claude.ts), `wrap_untrusted` in [build_failure_categorizer.py](../coordinator/build_failure_categorizer.py)). That is a mitigation, not a guarantee. The admin's analysis is advice shown to the admin: the build page shows its fix summary, escaped, above the Queue Fix form, whose description starts empty, and nothing reaches the pipeline unless the admin writes a description and submits it ([admin-build-detail.ejs](../web/views/admin-build-detail.ejs)).

## Authentication and sessions

- A raster logo at the pixel limit costs one decode on the web process's shared thread pool (measured up to about a tenth of a second and about 100 MB). The palette read from an SVG counts mentions of a color, not drawn area, and does not see colors inside an embedded raster image ([logo.ts](../web/src/services/logo.ts)).
- A CSRF token has no expiry of its own: it is good for as long as the session it was issued in. A token minted with no session id, which only test code does, is accepted from any session ([auth.ts](../web/src/middleware/auth.ts), `generateCsrfToken`, `verifyToken`).
- Rendering a page stores a session, and sets its cookie, for a visitor who has none, so that the page's CSRF token has a session to belong to (`keepSessionForRenderedPage` in [auth.ts](../web/src/middleware/auth.ts)). A client that keeps no cookies adds a `user_sessions` row with every page it fetches; the rows expire after 24 idle hours.
- Outside development and test the session and conversation cookies are named `__Host-cas.sid` and `__Host-cas_harbor_trial` (`hostOnlyCookieName`); a cookie under the bare name is not read there, so a deployment that ran under the bare names loses its open sessions and conversation cookies when it moves to this code.
- The origin guard compares `Origin` with `Host` when `Sec-Fetch-Site` is absent, so a proxy that rewrites `Host` breaks POSTs from browsers that do not send `Sec-Fetch-Site`. Requests with neither header pass by design.
- Without `BASE_URL`, emailed verification and reset links and the Stripe return address of the make-public page use the request `Host` if it looks like a plain host, and `localhost` otherwise (`publicBaseUrl` in [auth.ts](../web/src/routes/auth.ts), which [lighthouse.ts](../web/src/routes/lighthouse.ts) also calls). Their scheme is `https` when `req.protocol` is exactly `https` and `http` otherwise; under `trust proxy` that is the client's `X-Forwarded-Proto` unless a proxy in front overwrites it, so such a client chooses between the two schemes and no other. The other emails link to the product's original domain; the boot warning is printed unless `NODE_ENV` is exactly `development` or `test` (an unset value and `staging` included). A `BASE_URL` that does not match that pattern (a scheme, a plain host and an optional port, with nothing after them) is ignored in the same way: the request's `Host` is used instead if it looks like a plain host, and the boot check looks only at whether the value is empty.
- Rate limits and the model-call budget are in process memory: per instance, reset on restart. Every limiter holds at most 20,000 keys and forgets the oldest window first when full, so a flood of distinct addresses loosens the limit for the clients it displaces and never refuses anyone. With `TRUST_PROXY_HOPS` unset the app trusts one proxy hop and warns at boot; started that way with nothing in front, it believes any X-Forwarded-For that is a valid address, and every per-address limit can be walked past by rotating it (text that is not an address shares one bucket). `web/.env.example` sets 0.
- Page views are recorded at most 30 a minute per client address and 600 a minute overall, counted in process memory; past a cap the page is served and the view is not recorded, so `page_views` undercounts during a flood ([app.ts](../web/src/app.ts)). A view keeps the Referer as a path only, with no query string or fragment.
- Admin is one email with no MFA. There is no general audit log: admin actions are console log lines (review and approval decisions also stamp `reviewed_by` and `resolved_by` on their rows), and the typed confirmation on admin delete (`data-confirm-typed` in [admin-build-detail.ejs](../web/views/admin-build-detail.ejs)) is checked only in the browser.
- `OPS_API_KEY` is a static bearer key with admin-equivalent power over the queue ([ops-api.ts](../web/src/routes/ops-api.ts)).
- Opening a verification or unsubscribe link shows a page whose button acts (`POST /verify-email` and `POST /unsubscribe` in [auth.ts](../web/src/routes/auth.ts)), so a mail scanner that only fetches a link spends nothing; one that also submits the page's form would. A verification link confirmed in a browser other than the one that typed the account's password still verifies the account, replaces the stored password with an unusable one, sets the name to the address's local part and asks for a new password. Unsubscribe tokens are a deterministic HMAC of the address and never expire.
- At most one verification link is issued to an address per hour, whoever asks (`ISSUE_VERIFICATION_TOKEN_SQL` in [auth.ts](../web/src/routes/auth.ts)); earlier links stay valid. The limit reads the token table as it was when the statement started, so requests that arrive at the same moment can each send one.
- A signup for an address that already has an unverified account writes nothing to that row, so an owner who signs up a second time with a different password cannot log in with it elsewhere until a link is confirmed in the browser where they signed up; the row keeps the first password until then.
- An intake draft attached by the signup that created an unverified account stays on that account after a later claim settles it at verification ([auth.ts](../web/src/routes/auth.ts)).
- Account deletion keeps the account's build rows with the customer link removed, including `builds.spec` (which can hold the address as `admin_email`) and the build logs; the `email_log` and `newsletter_subscribers` rows keyed by the address stay, and so do the `page_views` rows (without the account identifier, and with the referrer as a path, no query string or fragment); the deployed app, its database and its Railway project are not touched ([auth.ts](../web/src/routes/auth.ts), `ACCOUNT_DELETION_LEAVES`). The privacy page says so. It asks Stripe to cancel the account's subscriptions at period end before its transaction opens (so billing runs to the end of the paid period), marks the account's queued builds failed, and keeps the Stripe subscription ids for 90 days in `harbor_subscription_tombstones` so that later events are acknowledged. It also deletes the account's Haven trials (a trial stamped with one of the account's builds, or carrying the account's address unless another account's build is stamped on it; the turns and notes cascade, and the address is cleared from any other trial row), locking the builds, then those trials, then the customer row. A build of that account that was already in flight keeps running; if it is later requeued it is never claimed, because the claim joins the customer row (`_claim_next_job` in [worker_pg.py](../queue/worker_pg.py)), and nothing sweeps such rows. The data export (`GET /export-data` in [builds.ts](../web/src/routes/builds.ts)) covers the account, builds, intake messages and feature requests; it omits Haven conversations and memory, `email_log` and subscription records.
- Passwords are 8 to 72 bytes with no breach check.
- `POST /forgot-password` still does more work for a registered address than for an unknown one: both run one statement and send the mail after the response, but the statement inserts a token only for an account, about 0.2 ms of server time measured locally (a remote database was not measured), and no test bounds the timing ([auth.ts](../web/src/routes/auth.ts), `ISSUE_PASSWORD_RESET_TOKEN_SQL`).
- Accounts whose placeholder password was hashed at cost 10 before the cost was unified keep that hash until their password is reset (login does not rehash), so a wrong-password login against such an account is still measurably faster than against others ([password-hash.ts](../web/src/utils/password-hash.ts)).
- `requireAuth` and `requireAdmin` answer a logged-out script with a redirect to the login page, not JSON. A 400 or 413 raised by the body parsers for a form is rendered without the site layout, because the layout middleware is installed after the parsers.
- The web app reaches a remote Postgres over TLS without certificate verification unless `NODE_ENV` is exactly `development` or `test` (an unset value and `staging` get TLS), and without TLS in those two, unless the URL sets `sslmode` ([db/tls.ts](../web/src/db/tls.ts)).
- `style-src` keeps `'unsafe-inline'`; the Plausible script and Google Fonts load without Subresource Integrity. `/health` is public and reports version, commit, worker heartbeat, memory and pool counts ([app.ts](../web/src/app.ts)). Recipient addresses and subjects appear in logs ([email.ts](../web/src/services/email.ts)). Several customer routes pass a path id to Postgres without a UUID check, so a malformed id can surface as the generic error page rather than a 404 ([builds.ts](../web/src/routes/builds.ts)).

## Harbor companion

- The trial cookie is an opaque bearer token stored unhashed in `trial_keepers.cookie_token`; a database read exposes live trial sessions ([trial-cookie.ts](../web/src/middleware/trial-cookie.ts)). Its value is replaced at two steps only: when the trial's first address is recorded (`rotateTrialCookie`, called from [lighthouse.ts](../web/src/routes/lighthouse.ts)), and on the first request that presents the trial after a payment released it (`resolveTrial`, `trial_keepers.cookie_rotated_at`). It is not replaced at the dispatch. A request sent with the old value after a replacement gets a fresh trial in its place.
- After paying, a trial visitor owns the website they paid for through that cookie, in that browser only, for 30 days from payment (`loadPaidKeeper` in [trial-cookie.ts](../web/src/middleware/trial-cookie.ts), `PAID_TRIAL_ACCESS_DAYS` in [keeper_promotion.ts](../web/src/services/keeper_promotion.ts)). The webhook that releases the trial cannot set a cookie, so the value is replaced on the paying browser's next request instead. The account itself is entered by requesting a password reset for the paying address; completing the reset also verifies the account. Cancelling the subscription takes a login to the account: the paying cookie alone is shown a page that says to log in or to choose a password (`POST /lighthouse/lamp/:buildId/cancel-subscription` in [lighthouse.ts](../web/src/routes/lighthouse.ts)). The cookie also stops speaking for the account when its browser logs in to another account (that browser then gets a fresh trial), when that browser logs out (the cookie is cleared), and when a password reset or email verification completes for the account it was promoted into (`expirePromotedTrialCookies`, [trial-cookie.ts](../web/src/middleware/trial-cookie.ts)). A copy of the cookie taken after that replacement keeps speaking for its account until its 30 days end or the account's password is reset or its mailbox verified (logout clears the cookie in the browser that holds it, but does not expire the trial row); a copy taken before the payment does not.
- When an account's owner, logged in, pays for a build whose stamped trial is another person's conversation (a preview a stranger's dispatch made for the address before the owner claimed the account), that trial is promoted into the account and its cookie becomes the account's paying cookie until its 30 days end or the account's password is next reset ([keeper_promotion.ts](../web/src/services/keeper_promotion.ts), `PROMOTED_KEEPER_OF_TRIAL_SQL`).
- A browser that paid under code from before `trial_keepers.promoted_customer_id` existed holds a released trial with that column empty; its cookie is treated as stale and gets a fresh trial, and the account is reached through its mailbox. A deployment that never ran the earlier code is unaffected ([keeper_promotion.ts](../web/src/services/keeper_promotion.ts), `PROMOTED_KEEPER_OF_TRIAL_SQL`).
- A free preview is tied to an email nobody verified. An anonymous dispatch, the visitor's or the operator's of a captured address (`dispatchHarborTrialBuild` in [harbor_dispatch.ts](../web/src/services/harbor_dispatch.ts), `POST /admin/harbor/:trial_id/dispatch` in [admin.ts](../web/src/routes/admin.ts)), attaches its build only to a customers row it creates in the transaction that inserts the build, and refuses an address that already has any account (`account_exists` when it is verified, `address_in_use` otherwise; the visitor sees `email_not_usable` for both). The account it creates belongs to the address: whoever later proves that mailbox owns it with the build, and with the keeper row, the subscription and the conversation if the visitor paid first. A trial's payment is promoted only into the account its own dispatch created (`builds.owner_created_by_dispatch`) or the payment itself created, unless the account's login or paying cookie opened the Checkout session, and no keeper row is written on a verified account for a session that no login of it opened (`promoteTrialInTransaction` in [keeper_promotion.ts](../web/src/services/keeper_promotion.ts), `handleHarborMakePublic` in [webhooks.ts](../web/src/routes/webhooks.ts)).
- A build dispatched before `builds.owner_created_by_dispatch` existed carries FALSE: a payment for it that a trial cookie opened is refused, recorded, mailed and listed as the refusals below are, and the make-public page does not refuse it before Checkout ([schema.sql](../web/src/db/schema.sql)).
- The operator's dispatch of a captured address counts against the anonymous share of the daily model-call budget, as the visitor's does ([admin.ts](../web/src/routes/admin.ts)).
- Cost caps count Haven conversation turns only; the memory classifier, embeddings and spec extraction are excluded ([memory_capture.ts](../web/src/companion/memory_capture.ts)), and the cap query fails open on a database error. The caps bound one cookie, not one person; the per-address limits bound cookie rotation.
- The shared cap means a flood can stop model-backed turns for everyone until older turns leave the 24-hour window (the crisis script still answers). That was chosen over an open-ended bill.
- The sacred-memory filter is a model classification, best effort; nothing else enforces the partition.
- A keeper talks as the keeper with an account session or with the cookie that paid: turns, notes and template choices are read and written by keeper id (`resolveCompanionIdentity` in [lighthouse.ts](../web/src/routes/lighthouse.ts)). The exception is a crisis message from a keeper who is logged in on a browser that did not make the payment: it gets the same reply, but its stored copy is filed under that browser's own trial (or not stored, if the browser has no cookie), because the crisis handler runs ahead of the session middleware (`fileCrisisTurn`).
- No transaction surrounds a companion turn; a persist failure after the model call is a paid retry ([runtime.ts](../web/src/companion/runtime.ts)).
- Each weekly sweep runs when a week has passed since its last claimed run, recorded in a `platform_metadata` row (`claimSweepRun` in [harbor-cron-scheduler.ts](../web/src/services/harbor-cron-scheduler.ts)); a restart does not rerun it and one replica gets the claim. The claim is taken before the sweep runs, so a sweep that fails or is interrupted is not retried until the next interval. The check runs 60 seconds after boot and then hourly, and if the claim cannot be read or written the sweep does not run.
- `support_kb` rows written by the topic sweep and by the coordinator are model-drafted from visitor text and stored as `pending`; the support chat serves only `approved` rows (`findKnowledgeBaseAnswer` in [support.ts](../web/src/routes/support.ts)). There is no admin page for approval: an operator reads the pending rows and runs the `UPDATE` written next to the column in [schema.sql](../web/src/db/schema.sql). Rows that existed when the column was added were marked `approved` and are served without that review. The sweep's filter reads shapes (URLs, `www.` hosts, host names other than the product's domain, IPv4 addresses, tags, email addresses, runs of seven or more digits), so an address spelled out in words passes it, and a year range such as "2025-2026" is refused as a phone number; the approval is the control ([topic_kb_sweep.ts](../web/src/cron/topic_kb_sweep.ts)). The coordinator's own gap detection reads rows of any status, so a pending row counts as answered there.
- The crisis scan is about 160 English regular expressions over normalized text ([crisis_detection.ts](../web/src/companion/crisis_detection.ts)); it is not a clinical safeguard. It was measured on phrasings not derived from its patterns, all written by a language model given only the product context, none taken from real conversations. Forty plainly worded disclosures and thirty harmless messages, written after the patterns were final and never used to change one: 39 of 40 flagged and 0 of 30 (the `blind` split of [crisis_corpus.fixture.json](../web/tests/unit/companion/crisis_corpus.fixture.json), recomputed by [crisis_corpus.test.ts](../web/tests/unit/companion/crisis_corpus.test.ts); the scan it replaced: 20 of 40 and 8 of 30). Two earlier sets, each scored once before the patterns were extended with what it showed: 54 of 68 (79%), and 55 of 79 (70%) for a set written to be indirect or buried in business talk, with 1 of 70 and 4 of 80 harmless messages flagged (the replaced scan: 15 of 68 and 19 of 79). So plain wording is caught almost always, and wording that is indirect or buried in other talk about seven times in ten. The scan's 339 of 344 and 5 of 346 on the other three splits of the fixture (the 197 and 196 messages written while the patterns were rewritten, and the two earlier sets after the patterns were extended with them) are in-sample and not an estimate.
- The scan is known to miss a plan that is never named and carries a single cue ("i know how im going to do it", "i decided on the date. its friday.", "I've picked the bridge"), a threat worded as exasperation ("I could actually hurt him"), "I am planning to hurt a coworker badly", anything not in English, and spellings built to dodge a filter beyond the few it folds. A missed message goes on to the rate limiters, the email gate and the cost caps like any other. No clinician has reviewed the patterns or the reply text, including the lines added for a medical emergency and for a threat to another person.
- The scan deliberately does not flag a practitioner describing their work (a phrase such as "people who", "I refer" or "beyond my scope" before the match; for bare topic words also a professional-context phrase such as "workshop on", "survivors of" or "clients with") or a direct denial ("I would never", "I am not"). A disclosure with one of those phrases before it in the same sentence, and no "I", "me", "my" or clause break between, is missed. Known false positives are figurative lines that are word for word a disclosure, quoted speech, "hurt me" said of feelings, and "I don't want to be here anymore" said of a place; each costs one scripted reply. At the route the scan reads the first 20,000 characters of a message, weighs context for at most 24 matches (a later match is treated as a hit) and looks 400 characters to either side of a match. The honesty rail ([ai_honesty_rail.ts](../web/src/companion/ai_honesty_rail.ts)) is also a list of regular expressions and misses phrasings it was not written for.
- The crisis reply comes before the trial-cookie lookup, the rate limiters, the email gate and the cost caps, but after the optional `PREVIEW_PASSWORD` gate and the body parsers: a body over 1 MB or malformed JSON is refused there. A sender with no usable trial cookie gets the script but the turn is not stored, and all such senders share one identity for the alert bound. Past the alert and stored-turn bounds a crisis is recorded in the server log only, and those counters are in process memory. Stored crisis turns are also capped at 60 per process per one-minute window across all identities (`CRISIS_PERSIST_MAX_PER_MINUTE`, [runtime.ts](../web/src/companion/runtime.ts)); a crisis past that cap gets the fixed reply and is logged, not stored, and the caps are per process.
- The build-start limits are per customer, and on the self-serve path the customer is the address the visitor typed ([build-start-limits.ts](../web/src/services/build-start-limits.ts), [harbor_dispatch.ts](../web/src/services/harbor_dispatch.ts)): a visitor who gives a different address each time is not bounded by them, only by 6 attempts an hour per trial and 24 per address and by the anonymous share of the model-call budget.
- `POST /lighthouse/build` starts no build for a typed address that already has an account, verified or not. The refusal costs no model call (unless the account appears while the extraction runs) and does not say why, but an address that would have been accepted gets a build, so a visitor with a build-ready conversation can tell whether an address has an account, at the rate the build limiters allow (6 attempts an hour per trial, 24 per address) ([lighthouse.ts](../web/src/routes/lighthouse.ts)).
- Account deletion leaves a Haven trial that is tied to the account by neither a build nor a captured address (for example a conversation in another browser that never asked for a build); nothing purges trial rows. `funnel_events` keeps the deleted trials' ids (event name, path, referrer and a hashed user agent; no text and no address), and a `newsletter_subscribers` row with the same address is not removed ([auth.ts](../web/src/routes/auth.ts)).
- The admin Harbor inbox lists unreleased trials by default. A paid keeper's conversation appears under its "Paid keepers" filter (`?status=keepers`) as counts, opening words and the time of the last turn; reading the turns is a SQL lookup by keeper id, and the development `dev_trial` links exist for trials only ([admin.ts](../web/src/routes/admin.ts)).
- A keeper's own build request and their account deletion, sent at the same instant, can deadlock on the keeper and customer rows; Postgres aborts one of them and nothing is half-written ([harbor_dispatch.ts](../web/src/services/harbor_dispatch.ts), [auth.ts](../web/src/routes/auth.ts)).
- A trial's website is attached to the address typed in the conversation, which nobody verified. Before Checkout the make-public page shows that address and the visitor must confirm it; a request that names a different address is refused, and a visitor who confirms a mistyped address pays into an account that whoever reads that mailbox can enter.
- A form page whose model is shown to visitors is built without its form when the web translator cannot tell that a submitted row could be held back: the model has no field list of its own, or its `published` field is not a boolean ([harbor_to_compose.ts](../web/src/services/harbor_to_compose.ts), `holdPublicFormRowsBack`). The page is kept and the translation warning says why. For a form page it keeps, the translator names the columns a visitor may fill in (the model's own fields less the engine's reserved columns and the password and image fields, `nameVisitorFields`), and a page whose model has none left to offer loses its form.
- A conversation held without an account is never deleted on a schedule; it outlives its cookie. The privacy page says so.
- The build engine accepts only a plain address as a site's admin address (letters, digits and `. _ % + -` before the `@`; letters, digits and hyphens in each part after it; ASCII only; `_ADMIN_EMAIL_RE` in [build.py](../compose/build.py)), and the worker writes the owning account's email there. Signup ([auth.ts](../web/src/routes/auth.ts)) and the conversation's email field accept more. An account under such an address cannot get a website: the Harbor dispatch refuses it before any model call, the conversation page tells a logged-in owner so, and no route changes an account's address. A visitor who typed such an address is told only that it could not be used, in the same words as for an address that has an account, and can give another; the conversation's email gate still accepts it. The retry, rebuild and revision routes, the ops API and the coordinator's automatic rebuild do not make the check: for such an account they queue a build that the engine refuses at validation.

## Payments and product gaps

- A payment that completes while its build is not at `preview` and `approved`, or for a build another session already paid for, is recorded in `harbor_subscriptions` (when the build has a customer, and is then listed on `/admin/harbor` under "Payments needing a person"), logged as an error and mailed to the operator; nothing publishes the site or refunds the charge. No keeper row is written for it, so the publish gate does not see that subscription and the payer is asked to subscribe again once the build is approved. A paid session whose build row is gone, or whose build has no customer while the session has no email, is logged and mailed to the operator and recorded nowhere (`handleHarborMakePublic` in [webhooks.ts](../web/src/routes/webhooks.ts)).
- A paid Checkout session that the webhook refuses to apply (the account's keeper already has a subscription that still publishes, or a trial's session names an account whose keeper already has any subscription, or the session names a trial that is not the one stamped on its build, or a session that no login of the account opened names a verified account, or a trial's session names an account its dispatch did not create) is recorded in `harbor_subscriptions`, mailed to the operator and listed on `/admin/harbor` under "Payments needing a person" until Stripe reports the subscription ended (`PAYMENTS_NEEDING_A_PERSON_SQL` in [admin.ts](../web/src/routes/admin.ts)), and nothing more happens: the money is not refunded, the website stays in preview, and the account's owner cannot cancel that second subscription from the lamp page (the page manages the keeper's own subscription); a person refunds or cancels it in Stripe, and deleting the account cancels it at period end ([keeper_promotion.ts](../web/src/services/keeper_promotion.ts), [webhooks.ts](../web/src/routes/webhooks.ts)).
- A keeper whose subscription has ended and who pays again for a website that has a trial stamped on it takes the new subscription, but that trial's conversation is not merged into the keeper's.
- A subscription event for a subscription with no local row and no tombstone is refused for 72 hours and then dropped. Subscription events created in the same second are applied in arrival order. The "website is public" email is sent after the commit and is lost if the process dies in between.
- A subscription that ends or goes unpaid changes `harbor_subscriptions` and the keeper row only: the owner can no longer publish a new build or download the source of an unpublished one, and builds that are already `live` stay `live`. `past_due` counts as subscribed for as long as Stripe reports it, and how long that is depends on the Stripe account's retry settings. A keeper whose subscription is `unpaid` can open a new Checkout; the unpaid subscription stays open at Stripe.
- The keeper row mirrors one subscription. A keeper pointed at a newer subscription that ends while an older one is still active is treated as unsubscribed; the mirror fails closed ([webhooks.ts](../web/src/routes/webhooks.ts)).
- A conversation dispatches one build without an operator (`handoff_at` on the trial or keeper row, which outlives the build). An operator can dispatch again for a trial whose build was deleted; there is no operator dispatch for a keeper ([harbor_dispatch.ts](../web/src/services/harbor_dispatch.ts)).
- The cleanup routes delete build rows and no Railway project, so a deleted row's project keeps running and is then recorded on no build row. The admin route ([admin.ts](../web/src/routes/admin.ts)) removes builds beyond the two newest of an app for each customer, and any failed build older than seven days, in any status except queued, in flight or preview (an older `live` build included), and names their projects in one log line. The ops route ([ops-api.ts](../web/src/routes/ops-api.ts)) removes every build of a named app but each customer's newest, whatever its status. Both detach the children of what they delete.
- The admin build delete reads the Railway project's name before it deletes the project, and keeps the project and the row (502) unless the name matches the build's app name after lowercasing and turning each run of other characters into one hyphen. A project Railway no longer has cannot be named, so a build whose project was deleted outside CAS keeps its row and must be cleared another way. A name that the build's translator prefixes (`site-` for a name that starts with a digit or with the reserved `craftandship`, `harbor-` when there is no usable name) does not match and is kept the same way ([admin.ts](../web/src/routes/admin.ts), `railwayProjectNameKey`).
- The feature-request subsystem has no payment path and no worker that builds its requests; only the bypass queues one. Its UI entry points were removed and the code remains ([features.ts](../web/src/routes/features.ts)).
- When Harbor is disabled (`CAS_HARBOR_ENABLED` unset or false), `/try` and `/intake` collect a spec and start no build. When it is enabled, the pages `GET /try` and `GET /intake` redirect to the Haven conversation and the anonymous `POST /try/...` routes answer 404, but a logged-in customer's `POST /intake/start`, `POST /intake/message` and `POST /intake/:buildId/logo` still answer; the first two draw on the customer's daily model-call limit and the process budget ([intake.ts](../web/src/routes/intake.ts)).
- Revision confirm has no idempotency key. `sendEmail` records a failed Resend call and does not retry it ([email.ts](../web/src/services/email.ts)). The contact form's call to Resend times out after 15 seconds (`CONTACT_SEND_TIMEOUT_MS` in [app.ts](../web/src/app.ts)) and is not retried.
- The privacy page and the terms page ([privacy.ejs](../web/views/privacy.ejs), [terms.ejs](../web/views/terms.ejs)) were rewritten during review to state what the code does (the cookies and their lifetimes, what is stored, what account deletion removes and leaves, who receives data, what a preview is); neither has had legal review, and the effective date printed on both was not changed. Their promises about response times ("within 30 days") are not code facts. Some marketing claims in the nurture emails and [docs-research.ejs](../web/views/docs-research.ejs) were not verified. The pricing FAQ says the subscription pauses the day the customer asks and offers to write in for a pause ([pricing-faq.ts](../web/src/services/pricing-faq.ts)); nothing in the code pauses a subscription, and the only subscription action the site offers is cancel at period end. Unsubscribing stops every email except verification and password reset, build notices included.

## Build worker

- The attempt token (`builds.started_at`) guards the status writes and the Railway columns. The other writes of a build thread (`build_logs` rows, screenshots, the stored artifact, cost) are keyed by build id only, so a thread left over from an earlier attempt can still write those until its next stage write stops it ([worker_pg.py](../queue/worker_pg.py)).
- The build lease is best effort: if the advisory lock cannot be taken, or its connection drops mid-build, the build keeps running unleased, and a second worker process would requeue it as an orphan once it is older than 30 seconds; only the in-process set `_OWN_ATTEMPTS` (build id and attempt) still protects it. A pipeline thread the supervisor gave up on is never killed; it ends when the call it is blocked in returns.
- Cooperative cancellation reaches only the v1 fix loops and model calls, which poll the attempt's cancel event at their checkpoints. A thread blocked in the Railway CLI, a socket read or Chromium is not interrupted, and the v2 pipeline has no checkpoints.
- A build requeued in place keeps its stored artifact when it has one, so the worker resumes it from the test stage and redeploys the same files without rebuilding; a `rebuild_request` set on such a row (the admin AI-fix reset of a failed build) is not applied.
- The stage-resume marker is a string in `builds.error_message` shared by the web app and the worker by convention; the worker accepts only the exact values `Requeued: resuming from <testing|deploying> stage` and `Recovered: resuming from <testing|deploying> stage` (`_parse_resume_marker`).
- Retries have no backoff beyond the 10-second poll, and Railway GraphQL calls back off only where a resend is safe: `gql()` retries queries and repeatable mutations (a variable upsert, the redeploy of a fresh database service), and sends any other mutation again only after a 429 or a connection that was never established; otherwise it raises `RailwayOutcomeUnknown` ([deploy.py](../cli/deploy.py)). The 2-hour retry budget is a clock kept in each worker's memory, so a restart or a second worker starts it again; `_MAX_RETRIES` is the hard bound.
- A bare number 429, 502 or 503 elsewhere in an error message (for example `line 429`) still reads as a transient status code ([worker_pg.py](../queue/worker_pg.py), `_TRANSIENT_STATUS_RE`).
- If Railway applies a `projectCreate` whose answer is lost, the attempt fails; the project it may have created is named in the build's log when it can be listed, and is neither deleted nor recorded.
- A v2 deployment that Railway reports as SUCCESS and that never answers `/health` as healthy is still treated as a deterministic failure; one that Railway reports as FAILED gets one more attempt.
- An attempt's Railway project is tracked in the worker's memory until the build reaches preview. If the worker is killed after `deploy()` created a project and before the preview write, no build row names that project; it keeps running until an operator or the opt-in orphan sweep removes it.
- An abandoned attempt's thread that cannot open a database connection within about 48 seconds leaves the project it created running, with its id in the worker log; nothing retries ([worker_pg.py](../queue/worker_pg.py), `_discard_after_abandonment`).
- When a build that was in preview is requeued in place and deploys again, the earlier deployment's Railway project is no longer referenced by any build row. The worker does not delete it; it is named once in a warning in the worker log, keeps running and stays in the monitor registry until an operator removes it.
- The janitor does not delete a failed or abandoned build that records a Railway project; such rows and their projects stay until an operator deletes them.
- A Railway delete that fails leaves the project running: the worker logs the project id with "NOT deleted" and nothing retries the delete. Per-deploy project tokens are never revoked ([deploy.py](../cli/deploy.py)).
- The opt-in orphan sweep deletes any project in the Railway account that no build row records and that is older than four hours. That includes a preview that a later deployment of the same build superseded, a project whose build row a cleanup route deleted, and any project the database never knew.
- The opt-in orphan sweep reads one page of at most 50 Railway projects and does not page, so a project outside that page is never considered and never deleted.
- `drainingSeconds` is 60, far shorter than a build; v2 lint failures are logged but do not fail a build, so whoever reviews must read them.
- The daily spend cap sums `builds.total_api_cost_usd` over builds whose current attempt started today or that were requeued today. It is 0 under the v2 engine, so the cap never triggers there. Under v1 it is checked at claim time only (attempts in flight finish), counts a retried build's earlier days in full, misses an attempt that spans midnight, and loses the cost of a failed build when the janitor deletes its row.
- The zombie-deploy probe matches Railway projects by app name. It excludes every project a build row records and the fresh projects of other attempts in the same worker process; a same-named build in another worker process whose project is not on a row yet can still be confused ([watchdog_probe.py](../queue/watchdog_probe.py)).
- After a healthy `/health` the login probe uses up one of the two seeded tokens. A v1 app that only implements `GET /magic?token=` is reported as "login link verification failed", a warning in the build log, not a failure.
- The worker writes two login tokens into the app's `db/seed.sql` when its login-token stage runs for a build. Each row expires 24 hours after the seed inserts it, not after the email is sent; the seed runs only when the app's `users` table is empty, and nothing in the worker deletes or revokes a token it has written ([worker_pg.py](../queue/worker_pg.py), `_inject_magic_link_token`).
- `provision_postgres` in [deploy.py](../cli/deploy.py) creates each customer database as a `postgres:15` image service with `PGDATA` set and never creates or attaches a Railway volume; whether that data survives a restart or redeploy depends on how Railway treats a service without a volume, which this repository does not establish.
- `builds.railway_database_url` keeps each app's database URL with its credentials masked (`postgresql://***@host:port/db`, written by `_set_preview_status` in [worker_pg.py](../queue/worker_pg.py)); the password stays with Railway, in the app's `DATABASE_URL` variable, and an operator who needs it reads it there. Whether Railway's variables query answers at every point after a deploy is not shown by this repository. The operator mailbox is BCC'd on three customer emails (`app_live`, `preview_ready`, `build_failed`) when `ADMIN_EMAIL` is set, and two of them can carry the login link ([mailer.py](../queue/mailer.py)).
- `deploy()` sets the app's `SITE_ORIGIN` only once the first deployment is running, because the Railway domain exists only then ([deploy.py](../cli/deploy.py)). The site reads it from the next deployment of the service, which Railway starts for a variable change by default (not verified from this repository); until then a site whose spec stored no `site_url` emails no login link and sends form notifications without the admin link.
- A generated site ends the account's other sessions when its password changes (`endOtherSessions`), but a request of another session that is in flight at that moment can write that session's row back, because connect-pg-simple saves by upsert.
- One Railway account token covers all customer projects, and one optional mail key covers all generated apps. The check that refuses to hand the platform `RESEND_API_KEY` to a customer app compares two environment values; it cannot tell whether a different key belongs to the same Resend account.
- Redaction is pattern based: the credentials of a URL are removed by one rule shared by the worker, `cli/deploy.py` and the failure knowledge base ([url_redaction.py](../monitor/url_redaction.py)), and tokens and keys by pattern lists of their own ([worker_pg.py](../queue/worker_pg.py), [failure_kb.py](../cli/failure_kb.py)); a credential in an unusual shape can pass through.
- The review browser cannot be pinned: its guard resolves a name (`host_resolution_problem`) and Chromium resolves it again, so a DNS answer that changes in between is not caught, and WebSocket and WebRTC traffic does not pass the guard ([ping.py](../monitor/ping.py), [deploy.py](../cli/deploy.py)). The pinned session of the `requests`-based probes is tested over http and over https against a local TLS listener (`TestHttpsIsPinnedAndBounded` in [test_bounded_fetch.py](../tests/test_bounded_fetch.py)); no probe has been run against a real external host.
- The link lint's time budget does not cover the DNS lookup, and a TLS handshake or request send already in flight runs to its own 5-second timeout ([lint_external_urls.py](../compose/lint_external_urls.py)).
- A generated site's `/health` checks its home page once, when the site starts, and remembers a pass: any other page, any POST and a home page that breaks later are not noticed ([compose/build.py](../compose/build.py), `services/health.js`).
- The engine refuses a seed value or a column default that Postgres would refuse, and a few that Postgres takes: dates and times written in any form but ISO, a date in front of a time, arrays of more than one dimension, and a timestamp longer than 64 characters (`_STORED_TIMESTAMP_MAX_CHARS`); a seed row with such a value is left out and reported as `seed_value_unfit`, a default is left off and reported as `column_default_ignored` ([compose/build.py](../compose/build.py), `_stored_value_problem`). A seed row that lacks a field the spec declares required is dropped with a `seed_shape_mismatch` warning instead.
- The wrong-type matrix ([test_spec_shape_matrix.py](../compose/tests/test_spec_shape_matrix.py)) changes one position of a spec at a time and, in its main mode, renders each site with one stand-in row per table and runs no SQL, so what a spec's own seed rows do to a page that reads them is not rendered; POST handlers are parsed, not called; and the default run takes a sample of the cases.
- A visitor can sort a public list only by a column that list prints in full (`_PUBLIC_LIST_COLUMNS`); a view that prints more has no extra sort column.
- The stock-photo check finds references of the form `/images/stock/<file>` only; a personal photo reached through any other URL is not detected.
- A build report that says `external_url_lint: skipped` means no URL was checked. The worker copies warning lines, not this header, into the build log.
- The real-database column tests and the Postgres mode of the wrong-type matrix skip without a reachable local PostgreSQL.
- The number of engine warning lines in `compose-manifest.txt` is bounded by the size limits on the spec, not by a constant of its own.
- The link lint still tells a reader of the build log that a name resolves to a non-public address, though not which one ([lint_external_urls.py](../compose/lint_external_urls.py)).
- A key in a page's data that its widget does not declare is left out of the page without a warning (`_spec_widget_data` in [compose/build.py](../compose/build.py)).
- A `spec.json` may hold NaN or Infinity: `json.load` reads them, a scalar field accepts them, and a non-finite seed value is written as NULL ([build.py](../compose/build.py), `_kind_problem`, `_seed_literal`).
- The sitemap line of a generated site's `robots.txt` takes its origin from the admin's `site_url` setting as typed (trailing slashes removed, nothing checked), or from the request's `Host` header when that setting is blank (`siteOrigin` in the emitted `routes/seo.js`).

Environments are scrubbed and QA runs in a child process ([qa_runner.py](../cli/qa_runner.py)), but nothing is sandboxed ([test.py](../cli/test.py), [qa.py](../cli/qa.py)).

## Coordinator, monitor and backups

- Approval requests are advisory: nothing executes an approved request, and unanswered ones are rejected on timeout. Only an agent's escalation and the reconciliation agent file one.
- Most coordinator agents are rule-based Python. No agent reports token usage, so a task is recorded at its estimate, and the model-call meter counts calls at fixed per-model estimates ($0.05 on the cheap tier, $0.12 and $0.80 above it), not tokens: it bounds how many calls a tick makes, not the bill ([tick.py](../coordinator/tick.py), [scorer.py](../coordinator/scorer.py)).
- A task that makes no model call is still booked in the cost ledger at its estimated model cost (`_dispatch_agent` in [tick.py](../coordinator/tick.py)), so it counts against the ledger the budget reads when no `ANTHROPIC_ADMIN_KEY` is set.
- `query_readonly` runs in a read-only transaction, which does not confine a function that acts outside its connection (dblink and the like); the platform's schema installs no extension. A lock the statement takes lasts until the connection closes ([actuators.py](../coordinator/actuators.py)).
- Without `ANTHROPIC_ADMIN_KEY` the coordinator budgets against the worker's own ledger, which omits web-tier spend and records an estimate, not a measurement, for each agent task. Failure-triage calls are counted in the tick they happen in and recorded on that tick's row, but are not written to the ledger, so later ticks do not see them: at most five cheap-tier calls per tick. With the key, the cost report is cached for ten minutes ([spend_tracker.py](../coordinator/spend_tracker.py)).
- The coordinator's spend read takes a cost result with no `currency` field as USD and one with no `amount` as $0; only a currency that is present and not USD, or an amount that is not a finite non-negative number, makes the spend unknown (`_bucket_usd` in [spend_tracker.py](../coordinator/spend_tracker.py)).
- The ledger's day is the database session's `CURRENT_DATE` while the per-tick split uses UTC; they differ when the database time zone is not UTC. The ledger records each dispatched task at its estimate under dry run too.
- Whether the Anthropic cost report always carries a bucket for the current day was not checked against the live API; without one the coordinator makes no model call while `ANTHROPIC_ADMIN_KEY` is set.
- The model client timeout (60 s) is per phase, not a deadline for the call. The name lookup of a bounded exchange runs on a helper thread that is abandoned at the deadline. A diagnosis that takes a pre-fix snapshot can hold the health loop for up to `CAS_BACKUP_TIMEOUT_S` (900 s) per pg_dump attempt, three attempts at most.
- A build-log warning line longer than 1,200 characters is cut (the current engine writes none longer than 991), and a `compose-manifest.txt` over 256 KiB is read up to that size and reported as a lint error ([worker_pg.py](../queue/worker_pg.py)).
- The import scan does not show that a coordinator module makes no database write through a connection it was handed (the tick loop, work detection, the world state and the spend tracker hold one).
- The `agent_performance` table in the schema is read and written by nothing.
- A coordinator agent's thread that runs past its round's deadline cannot be stopped. The tick marks its task failed and refuses its later actuator calls, but its reads continue, a model call authorized before the deadline can still complete, and the task's budget reservation is kept for that reason ([tick.py](../coordinator/tick.py)).
- The phrase `go live` that the admin settings page asks for before it turns dry run off or enables the coordinator guards against a mistaken click, not against someone else: an admin session can send it. The page shows the stored Railway variables, not what a running worker read at its start.
- `finding_add` writes under dry run by design.
- A switch set to a blank value (`NAME=`) takes its default instead of the rule for other values: `BLOCKING_QA` and `BLOCKING_DESIGN_REVIEW` are off when blank, though any other value that is not an off word turns them on ([envflags.py](../coordinator/envflags.py), `safety_switch`).
- A row whose transaction began before a coordinator tick's watermark and committed after that tick's queries ran is seen by no tick. Each tick takes its watermark from the database clock at its start; after a restart the coordinator resumes from the last completed tick, at most 24 hours back, and a restart inside the overlap guard (half the interval, at most 5 minutes) skips one tick.
- The lineage bound on automatic rebuilds counts per root build over 7 days whatever the spec; deleting the root build starts a new count. Test builds queued by `queue_new_build` are not in the build-start ledger.
- The two ops playbooks act on Railway only (a redeploy of the platform's web or worker service, and one of three variables); failures classified `version_mismatch`, `missing_dep`, `missing_tool` or `dockerfile` are reported and not fixed. The legacy ops agent does not go through `Actuators` and has no permission table ([monitor-ops-scripts.md](internals/monitor-ops-scripts.md) says what bounds it).
- The cap on diagnosis model calls is an in-memory counter, per process ([diagnose.py](../monitor/diagnose.py)).
- The web tier sets no statement timeout: a slow or blocked query holds its request and one of 10 pooled connections until Postgres answers; `connectionTimeoutMillis` (15 s) bounds only the wait for a connection ([db/index.ts](../web/src/db/index.ts)).
- The health monitor removes an app from its registry after 10 consecutive check cycles in which it did not answer (about 2.5 hours at the default interval), and the app's daily database dumps stop at the same moment because the backup run iterates that registry; the only signal is an error log line ([ping.py](../monitor/ping.py)).
- Daily backups run `pg_dump` inside the worker against the `DATABASE_URL` Railway reports for the app's service, which `deploy()` sets to the private host `postgres.railway.internal` (the same name for every customer app); whether the worker can reach each customer database that way is not established by this repository, and there is no other backup route. A failed dump is logged as an error and reported ([backup.py](../monitor/backup.py)).
- Backups are unencrypted gzip files written to the container filesystem unless `CAS_BACKUP_DIR` points at a volume, and `snapshot()` streams to disk with no size cap, while `restore()` still holds the uncompressed dump in memory. A dump is checked for completeness (gzip integrity, pg_dump's header, its "dump complete" line in the last 512 bytes), not for content. A restore replays a `--clean` dump in one transaction: it drops and recreates what the dump contains.

## Roadmap executor and agent tooling

- [cas-roadmap-loop.sh](../scripts/cas-roadmap-loop.sh) runs a headless agent session with whatever permissions the operator's agent settings grant. The session is not sandboxed: it can write outside its worktree (the checkout, the `web/node_modules` the gate links, the state directory, the remote). The guard and the gate described in [ARCHITECTURE.md](../ARCHITECTURE.md#roadmap-executor-scripts) bound what a branch can get merged through the loop, not what a session can do. Roadmap text is prompt input, so anything filed in `coordinator/roadmap.json` becomes work for an enabled executor; no code in `coordinator/` writes that file, and the loop changes only the status, and at most one note field, of an item that is already there.
- The executor pushes every commit on the target branch of its checkout that the remote lacks, not only its merge and its status commit; a session, which is not sandboxed, can commit there directly.
- The executor reads `scripts/cas-executor-config.json` from the working tree at each cycle. It never commits the file, but a session that rewrites it changes the limits of the next cycle.
- The gate tests one commit and merges that commit by hash, but it runs the commit's own tests: a branch may add or edit tests and the code they import, so it cannot stop a session from weakening a test it is allowed to edit, and a test file or imported module that ends the process with a zero exit status still passes.
- Python tests are not re-run on the merged tree.
- The executor starts a session only when the web app's cost report is complete (`platform_costs_partial` false). Without `ANTHROPIC_ADMIN_KEY` on the web app the report is always partial, so an enabled executor then starts nothing. The figure it compares with the ceiling is platform spend, not the executor's own.
- The web app's cost read treats a figure it fetched earlier the same UTC day as current and reports it as complete until that UTC day ends, so spend after the fetch is missing from that figure. A cost report page that says `has_more` without a `next_page` is read as the whole report, and amounts are read as USD cents ([anthropic-costs.ts](../web/src/services/anthropic-costs.ts)).
- The executor starts no session and pushes nothing unless the web app's ops API answers its build check and its spend read (it fails closed on both, and on an answer that is not whole numbers, a finite non-negative total or a complete report). The build check is a snapshot of row counts: a build the worker claims after the last zero count is still cut off by the redeploy that the push causes, a build stuck in an active status holds every executor push until it is failed (the wait gives up after 45 minutes), and work the worker does after it writes `preview` is not counted.
- The executor's time limits cover its ops API, git and `gh` calls, the session and the gate's three commands. A job that runs over is ended as a process group together with its process tree; a process that has both left the group and been re-parented is not reached. The per-item log file has no size limit.
- The merge guard refuses every path with a byte outside printable ASCII, so an executor branch cannot add or change a file with such a name.
- A loop that is killed outright leaves its jobs running until its next start ends them (or their own timers do), and leaves an interrupted merge in the checkout until the next cycle settles it from `logs/executor/merge-in-progress`. When a person has committed on top of an interrupted merge, when the checkout is on another branch, when taking the merge back would overwrite a person's edit, or when the remote cannot be asked, it settles nothing, starts no session, and says why in each heartbeat.
- When the loop gives up on a merge in the middle of a run (the status mark cannot be committed, or the journal cannot be updated for the push), it takes the merge back only if the checkout is still on the target branch, the merge is the loop's own and `git reset --keep` accepts it; otherwise the merge stays, unpushed, with its journal and stash, the dashboard gets the result `Merge not taken back`, and no session starts until the next cycle settles it.
- A path that becomes unmerged between the executor's pre-merge check and its `git merge` is still charged to the item as a merge failure.
- The executor's tolerated-file check matches the end of each path, so any path that ends in `cli/failure_kb.json`, `scripts/cas-executor-config.json` or `CLAUDE.md` is tolerated, including a CLAUDE.md under web/ ([cas-roadmap-loop.sh](../scripts/cas-roadmap-loop.sh), `DIRTY_OK_RE`).
- The loop treats local branches named `auto/*` and `.worktrees/auto-*` and `.worktrees/gate-*` as its own: at every start and exit it deletes each `auto/*` branch no worktree has checked out, whoever made it, and removes those worktrees with `--force`.
- In its stash step the loop removes `.git/index.lock` once it is 60 seconds old without checking for a running git process (the watchdog waits 120 seconds and checks).
- The merge guard judges path names, not content: it keeps an executor branch out of the schema file, the Dockerfiles, the Railway and compose configuration and the Makefile, but a branch can still change product code, and the tests that pin the three statements writing `live` are tests a branch may edit.
- A kill that cannot be caught while an item's status is being written outside a merge leaves `coordinator/roadmap.json` changed and uncommitted; every cycle then yields until a person commits or discards it.
- The executor's locks identify their owner by process id alone: an unrelated process that was given the id of a dead owner makes a lock look held until it exits.
- The gate runs `tests` and `compose/tests`, not Playwright. A failure of `git pull --ff-only` is still ignored, and the second guard pass then judges against the local branch.
- The merge guard refuses compiled Python anywhere in a branch's diff, and the gate removes every `__pycache__`, `.pyc` and `.pyo` from its checkout before the tests run; an extension module (`.so`, `.pyd`) already on the target branch is not removed, and Python imports it ahead of a `.py` of the same name ([cas-roadmap-loop.sh](../scripts/cas-roadmap-loop.sh), `gate_remove_bytecode`). Python processes that the tests start inherit `PYTHONDONTWRITEBYTECODE` but not `--check-hash-based-pycs always`.
- The destructive-DDL and row-change check does not evaluate expressions (`WHERE id = id` passes), does not follow SQL assembled at run time (it refuses any `EXECUTE` of anything but one literal, and a person's `-- SAFE:` reason settles that), does not follow a value through a variable or a call, does not decode strings (`E'\x6c...'`, concatenation), flags every `TRUNCATE` keyword, reads PL/pgSQL only by cutting bodies at semicolons, and refuses a statement of more than 2000 tokens. A reason is a person's claim: it settles the check, not the question of whether the statement is safe. `verify_hooks.sh` runs the hooks' own checks for DDL, JSON, brand voice, the bless gate and the staging gate; for the audits, the web tests and the SEO lint it verifies that the hook runs them and stops on failure, not what they find.
- `record_roadmap_status` compares `coordinator/roadmap.json` with HEAD and then commits the file; a process that rewrites it between the two is not excluded.
- The gate needs python3 3.11 or newer and pytest 8.4 or newer and fails closed without them; a pytest configuration kept in `pyproject.toml`, `tox.ini` or `setup.cfg` is not read by the gate.
- It ships disabled (`"enabled": false` in [cas-executor-config.json](../scripts/cas-executor-config.json)); its behavior is covered by [test_executor_loop_behavior.py](../tests/test_executor_loop_behavior.py), which runs the real loop against a fake agent, a stand-in ops API and a local bare repository only; [test_executor_ops_contract.py](../tests/test_executor_ops_contract.py) checks the loop's assumptions about the web app's ops API against the text of the routes. It was not run against the real agent CLI or a hosted remote for this release.
- The completion hook ([honest_completion_audit.py](../scripts/honest_completion_audit.py)) matches phrases. A plain "done" or "fixed" does not trip it, it does not verify that a listed gap is real, it blocks at most once and it fails open. Of the six hooks in the example settings it is the only one that can block; the other five add reminder text.
- The guard against text that ties sample data to a customer ([test_no_customer_markers.py](../tests/test_no_customer_markers.py)) is structural. It reads every published text file and fails on a real-customer tag, and it holds `compose/fixtures/*.json` to reserved hosts, 555-01xx phone numbers, the placeholder state `ST` and postal codes counted up from 00001. It also holds the Medicine Waves data files (`tests/fixtures/*.json` and `tests/golden/*/spec.json`) to three checks: a street address with a postal code outside the placeholder run, a phone number outside the 555-01xx block, and an event start that is not a sample date in 2030; and `cli/failure_kb.json` to no calendar day with a clock time. It does not look for names, so a real name in a comment, a test string or an image would not fail it.

## Infrastructure and dependencies

- A second copy of the web server started against the same database runs the schema migration before it discovers that the port is taken, so it can briefly contend with the first copy before it exits ([server.ts](../web/src/server.ts)).
- The worker image ([Dockerfile.worker](../Dockerfile.worker)) is `mcr.microsoft.com/playwright/python:v1.42.0-jammy` (Ubuntu 22.04 with Playwright 1.42.0 and its Chromium; the Dockerfile pins no Python version of its own and uses the one that base image ships, which for Ubuntu 22.04 is 3.10) plus Node.js 20 from NodeSource, `postgresql-client-15` from the PostgreSQL project's apt repository and Railway CLI 4.31.0. Node 20 reached end of life on 2026-04-30 according to the file's own note; the setup script is fetched with `curl | bash`, the base image is pinned by tag and not by digest, and the container runs as root. The image was not built or run when the release was prepared: the suites were measured under Python 3.12 and Node 25 on macOS, and CI runs Python 3.12 and Node 24 on Linux, so nothing here was tested on the image's own versions. That the image carries a `pg_dump` of at least the customer databases' major version rests on the Dockerfile's text, a test that compares two files and the `worker-image` job of `test.yml`, which builds the image, compares its `pg_dump` version with the server's and dumps the schema of a `postgres:15` server with it; that job had not run on GitHub when the release was prepared. It first ran on the release commit afterwards and passed, which also confirms the PGDG key fingerprint in the Dockerfile (it was typed from memory, and a wrong value fails the build).
- The pinned Playwright 1.42.0 and its bundled Chromium get no security updates at that pin, and that browser loads deployed customer sites for review screenshots.
- One web process serves everything. Synchronous work on its event loop delays every request, the crisis handler included; the crawl's HTML parsing was moved to a worker thread for that reason, and other request-time work was not audited for it line by line.
- The parse thread's 256 MB heap cap (`ParseWorker` in [site_copy_crawl.ts](../web/src/services/site_copy_crawl.ts)) is not a hard bound on memory. Node ends a worker that reaches its heap limit by terminating it, and the thread keeps allocating until the termination lands. In one cloud sandbox (Node 22 and 24, measured after release) a thread allocating 400 KB arrays under a 32 MB limit reached 8.5 GB of heap and was stopped after 28 seconds; on CI the same test thread is stopped within its 15-second budget. In production the 2 MiB body cap and the parse job's 10-second kill are what bound it. On a machine like that sandbox, the test "a thread that runs out of heap fails its job and nothing else" (`services.site-copy-crawl.parse-worker.test.ts`) times out instead of seeing the memory error. Parsing in a child process with its own `--max-old-space-size` would make the cap hard.
- Python dependencies are version ranges plus one exact pin (Playwright 1.42.0). `Pillow`, `requests` and `sentry-sdk` in [requirements.worker.txt](../requirements.worker.txt), and `Pillow`, `bandit` and `pip-audit` in [requirements-dev.txt](../requirements-dev.txt), have a lower bound and no upper bound. No dependency, direct or transitive, is pinned by hash, and there is no lockfile, so two installs can resolve to different versions.
- The web app's stylesheet is built with Tailwind 4, which targets Safari 16.4, Chrome 111 and Firefox 128 or newer. The build carries fallbacks for colors with an opacity and for its custom properties, but no older browser was tried. The move from Tailwind 3 was compared page by page (49 addresses, at desktop and phone width, as a visitor, a customer and the admin): one difference was kept, the Save button on `/admin/settings` sits 8 px closer to the notice above it, because Tailwind 4's `space-y-*` no longer counts the form's hidden CSRF field.
