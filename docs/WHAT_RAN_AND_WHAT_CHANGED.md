# What ran in production, and what the review changed

The first list is what the system did while it served customers. The second is what the pre-release review added, and none of that has run in production. The split was made by comparing the published tree with the last private one.

## As it ran in production

**Replacing a model with a template composer.** v1 asked a model to write each customer's app and then repaired the result: [cli/build.py](../cli/build.py) holds 117 `@processor` functions (count them: `grep -c '^@processor' cli/build.py`), ordered as a dependency graph by [cli/pipeline.py](../cli/pipeline.py). The same classes of bug kept coming back, which [MW_BUG_RECURRENCE_RCA.md](internals/MW_BUG_RECURRENCE_RCA.md) documents. v2 removes the model from the build path: 10 archetypes, 14 palettes, 21 font pairs, 62 page layouts and a registry of 55 widgets live in [compose/data/](../compose/data/archetypes.json) as JSON, and the engine composes them. The model stays where it is useful, in the conversation and in turning that conversation into a spec. The decision record is [CAS_V2_STATIC_COMPOSE_PLAN.md](internals/CAS_V2_STATIC_COMPOSE_PLAN.md).

**Postgres as the only moving part between services.** No broker. The worker claims a build with `FOR UPDATE SKIP LOCKED`, recovers builds orphaned by a restart, and stops retrying deterministic failures, because the same input gives the same output.

**A review gate in the publishing statement.** A build finished at `preview`. The two statements that mark a customer's site live, the approve route in [web/src/routes/builds.ts](../web/src/routes/builds.ts) and the Stripe checkout handler in [web/src/routes/webhooks.ts](../web/src/routes/webhooks.ts), require `review_status = 'approved'` in the same `UPDATE`. The admin's variant of the approve route requires only `preview`.

**Deterministic rails around a language model.** The companion can be talking to someone in distress, so crisis detection is a local pattern scan that answers with a fixed script and needs no model call. That sentence is about where the scan runs; how much of what people write it recognizes is a separate claim, answered under "Crisis handling" below. A second set of rails checks what the model says about itself. Spend was capped per identity.

**Bounded automation.** Coordinator agents act through a permission table ([coordinator/actuators.py](../coordinator/actuators.py)), and most of them are rule-based Python, which the docs say plainly. The roadmap executor in [scripts/](../scripts/cas-roadmap-loop.sh) merged and deployed code unattended; its merge guard at the time protected a single file, `CLAUDE.md`. It ships disabled.

## Added or completed by the pre-release review

The review ended with six adversarial rounds. The second found that several guarantees were correct inside one function and broken where two components met. The third found that several controls were correct in mechanism and narrow in coverage: a matcher that missed common phrasings, switches that failed open on common spellings, limits that guarded dead code while the live path went around them, and a generator that published by name. The fourth found mostly availability problems (what a slow, huge or malformed input does) and gates that passed when they should have failed; the README's claims and numbers all reproduced. The fifth round found more gaps where two components meet, and the sixth found controls that outlived the session, cap or check they were meant for, and copy that promised more than the product kept. The passages below, marked by round, are the answers to those. The findings and the test for each are in [PRE_RELEASE_REVIEW.md](PRE_RELEASE_REVIEW.md); the mechanisms are described in [ARCHITECTURE.md](../ARCHITECTURE.md) and [THREAT_MODEL.md](THREAT_MODEL.md).

**The generator now assumes a hostile spec.** Spec strings become file names, route paths, SQL identifiers and JavaScript, and as it ran the engine trusted them. The review added the gate (`_spec_safety_errors`), a single writer that refuses to leave the build directory or write one path twice, and reserved names. [test_spec_hardening.py](../compose/tests/test_spec_hardening.py) holds 305 tests (`pytest --collect-only` counts them), including hostile shapes that must be refused by validation, resolution and build alike, and a determinism test that builds one spec in two interpreters with different hash seeds and compares every file.

**The generated site, second round.** A page that lists several roles used to get one guard per role, which no account could pass; it now gets one guard that any listed role passes. A spec whose protected page would be answered without a login by something else in the build is refused, not warned about. The site's access log no longer records query strings, so a login link is not in it. SQL that depends on a model (the contact form's insert, a listing's order) is derived from that model's fields. [test_generated_site_security_e2e.py](../compose/tests/test_generated_site_security_e2e.py) checks these on a booted site.

**What a generated site publishes, third round.** A page that shared a model's name published that model's table, and a visitor's form submission went public at once. A model's rows are now public only where the spec sets `public_listing_path` or an archetype's page reads the table (`_public_row_sources` in [compose/build.py](../compose/build.py)), a visitor's row is stored unpublished until the admin publishes it, and public form values are validated before the insert. Every emitted stylesheet and script is now parsed in a test (one template emitted a doubled brace). [test_generated_site_publication_e2e.py](../compose/tests/test_generated_site_publication_e2e.py) boots a site and checks the publication rules, and [test_emitted_css_js_syntax.py](../compose/tests/test_emitted_css_js_syntax.py) parses 164 builds. The web translator that turns a conversation's extracted spec into the engine's input now resolves each contradiction the engine would refuse toward less exposure, with a warning ([harbor_to_compose.ts](../web/src/services/harbor_to_compose.ts)), and [test_translator_output_builds.py](../compose/tests/test_translator_output_builds.py) runs its real output through the engine. Only a boolean `published` column holds a visitor's row back. The engine's exceptions to determinism are four, not two: the build time, the build day, the raster brand assets and the external-link lint's reports.

- *Fourth round, shape:* a spec is JSON written by a model, and 180 of 3,456 wrong-typed shapes crashed an emitter or built a page that threw while `validate_spec` returned nothing. The validator now owns the type and size of everything an emitter reads, and page data reaches a view only through the parameters its widget declares ([build.py](../compose/build.py), [widget-registry.json](../compose/data/widget-registry.json)); [test_spec_shape_matrix.py](../compose/tests/test_spec_shape_matrix.py) puts every JSON type at every position of ten sample specs, and [test_gate_checks.py](../compose/tests/test_gate_checks.py) adds a test for each gate condition no test pinned.
- *Fourth round, build report:* a spec could bury the engine's warnings under its own. The engine's findings are now written first as `warning: ` lines and the spec's notes after them as at most 40 `spec-warning: ` lines, so a spec cannot add, remove or imitate an engine line ([build.py](../compose/build.py), [test_build_report.py](../compose/tests/test_build_report.py)); the link lint no longer reports the address a host name resolved to ([lint_external_urls.py](../compose/lint_external_urls.py)).
- *Fourth round, health:* a generated site whose home page throws used to pass the deploy check, because `/health` asked only the database. The emitted `services/health.js` requests the home page once when the site starts, and `/health` answers 503 `home_page_error` when that failed ([build.py](../compose/build.py), [test_site_health.py](../compose/tests/test_site_health.py)).
- *Fifth round, shape and columns:* the size bound now covers the whole document, unknown keys included, and the link lint's walk no longer recurses ([build.py](../compose/build.py), [lint_external_urls.py](../compose/lint_external_urls.py)). A column the engine reads with a fixed meaning (`id`, `created_at`, `published_at`, the link to a parent, the newsletter email) is refused when its type cannot work, a seed value or default that Postgres would refuse is left out with a warning, and tables are created parent first; [test_engine_columns.py](../compose/tests/test_engine_columns.py) and [test_stored_values.py](../compose/tests/test_stored_values.py) run the built SQL on a real Postgres, and the wrong-type matrix has a Postgres mode and two valid column types as values.
- *Fifth round, publication:* a page that lists roles requires a login, a public form page must name the columns a visitor may fill in, a row whose flag has no value is public nowhere, a visitor sorts a public list only by a column it prints, and a stock photo of a specific person or place is refused and never copied ([build.py](../compose/build.py), [test_publication.py](../compose/tests/test_publication.py), [test_stock_photos.py](../compose/tests/test_stock_photos.py)). The web translator no longer emits what the engine refuses for these ([harbor_to_compose.ts](../web/src/services/harbor_to_compose.ts)), and the build report's `external_url_lint:` line says whether the lint was skipped, ran or failed.
- *Sixth round, stored values and layout:* a stored timestamp longer than 64 characters is refused before its pattern runs (one value of about 100,000 characters had held the worker for about half a minute), and the public layout escapes the characters that let a site description close its own script block, so a description could blank the page ([build.py](../compose/build.py), [layout-public.ejs](../compose/templates/layout-public.ejs)).

**The worker's status machine.** `_set_status` moves a build forward only, the worker has no statement that writes `live`, and every status write carries the build's current status and an attempt token, so a thread left over from an earlier attempt cannot move a newer one. Terminal failures in the worker go through one function that records a dead-letter row and emails the customer. A rebuilt site goes back into review instead of keeping the previous verdict. The claim takes an advisory lock, and each running build holds a best-effort lease that orphan recovery checks.

- *Fifth round:* the optional status hook now enters a build into review the way the worker does, as `pending` or, under `CAS_HARBOR_AUTO_REVIEW`, `ai_review_queued` (before, it wrote `pending` whatever the switch said), and it takes the preview address in a field named `preview_url` ([webhooks.ts](../web/src/routes/webhooks.ts)). The schema file that runs at every boot is held to the rule the three statements that write `live` are: nothing in it may name that status, and any other row change in it needs a reason of its own ([check_destructive_ddl.py](../scripts/check_destructive_ddl.py), [schema.idempotency.test.ts](../web/tests/unit/schema.idempotency.test.ts)).

**The worker's lifecycle, second round.** The attempt token is now required, not optional. A Railway project belongs to the attempt that created it until the build reaches preview: the failure path no longer deletes whatever project the build row names (after a requeue that was the customer's working preview), and the row's project is written only by the preview write. A deployed app that never answers its health check is retried, not previewed. The loop claims a build only when a thread is free to run it, and takes ownership and the lease at the claim. The janitor deletes rows only and keeps what other rules read. The supervisor's cancel signal reaches the fix loops it was meant for, the monitor loop survives a database error, and the login probe posts its token and never puts it in a URL. [tests/test_worker_pg_realdb.py](../tests/test_worker_pg_realdb.py) and [tests/test_worker_lifecycle_realdb.py](../tests/test_worker_lifecycle_realdb.py) run this against a real Postgres from one process; no test runs two worker processes against one database.

**The worker's lifecycle, third round.** Ownership of a running build is a (build id, attempt) pair and the lease key includes the attempt, so the leftover thread of an earlier attempt can no longer make orphan recovery treat a newer attempt as abandoned (`_OWN_ATTEMPTS` in [queue/worker_pg.py](../queue/worker_pg.py)). A Railway deployment that ends FAILED is retried once, one that ends CRASHED with a database-unreachable log is treated as transient, and a mutation whose answer was lost is resent only when it cannot have run (`RailwayOutcomeUnknown` otherwise, in [cli/deploy.py](../cli/deploy.py)). A deployment counts as healthy only on HTTP 200 with JSON `status` equal to `ok`, in the deploy step and in the supervisor's probe (`health_response_ok`). [test_deploy_outcomes.py](../tests/test_deploy_outcomes.py) and [test_worker_lifecycle_realdb.py](../tests/test_worker_lifecycle_realdb.py) run these.

**The worker's lifecycle, fifth round.** A thread the supervisor had given up on found its database connection closed, could not check whether its Railway project was recorded, and left the project running; it now cleans up on a connection of its own, and the supervisor's preview write and that clean-up hold one lock, so a project is announced or deleted and not both ([worker_pg.py](../queue/worker_pg.py)). A crashed deployment whose log cannot be read is retried once instead of being called the app's fault, and the error classifier reads 429, 502 and 503 as whole tokens, not as pieces of a build id. The credentials of a URL are removed by one rule in the worker, `cli/deploy.py` and the failure knowledge base, the rule the web app applies to what a customer is shown, so a URL whose user-info is only a token no longer reaches a log or a child process ([url_redaction.py](../monitor/url_redaction.py)).

**Crisis handling ahead of everything else.** As it ran, the crisis scan sat inside the turn function, behind the rate limiter, an email-capture gate and the cost cap, so a message from someone in crisis could be answered with a request for an email address or a refusal. The scan now also runs first at the HTTP boundary (`crisisFirst`): it answers from the request body alone, then stores the turn and alerts the operator in the background, with the alert rate bounded. A shared daily spend cap across all visitors was added next to the per-identity one, and every route that can cause a model call has a stated bound (the table is in [THREAT_MODEL.md](THREAT_MODEL.md)).

- *Second round:* the handler shares one event loop with the rest of the web process, and the admin-triggered site crawl parsed fetched HTML there with regular expressions that a crafted page could make run for minutes. That parsing is now single-pass scanners in a worker thread with a hard kill ([site_copy_parse.ts](../web/src/services/site_copy_parse.ts)).
- *Third round:* everything above is a guarantee about order, and it held only for text the scan recognized. The patterns missed common plain phrasings ("I just want to die" met the email gate), so [crisis_detection.ts](../web/src/companion/crisis_detection.ts) was rewritten and scored on phrasings not derived from its patterns: 39 of 40 plainly worded disclosures and none of 30 harmless messages in a set written after the patterns were final, and 54 of 68 and 55 of 79 in two earlier sets, the second written to be indirect (the scan it replaced scored 20 of 40, 15 of 68 and 19 of 79). Every set was written by a language model, the numbers and the known misses are in [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md), and [crisis-phrasing.realdb.test.ts](../web/tests/unit/crisis-phrasing.realdb.test.ts) sends the plain phrasings through the email gate of a real conversation. The reply now names 911 first for a medical emergency, and a threat to another person has its own reply; no clinician has read either.
- *Sixth round:* the crisis path stores at most 60 turns per process per minute across all identities, evicts entries that hold no quota, oldest first, rather than clearing the whole map, and gives a turn over the cap the fixed reply without storing it ([runtime.ts](../web/src/companion/runtime.ts)). Before that cap, the path still looks up the trial cookie, one database read per crisis request; that is open.

**Authentication and environment handling.** One function decides whether the process is in development (`isDevOrTestEnv`: anything but exactly `development` or `test` is production), one resolves the session secret and refuses placeholders outside development, one defines an admin session, and a global guard refuses cross-origin writes. All four are in [web/src/middleware/auth.ts](../web/src/middleware/auth.ts). Signup no longer lets an earlier, unverified claim on an address keep its password: the credentials that count are the ones typed in the browser that proves control of the mailbox ([web/src/routes/auth.ts](../web/src/routes/auth.ts)).

- *Third round:* every rate limiter is built by one function, `boundedRateLimit` in [companion-rate-limit.ts](../web/src/middleware/companion-rate-limit.ts), which caps its memory at 20,000 keys and hashes long keys (before, a client could fill the process's memory with limiter keys, and 80 requests were enough to take the heap from 30 MB to 254 MB); the account forms accept bodies of 10 KB; and the quickstart's `web/.env.example` sets `TRUST_PROXY_HOPS=0`, because with one trusted hop and no proxy in front a rotating `X-Forwarded-For` walked past every per-address limit. Query strings no longer reach the error buffer behind `/ops/api/v1/errors`, the error tracker or the stored entry URLs ([recent-errors.ts](../web/src/utils/recent-errors.ts), [instrument.ts](../web/src/instrument.ts)).
- *Fifth round:* every password hash comes from one module at one cost, so an account made at checkout no longer answers a wrong password faster than the rest ([password-hash.ts](../web/src/utils/password-hash.ts)); `POST /account/delete`, the one other route that checks a password, has a limiter ([auth-rate-limit.ts](../web/src/middleware/auth-rate-limit.ts)); `STRIPE_BYPASS=false` no longer turns the feature-payment bypass on, because the variable is read as an arming switch ([features.ts](../web/src/routes/features.ts)); and the page-view log stores the Referer as a path, not the whole URL ([app.ts](../web/src/app.ts)).
- *Sixth round:* the admin settings page keeps only the twelve setting names from the worker's variables, and the admin build delete reads the Railway project's name back before it deletes anything, and refuses a name that does not match ([admin.ts](../web/src/routes/admin.ts), [railway.ts](../web/src/services/railway.ts)).

**The payment path, walked end to end.** The first adversarial round found that the webhook that charges a trial visitor also invalidated the cookie that identified them, so the page Stripe sends a payer back to returned 404. Each Stripe event is now handled in one transaction together with its idempotency claim, the paying browser stays the owner of the site it paid for, and a customer's own publish of a Harbor site requires a subscription.

- *Second round:* that last rule read a build's ancestors, which the worker's own cleanup deleted, so it could be walked around. Whether a build is a Harbor build is now a column on the build row (`builds.is_harbor`), set at dispatch and inherited through a trigger. The keeper row stores Stripe's subscription status word for word, so `unpaid` and `paused` no longer count as subscribed, and the owner's source download follows the publishing rule. [money-path.realdb.test.ts](../web/tests/unit/money-path.realdb.test.ts) drives the publish, payment, signup and crisis routes against a real Postgres, and runs the worker's real cleanup function against the rows the publishing statement reads.
- *Third round:* after a payment the keeper's notes were read and written by the trial id, which promotion had emptied, so the notes panel and the recall page came up empty. One function, `resolveCompanionIdentity`, now decides whose conversation a request speaks in. The same test file also covers a conversation's first build counting against the build-start limits and the address a payment is tied to.
- *Third round, in the same file:* a turn whose model answer straddles the payment is stored under the keeper the trial was promoted into (`persistTurn` in [runtime.ts](../web/src/companion/runtime.ts)), the webhook promotes the build's unreleased trial when the Checkout metadata names none ([webhooks.ts](../web/src/routes/webhooks.ts)), the operator's inbox lists paid keepers under `?status=keepers` ([admin.ts](../web/src/routes/admin.ts)), and account deletion deletes the account's Haven trials with their turns and notes ([auth.ts](../web/src/routes/auth.ts)). A conversation's first build is a `dispatch` row in the build-start ledger, and the limits have one definition, [build-start-limits.ts](../web/src/services/build-start-limits.ts).
- *Fifth round:* the rule that a trial cannot pay into an account that already has a subscription was kept only by the route that opens Checkout, so a session opened earlier and completed later promoted a second trial into the first keeper: it repointed the subscription and gave the second browser the first keeper's conversation. It is now kept in the statement that writes the keeper row (`claimKeeperSubscription`), a payment it refuses is recorded and mailed to the operator, and a released trial's cookie speaks as a keeper only through `trial_keepers.promoted_customer_id` ([keeper_promotion.ts](../web/src/services/keeper_promotion.ts), [webhooks.ts](../web/src/routes/webhooks.ts), [trial-cookie.ts](../web/src/middleware/trial-cookie.ts)).
- *Sixth round:* a paid trial cookie stops speaking for its account when its browser logs out, when that browser logs in to another account, and when the account's password is reset or its mailbox verified. A copy of the cookie still works until its 30 days end. An anonymous dispatch refuses an account that already has a keeper row or a build. An event for a subscription the server does not yet know is refused for 72 hours, so Stripe's retries can apply it; the three-day retry figure is not checked against Stripe's documentation ([trial-cookie.ts](../web/src/middleware/trial-cookie.ts), [auth.ts](../web/src/routes/auth.ts), [harbor_dispatch.ts](../web/src/services/harbor_dispatch.ts), [webhooks.ts](../web/src/routes/webhooks.ts)).

**Automation that fails closed.** Unanswered approval requests are rejected on timeout, the coordinator's writes, sends and model calls are made through the permission table and do nothing under dry run (one action, which only files an entry for a person to review, is exempt), and customer text is escaped before it reaches a prompt.

- *Second round, coordinator:* a tick whose spend source cannot be read gets zero dollars and zero calls, with no older figure substituted, and every model call is granted one at a time by a per-tick meter; before, failure triage called a model outside the allowance. A scan of what coordinator modules may import was added beside the one that only matched call names, and four triggers that routed work to agents with no handler for it were removed.
- *Second round, executor:* its merge guard already covered its own gate (scripts, hooks, CI, test configuration) and both sides of a rename; it now also covers what the test runners load before the first test, the tests run on a fresh checkout of one commit, and that commit, by hash, is what is merged.
- *Third round, executor:* it also pushes nothing while a build is queued, building, testing or deploying, starts no session and pushes nothing when the ops API does not answer, puts a time limit on its network calls and commits only an item's status change, through the pre-commit hook. [tests/test_executor_loop_behavior.py](../tests/test_executor_loop_behavior.py) runs the real loop against a fake agent, a stand-in for the ops API and a local bare repository.
- *Third round, coordinator and ops:* a dry run, an analysis-only mode and a blocking gate are turned off only by `false`, `0`, `no`, `off` or `disabled`, through one module, [envflags.py](../coordinator/envflags.py) (before, `COORDINATOR_DRY_RUN=1` meant live); the limits on redeploys and variable writes sit in [ops/fixer.py](../ops/fixer.py), where the playbooks end, and no longer on methods nothing called (commits were removed altogether in the fourth round); `Actuators.queue_rebuild` refuses a deterministic failure, a customer at the build-start limits and a chain of more than three rebuilds of one root build in seven days; and a tick reads from the previous tick's start, so a row written while a tick runs is not lost ([tick.py](../coordinator/tick.py), [test_coordinator_rebuild_realdb.py](../tests/test_coordinator_rebuild_realdb.py)). Third round, follow-up: the admin settings form no longer takes the coordinator live on an ordinary save (it writes only what changed, from a fixed list of twelve names, and asks for the typed phrase `go live` before it turns dry run off or enables the coordinator; [coordinator-settings.ts](../web/src/services/coordinator-settings.ts)); each grant in the permission table is asked for by a real handler ([test_coordinator_permission_use.py](../tests/test_coordinator_permission_use.py)); every dispatch branch is routed to by a trigger, and the approval method and permission were deleted; the executor watchdog is live only with no argument; and a coordinator task past its deadline is closed as failed.
- *Fourth round, coordinator:* unknown is treated as unknown. A cost report that cannot be read, or has no bucket for today, is unknown spend and gives the tick nothing; a failed refresh leaves its figures unknown, and an unknown pipeline count is read as a customer build in progress ([spend_tracker.py](../coordinator/spend_tracker.py), [state.py](../coordinator/state.py)). The failure circuit no longer trips under dry run and gets a probe after six hours ([tick.py](../coordinator/tick.py)). An agent cannot build its own `Actuators`, and filing an approval request is a permission of its own ([actuators.py](../coordinator/actuators.py): 29 grants). The learning loop, the GitHub client and the three playbooks that could not commit against the real files were deleted, so nothing in `ops/` or `coordinator/` commits to a repository. A model reply can no longer silence the diagnosis alert ([diagnose.py](../monitor/diagnose.py)).
- *Fourth round, executor:* the guard's rules moved into [cas-merge-guard.py](../scripts/cas-merge-guard.py) and now refuse the deletion of any test file in the tree (not only under `tests/`), any path with a byte outside printable ASCII (on APFS a Unicode spelling of `.githooks/` got a hook merged and run), and submodule links; the gate also runs `compose/tests`; the pre-commit DDL check reads SQL with a tokenizer and judges the staged content, and `verify_hooks.sh` runs the hooks instead of grepping for their names; the spend read refuses a partial or implausible report, so an enabled executor needs `ANTHROPIC_ADMIN_KEY` on the web app; an interrupted merge is settled from a journal at the next cycle; and locks, kills and the reading of `enabled` were made atomic, whole-tree and single ([test_executor_loop_recovery.py](../tests/test_executor_loop_recovery.py), [test_destructive_ddl_corpus.py](../tests/test_destructive_ddl_corpus.py)).
- *Fifth round, executor:* a merge the loop gave up on mid-run was undone with `git reset --hard` on whatever branch was checked out, which discarded a person's edit; both paths now go through `take_back_merge`, which acts only on the target branch, only on the loop's own merge and with `git reset --keep`, and otherwise leaves the merge, its journal and the stash for the next cycle ([cas-roadmap-loop.sh](../scripts/cas-roadmap-loop.sh)). The merge guard's path list gained the Tailwind and Playwright configuration, the Dockerfiles, the Railway and compose configuration, `requirements*.txt`, the `Makefile`, and the schema file with `migrate.ts` ([cas-merge-guard.py](../scripts/cas-merge-guard.py)).
- *Fifth round, coordinator and monitor:* `query_readonly` runs exactly one statement in a read-only transaction (a text that began `COMMIT;` used to delete a row), an agent's result says what became of each alert, finding, KB entry, rebuild and approval request instead of reporting success after a refusal, and a tick with no budget still runs the tasks that cannot make a model call ([actuators.py](../coordinator/actuators.py), [base.py](../coordinator/agents/base.py), [tick.py](../coordinator/tick.py)). The worker image installs a PostgreSQL 15 client, and a dump whose `pg_dump` is older than the server is refused with both versions named ([Dockerfile.worker](../Dockerfile.worker), [backup.py](../monitor/backup.py)); the image was not built when the release was prepared, and a CI job now builds it. The legacy ops agent's mail no longer says that fixes were committed to master.
- *Sixth round, executor:* the loop refuses to start a cycle while any path is unmerged (a conflicted stash pop), the watchdog alerts on it, and a stash or merge refused for that reason is not charged to an item ([cas-roadmap-loop.sh](../scripts/cas-roadmap-loop.sh), [cas-executor-watchdog.sh](../scripts/cas-executor-watchdog.sh)). The executor ships disabled.

**Outbound request guards.** The site crawl and the link lint connect only to an address that passed a public-address check, on the connection they actually use.

- *Second round:* the monitor's and the deploy step's probes do the same now (their URL check used to read a URL differently from the library that sent it, and resolved nothing). The review browser is checked the same way but cannot be pinned.
- *Fourth round:* every probe and provider call is one exchange with a deadline for the whole of it and a cap on the decoded body ([bounded_fetch.py](../monitor/bounded_fetch.py)); before, a `/health` that sent one byte per read held a probe for 11 seconds at a 1 second timeout, a 40 MiB body was read in full and 24 KiB of gzip became 24 MiB, so one customer app could stall the health loop for every other. On the web process, `/sitemap.xml` no longer runs `git` on the event loop that serves the crisis handler, the status poll's redaction is linear, and the contact form and Stripe calls have deadlines ([sitemap-lastmod.ts](../web/src/services/sitemap-lastmod.ts)).
- *Sixth round:* the worker's health probe does not follow redirects, so a project that redirects to another healthy-looking page is not reported healthy ([watchdog_probe.py](../queue/watchdog_probe.py)).

**Hostile input kept off the event loop.** The crawler that copies an existing site and the logo upload both parsed attacker-controlled text with regular expressions on the web process's only event loop. Both now use single-pass scanners in a worker thread that is killed on a deadline, and an uploaded SVG is rebuilt from an allowlist and never handed to the image library ([site_copy_parse.ts](../web/src/services/site_copy_parse.ts), [svg_sanitize.ts](../web/src/services/svg_sanitize.ts)).

**Copy brought in line with the code.** Marketing pages, emails and prompts that said a named person designs, builds and personally reviews every site now say what the code enforces: a site is built from tested building blocks and a review verdict is recorded before it can be marked live. An artificial delay that made chat replies look typed was removed, along with code that nothing called.
- *Fourth round:* the build request answers every failure of the extraction with a typed answer from one table, 409 when there is nothing to read and 502 when the model call fails or its reply is not a spec (before, 500 HTML after a paid call), and a refusal on a JSON route is JSON ([harbor_dispatch.ts](../web/src/services/harbor_dispatch.ts), [json-request.ts](../web/src/utils/json-request.ts)). The privacy and terms pages, the Stripe product text and the preview-ready emails were rewritten to say what the code does (the cookies and their lifetimes, what account deletion removes and leaves, who receives data), and none has had legal review. Error-tracking events no longer carry request bodies or cookies ([instrument.ts](../web/src/instrument.ts)).
- *Fifth round:* the contact form answers 400, not 200, when it refuses a message; the home page and About page titles no longer repeat the brand; and the redaction applied to what the status page and the log stream show an owner now covers a URL whose user-info is only a token and a database password that contains `)` ([app.ts](../web/src/app.ts), [builds.ts](../web/src/routes/builds.ts)).
- *Sixth round:* the copy no longer promises a review time, a reply from a named person or a personal reply. It says that a website needs a recorded review approval before it goes live, which is what the code enforces. The rewritten copy has had no review beyond the tests, and the title "Senior Web Craftsman" is unchanged.

## What these guarantees do not cover

A short list; [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md) has each of these precisely, and many more.

- **A preview is not private, and "live" is a status.** The preview address is public and crawlable from the first deploy, the customer is emailed it before any review, and approval changes a row in the platform's database and nothing on the site.
- **Review was not always a person.** An automated review mode was added in June 2026; its loop is not in this repository, which does not record which production sites took which path.
- **Payment.** A reviewed build that is not a Harbor build can be taken live by its owner without payment. One subscription covers every Harbor build on an account. A payment that completes while its build is not publishable is recorded and logged; nothing publishes the site or refunds the charge.
- **Railway projects can be left running.** A worker killed mid-attempt, a failed delete, a preview superseded by a later deployment of the same build, and the cleanup routes all leave a project that no build row names.
- **Customer databases and backups.** Each customer database was a Postgres container with no volume attached by this code, and whether the nightly dumps could reach those databases is not established by this repository.
- **The crisis scan is a pattern list, not a clinical safeguard.** It runs first and needs no model call, but it recognizes plainly worded disclosures almost always (39 of 40 in a set written after its patterns were final) and indirect ones about three times in four (54 of 68 and 55 of 79 in two earlier sets); it misses a plan that is never named, anything not in English and spellings built to dodge a filter. The sets were written by a language model, and no clinician has read the patterns or the replies.
- **What was and was not exercised.** The web unit tests replace the database with mocks; SQL is executed by the browser suite, three web integration files and the worker's and coordinator's real-database tests. No test runs two worker processes, no deploy, payment or model call was exercised against Railway, Stripe or a model provider, the worker image was not built or run (the `worker-image` CI job now builds it and had not run when the release was prepared), and the executor was run only against a fake agent.
