# Pre-release review

**In short.**

- **What it was.** AI coding agents (Claude Code), directed by the author, read, tested, fixed and documented a snapshot of this code after development stopped, in six adversarial rounds. Each round gave four fresh reviewers the repository with a role and a report format, and no account of the code or of the earlier rounds' findings; a fix round followed each, and after publication a security review in four areas found one High and three Medium defects, since fixed ([below](#found-by-the-security-review-after-publication)). Nothing ran against a live deployment, and no independent human security review is described here.
- **The five most serious findings, all fixed in this tree.** (1) The forgot-password page showed the one-time reset link to whoever submitted the form. (2) A placeholder session secret was accepted in production. (3) The companion's prompt told people their notes were encrypted and held to a therapist's standard of confidentiality, and neither was true. (4) Someone could register another person's address first and keep access after that person verified it. (5) One customer's app could stall the health checks of every other customer and fill the worker's memory, because the probes had no time or size bound.
- **What it did not verify.** Nothing was run against Railway, Stripe, Resend or Anthropic, and the worker image was not built (after the release, CI's first run on the release commit built it and passed: [the run](https://github.com/aqlong/craftandship/actions/runs/38287911118)). The crisis scan's patterns and the wording of its replies had no clinical review. Two worker processes were never run against one database.
- **Where the numbers are.** The measured test results are in the README; every finding below has its fix and its test, and the limits that remain are in [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md).

This is an account of the review the code received before it was published, and of the security review that followed publication, written so a reader can judge the process and its limits. It lists what was found, what was changed in behavior, and what was not verified. It is a companion to [THREAT_MODEL.md](THREAT_MODEL.md) and [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md), which hold the threat model, the controls and the known limitations, and to [ARCHITECTURE.md](../ARCHITECTURE.md).

The system ran in production from March 2026. It is no longer developed and the site was taken offline in October 2026. The review below was done on a snapshot of that code, after development stopped, so none of it was done against the live site.

## Who did the work

The scrub, the reviews, most of the fixes and the documentation were carried out by AI coding agents (Claude Code) at the author's direction. This document makes no claim about the author's review of any individual change; the root README, "How I built this", says what the author did and did not do. Each agent worked on one area under a shared written brief; the reviewers of the adversarial round (step 7 below) were the exception: each was given a role and a report format, and no account of the code or of the earlier findings. The rules that brief set matter for judging the results:

- Read the code in scope properly, most important files first. Record each finding with a severity, a location, what is wrong and a concrete failure scenario.
- Fix Critical, High and Medium findings in place and add or extend a test that fails before the fix and passes after it. When a correct fix was too large or too risky, do not paper over it: report it with a recommended fix so it can be documented as a known limitation.
- No credentials, and no network calls to the model, payment, mail, hosting or error-tracking providers. Tests run on dummy values. Version control was handled outside the review agents, which did not commit.
- No new runtime dependencies, no lockfile changes, no refactors, file moves or renames. The job was repair, not a rewrite. The fix rounds that followed the adversarial reviews added no dependency but departed from the rest where a finding required it:
  - The first fix round removed three unused web dependencies (so the web lockfile changed), renamed one test file whose name overclaimed, consolidated duplicated code, deleted dead code with the tests that only kept it alive, and deleted sixteen documents and an unused image directory.
  - The second did the same on a smaller scale. It deleted code that looked alive and was not (the day-7 conversion letter and its scheduled job, an email template nothing sent, five coordinator triggers that were never called and four more whose work no agent accepted, the `agent_performance` writer, a stub customer-email method, an intake-funnel script with its test) together with the tests that only kept it alive. It renamed the pool of sample specs `test_build_specs.py` (it is data, not a test) to `coordinator/sample_build_specs.py`, and removed a delay that held every AI reply back so that it would not feel instant.
- Name the worst code in the area, and end the report with what was not reviewed and what was not verified.

This document does not claim an independent human security review. None is described in the reports it was assembled from.

## What was done, in order

1. **An allowlisted export with fresh history.** The public tree was built from an explicit allowlist of paths taken from the private repository, not by deleting from a copy, and its history starts over: it contains no commits from the private repository.
2. **A scrub for secrets, personal data and customer data.** The exported tree was scanned for credentials and personal data, and anything secret-shaped was removed or rewritten, including test fixtures, which now assemble such values at runtime. Real customers and their sites were replaced with invented names and sample copy, stock photos were replaced with generated placeholders, and several documents and scripts tied to private infrastructure were removed. The private organisation name and the hosting provider's project and service ids became environment variables. The result was scanned with gitleaks and with a denylist of secret and personal-data patterns; "Secrets in this repository" in [THREAT_MODEL.md](THREAT_MODEL.md#secrets-in-this-repository) states what the gitleaks scan covers.
3. **Component review.** Each area was read by its own agent: web authentication, sessions and security headers; the Harbor companion; web routes, schema, services and mail; the v2 build engine; the queue worker; the coordinator, monitor and ops code; the legacy v1 engine; and the scripts, hooks, CI and roadmap executor. Fixes carried tests; for several areas the reviewer also reverted a fix to confirm that its new test then failed. Each reviewer also named the worst piece of code in its area; the largest of them are listed at the end of [ARCHITECTURE.md](../ARCHITECTURE.md).
4. **A cross-cutting security pass** over the web application (spend bounds on every route that can cause a model call, outbound request guards, the development bypasses, transport settings) and another over the Python side (secrets flowing into child processes and error tracking, the deploy path, the URL guards).
5. **A tests round** over the three suites. Both the web and the Python suites were run with the clock shifted forward by about 400 days, 3 years and 10 years, and under four time zones. Test files were run in reversed and shuffled order, and the web suite under many shuffle seeds. A fresh clone was run in a clean Python 3.12 virtual environment with only the two requirements files installed, and again with a `PATH` lacking `node`, `git` and `psql`, where tests skip with a reason instead of failing. The Playwright UI suite was run against a throwaway database and extended with specs for the browser behavior the review changed. Tests that asserted nothing, or that passed against broken code, were rewritten, and a number of tests were mutation-checked (the code under test was broken on purpose to confirm the test then fails). The real defects this round found were a sample data generator that emitted fixed "upcoming" dates, test fixtures that wrote to a developer database, and order-dependent tests.
6. **A documentation round.** Existing documents were checked against the code and corrected where they disagreed; [ARCHITECTURE.md](../ARCHITECTURE.md), [CONTRIBUTING.md](../CONTRIBUTING.md), [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md), [docs/README.md](README.md), [SECURITY.md](../SECURITY.md) (since split into that file, [THREAT_MODEL.md](THREAT_MODEL.md) and [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md)) and this file were written. The writer of each new document checked its statements of fact against the code.
7. **Adversarial review, in six rounds.** Each round gave four fresh reviewers the repository with a role and a report format, and no account of the code or of the earlier rounds' findings. The four roles:
   - A staff engineer checked every README, ARCHITECTURE and SECURITY claim by running the code, and looked for the worst code. This reviewer ran the three suites, booted the app, drove the payment, signup and crisis paths with curl against a local server, built crafted specs with the generator, ran the worker's SQL on a scratch Postgres, and mutation-tested the tests the documents cited.
   - An outside reader started from the README, opened the files it points to, and recorded what it could and could not believe from that.
   - A hunter looked for secrets and personal data.
   - A newcomer followed only the README to get the application running.

   What the rounds found:

   - In the first two rounds the numbers in the documents mostly reproduced, and several headline guarantees turned out to hold one layer below where a user meets them.
   - In the fourth round the README's claims and every number reproduced; the findings were mostly about availability (what a slow, huge or malformed input does) and about gates that passed when they should have failed.
   - In the fifth round the README and the documents were again accurate. The staff engineer's findings sat where two components meet: a rule kept by the route that opens a payment and not by the webhook that applies it, a wrapper that closed a connection its thread still needed, a worker image whose database client is older than the database it dumps.
   - In the sixth round the test counts reproduced again. The findings sat in the identity and payment paths, in the admin pages' use of Railway and of the worker's variables, in the generator's parsing of spec text, in the executor's handling of a conflicted stash, and in copy that promised a review turnaround and personal replies.

   How the fixes were made:

   - A fix round followed each review. Each fix was given a test that was run against the old code and shown to fail, except where the old code could not run it, and the real path (a local server, the worker's SQL on a scratch database, the generator on a crafted spec) was run again.
   - From the second fix round on, a stricter rule applied, because the second round's findings sat at the seams between components: for every invariant a fix touched, list every writer and every reader of the state it depends on across the web application, the worker, the coordinator, the schema (its `ON DELETE` rules and cleanup jobs) and the background jobs, show that none of them can break it, and give at least one test that crosses the component boundary the bug crossed, on a real Postgres where SQL was involved.
   - From the fourth fix round on, each fix was also checked by mutation: the condition it added was removed in a scratch copy, and its test had to fail.

   The first round's findings are under [Found by the adversarial round](#found-by-the-adversarial-round), the second round's under [Found by the second adversarial round](#found-by-the-second-adversarial-round), the third round's under [Found by the third adversarial round](#found-by-the-third-adversarial-round), the fourth round's under [Found by the fourth adversarial round](#found-by-the-fourth-adversarial-round), and the claims that did not survive are under [Claims the documents had to give up](#claims-the-documents-had-to-give-up). The fifth round's findings are under [Found by the fifth adversarial round](#found-by-the-fifth-adversarial-round), and the sixth round's under [Found by the sixth adversarial round](#found-by-the-sixth-adversarial-round).

8. **A security review after publication.** Four reviewers, one per area (web identity and money; web content and outbound requests; the generator, the generated sites and the Python side; the supply chain, CI and the executor), each told to reproduce rather than read, then five fixers on disjoint files, with the same rules of a failing test on the earlier code and a mutation check. Its findings are under [Found by the security review after publication](#found-by-the-security-review-after-publication).

## What the review found

These are the most significant defects that existed in the code as it ran, not a complete list. Severity is the reviewing agent's own rating, not a scored one; where a report gave none, the rating is assigned from the described impact. Every fix and test named here was found in the repository when this file was written. Tests are under `web/tests/unit/`, `tests/` and `compose/tests/`. Several rows in the first sections were incomplete when the earlier rounds recorded them as fixed; they are corrected in place and the gap is described under "Found by the adversarial round" and "Found by the second adversarial round".

**Behavior a reader would notice.**

- Outside development and test the cookies are named `__Host-cas.sid` and `__Host-cas_harbor_trial`. Cookies under the earlier names are not read, so moving a deployment to this code ends its open sessions and conversation links.
- Verification and unsubscribe links land on a page with a button, and nothing happens until it is pressed. The verification mail greets "Hi there,", and a second request within the hour sends no new link (the page says at most one is sent an hour).
- Cancelling a Harbor subscription takes a login to the account; the paying cookie alone gets a page that says to log in or to choose a password.
- Support answers drafted by the sweep or the coordinator wait for an operator's approval (an `UPDATE`; there is no admin page) before the support chat serves them.
- `builds.railway_database_url` is stored masked; the password is read from Railway.
- The operator's dispatch refuses a captured address that already has an account, a review verdict on a build that is not at preview is a 409, a build's log says the login link is in the email instead of showing it, and a generated site's admin shows fixed error messages.

**Claims the documents corrected.** [THREAT_MODEL.md](THREAT_MODEL.md) cited a real-SDK test of the Sentry scrub that did not exist, said generated sites' public forms all had a honeypot, said forgot-password did the same for known and unknown addresses (the page was the same, the work was not), described the Host-built links of a generated site as login links only, understated the generated site's password-change rule (the first change spends the allowance), listed the crawl's literal checks without the ranges it missed, and said an anonymous dispatch's refusals were repeated under the insert's lock (the verified-account one was not). [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md) said the admin's build analysis "triggers nothing" (it pre-filled the Queue Fix form) and that the sweep's filters "stop links", and described the operator's dispatch and the signup rule without what they allowed (above).

**What was not verified.**

- Nothing ran against Stripe, Resend, Railway or Sentry. Payments ran through signed local events with the Checkout creation stood in for; the Sentry scrub ran on the installed SDK (10.58) and an in-memory transport, not on the lower bound of the package's version range and not against a Sentry server.
- Concurrency cases were reasoned, not run: two anonymous dispatches for one address in flight together, and the webhook's share lock against a verification, a reset, an account deletion and a signup. Only the dispatch against a verification was run. The hourly verification limit can be passed by requests that arrive at the same moment, and several web instances were not run.
- Whether setting `SITE_ORIGIN` makes Railway redeploy the service, and so when a generated site first reads it, could not be checked here ([KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md#build-worker)).
- Not looked at in a browser: the payments card, the cancel page, the 409 verdict page and the two admin panels (their rendered HTML is asserted). The verification, unsubscribe and verify-email-sent pages were looked at in Chromium only; other browsers accepting `__Host-` cookies, and a production boot over HTTPS, were not tried.
- The timing residual was measured on a local socket, not against a remote database.
- The executor changes ran on macOS (BSD `find`) only; the workflows did not run on GitHub, and the gitleaks test skips in the CI `python` job, which has no gitleaks binary. The crawler's new ranges were not run through the system resolver.
- While one fixer proved its test against the earlier crawler code, the old code tried to connect to the special-use addresses in the test's table (unroutable and documentation addresses); nothing answered, and the test now refuses every socket.

The thread found its connection closed and deleted nothing, so the project ran on; the read-only session ended at the first `COMMIT;` in the text, so a second statement wrote. The thread now cleans up on a connection of its own, and `query_readonly` runs exactly one statement in a read-only transaction. |

### Found and left in place

The fix round did not fix these; each is a limitation of the published code.

- The preview address is public and indexable, and the worker emails it to the customer, with a login link, before any review.
- Customer databases are created from a `postgres:15` image with no Railway volume (`provision_postgres` in [deploy.py](../cli/deploy.py)). Whether their data survives a restart or redeploy is not established here, nor whether the worker can reach each database for its daily backup. The health monitor drops an app from its registry after ten consecutive failed check cycles, and the app's backups stop with it.
- A payment that completes while its build is not at `preview` and approved, or for a build another session already paid for, is logged as an error and, where the customer is known, recorded; nothing publishes the site or refunds the charge.
- A reviewed build that is not a Harbor build (queued by the operator or the coordinator, or from the legacy intake) can be taken live by its owner without payment, and a build whose Harbor ancestor had already been deleted when `builds.is_harbor` was backfilled is not marked as a Harbor build.
- The admin review routes filtered only on the build id, so a verdict and its customer email could be issued for a build that was not at preview; the worker reset the verdict when the build next arrived at preview. (Fixed after publication: a verdict is now recorded only at preview, see [Found by the security review after publication](#found-by-the-security-review-after-publication).)
- Publishing by the owner requires a recorded review verdict, not a particular reviewer, and the customer is emailed the preview address and a login link when the build arrives at preview, before that verdict exists. The customer-facing copy now says so.
- The worker's lease is best effort, and its writes other than status and the Railway columns (log rows, screenshots, the stored artifact, cost) are keyed by build id only, so a leftover thread can overwrite them until its next stage write stops it. The project an attempt creates is tracked in the worker's memory until the build reaches preview: if the worker is killed in between, no row names it and it keeps running until an operator or the opt-in orphan sweep removes it. A preview superseded by an in-place redeploy is no longer referenced by any row and is left for the operator, and a Railway delete that fails is logged and not retried.
- The executor's guard and gate bound what a branch can get merged, not what a session can do. The session is not sandboxed and can write outside its worktree; a branch may still weaken a test, or code a test imports, that it is allowed to edit, and a test that ends the process early passes the gate. The gate needs python3 3.11 or newer and pytest 8.4 or newer, fails closed without them, and does not read a pytest configuration kept in `pyproject.toml`, `tox.ini` or `setup.cfg`.
- Without `ANTHROPIC_ADMIN_KEY` the coordinator budgets against the worker's own ledger, which omits web-tier spend and records an estimate, not a measurement, for each agent task; its model-call meter counts calls at fixed per-model estimates, not tokens, and failure-triage calls are not written to the ledger (at most five cheap-tier calls per tick that later ticks do not see).
- Other limits of the second round that stay open, in the words of [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md): the janitor never deletes a failed build that records a Railway project; the two-hour retry budget is kept in each worker's memory; the daily spend cap is 0 under the v2 engine and loses a failed build's cost when the janitor deletes its row; one subscription covers every Harbor build on an account; a payment for a build that is not publishable at that moment is recorded and not matched to the keeper row; the review browser's guard is not pinned (a name resolves twice, and WebSocket and WebRTC traffic does not pass it).

## What changed in behavior

Intentional differences from the production system a reader may be comparing this code against:

- **Limits were added** where none existed: three-bucket limits on login, signup and password reset; per-address and shared ceilings on anonymous chat; per-address, per-trial and trial-mint limits and a shared dollar cap on the Haven conversation; a daily model-call ceiling per customer and per process; hard conversation lengths; build-start limits (two active builds, ten starts a day and three manual retries per build for a customer); and bounds on crisis alerts (one email per identity per 30 minutes, ten an hour per process). Every limiter holds at most 20,000 keys, and the account forms accept bodies of 10 KB. The numbers are in [THREAT_MODEL.md](THREAT_MODEL.md).
- **Defaults now fail closed.** An unset `NODE_ENV` is production, and a placeholder, short or obviously stand-in `SESSION_SECRET` stops the server from starting. Webhook endpoints with no secret answer 500 instead of accepting calls. With no `ADMIN_EMAIL` nobody is admin. The coordinator treats unknown spend as spent, so a tick whose spend cannot be read has a budget of zero, and it rejects unanswered approvals. The worker's daily spend check refuses new builds when its query fails. A dry run, an analysis-only mode or a blocking gate is turned off only by `false`, `0`, `no`, `off` or `disabled`, and any other value, an empty one included, leaves it on; a switch that turns something on needs `true`, `1`, `yes`, `on` or `enabled` (`coordinator/envflags.py`). Several development conveniences used to key on `NODE_ENV !== 'production'`, which treats an unset or custom value as development; they now require exactly `development` or `test`. The database TLS decision and the boot warning about an unset `BASE_URL` follow the same rule: an unset value gets TLS and the warning.
- **Secure cookies and HSTS** are sent for every environment that is not development or test, and error text reaches the client only in those two. The security headers are sent on every response, files from `web/public` included.
- **A crisis message on the Haven turn endpoint is answered ahead of the session store, the cookie lookup, the rate limiters, the email gate and the cost caps.** The reply does not wait for the database; the turn is stored and the operator alerted after it.
- **The crisis scan matches more, and its replies changed in three ways.** It was rewritten and measured (the numbers are in [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md)). The reply to a medical emergency now says to call 911 or the local emergency number before anything else. The reply to a threat to another person has its own opening and an emergency-number sentence. The sentence added for abuse now reads "you or someone else". The reply for suicide, self-harm and abuse alone is unchanged, and no clinician has read the new wording.
- **A reset link is never shown on a page,** and the app no longer re-verifies unverified accounts at boot.
- **A signup changes no existing account, and verification settles the credentials.** The password and name typed at signup are kept in that browser's session and written only to a row the signup creates; an unverified row is not changed and its links are not voided. (The pre-release fix wrote the claim to an unverified row and voided its links; the security review after publication found that a stranger could use that against the owner and stopped it.) Confirming a verification link, on the page it opens, sets the password and name from that browser's own signup, or, when it has none, sets an unusable password and sends the person to choose one. A verified account is never touched, the response is the same in all three cases, and the address is no longer put in a redirect URL ([auth.ts](../web/src/routes/auth.ts)). A completed password reset also verifies the account.
- **A paying trial browser keeps access to the site it paid for.** For 30 days from payment the trial cookie lets that browser see the one website it paid for and read and continue its conversation; it creates no account session. (It could also cancel the subscription until the security review after publication; cancelling now takes a login to the account.) The account is reached by setting a password through the emailed reset link, and the Stripe success URL no longer carries a Checkout session id.
- **A customer's own publish of a Harbor site needs a subscription, and so does the source download.** Whether a build is a Harbor build is a column on the build (`builds.is_harbor`), set when a Harbor conversation dispatches it and copied to every build made from it by a trigger, so deleting an ancestor build, which the worker's cleanup and the admin and ops routes do, does not change the answer. For a Harbor build the approve route promotes a reviewed preview only when its owner's subscription is `active`, `trialing` or `past_due`, and otherwise sends the owner to the make-public page; the keeper row stores Stripe's own status word, so `unpaid`, `paused`, `incomplete` and `incomplete_expired` do not count. The owner can download the site's source for a `live` build or for one the owner could publish, no longer at any preview. A conversation dispatches one build without an operator (`handoff_at`). A build that is not a Harbor build is unchanged, and so is the admin's approve.
- **Every arrival at preview puts a build back into review, and every requeue clears the verdict.** The worker sets `review_status` to `pending` (`ai_review_queued` under `CAS_HARBOR_AUTO_REVIEW`), clears the reviewer, notes and report columns, and, unless `CAS_HARBOR_AUTO_REVIEW` is set, emails the admin on each arrival rather than once per build. Each statement in the web app and the ops API that puts a build back in the queue clears the same columns, and so does the build-status hook when it lands a build at preview.
- **The worker claims the oldest queued build regardless of tier.** `builds.tier` now only selects the build timeout. A build the worker fails gets a dead-letter row and a customer email on every path, including the restart and thread-crash paths that used not to (when the database cannot take either write, the build is left as it was and no email goes out), and a build that an admin killed during deploy is no longer announced as ready for review.
- **Sessions** end 30 days after login whatever their activity, a password reset ends the account's other sessions, passwords are limited to 72 bytes, and account deletion cancels a running Stripe subscription at period end and deletes the account's Haven trials with their turns and notes.
- **The status webhook cannot set a build live,** and the worker cannot either; promotion is the approve route or a completed Stripe checkout.
- **A generated site's password change asks for the current password,** unless the account has none or the person signed in by a login link in the last 15 minutes. A custom page whose path names another origin, or whose id is the name of one of the engine's own views, is refused, and the generated site's protected form pages guard every verb.
- **The coordinator makes no model call under dry run, and every model call is metered.** Today's spend comes from one configured source with no fallback: if it cannot be read, the tick has zero dollars and zero calls. Failure triage, the support-answer draft and each draft of the failure-KB sync are granted one at a time by a per-tick `ModelCallMeter`, and an `Actuators` built without a meter grants none. Failure triage no longer writes a build row or a knowledge base without passing the actuator, and under the default dry run it makes no model call and writes no build row or knowledge base.
- **The roadmap executor rejects a run with no committed change,** a dirty worktree, a branch that does not descend from the commit it was created from, or a change to a protected path, including a rename or deletion of one. The protected set includes everything under `scripts/`, the test-runner configuration, package manifests and npm configuration, anything under a `node_modules`, and top-level Python modules. The tests run on a fresh checkout of the one commit the session left, with a pinned pytest command line, and that commit, by hash, is what is merged; a branch that moved after its tests is refused. Before it pushes, the executor waits for the ops API to report no build queued, building, testing or deploying; it starts no session and pushes nothing when the API does not answer its build counts or today's spend, and it commits only an item's status change, through the pre-commit hook.
- **The support chat no longer writes model answers to the shared answer table.** Rows still arrive there from the weekly Harbor sweep and the coordinator; they are model-drafted from visitor text, stored as pending and served only after an operator approves them (since the security review after publication; see [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md#harbor-companion)).
- **Customers no longer receive cost figures** from the build API, and worker error text and logs shown to them pass through a redaction backstop.
- **The feature-request flow has no UI entry points.** The routes and code remain; the only way to queue a request is the development bypass, and no worker builds its requests.
- **The terms page text was rewritten during review** to match the single subscription. The displayed effective date was left as it was, and the text has not had legal review.
- **Haven's answers about privacy changed.** The persona states what is stored and no longer claims encryption, therapist-level confidentiality or scheduled deletion.
- **Customer apps no longer receive the platform mail key.** Without `GENERATED_APP_RESEND_API_KEY` an app has no mail transport and logs a requested login link instead; the worker no longer BCCs a fixed mailbox.
- **Smaller visible differences.** The contact form confirms only when the mail provider accepts the message, and otherwise shows an error with the typed text kept. The preview-password gate exempts only files that exist under `web/public`. A production-mode connection to a database on `localhost` no longer attempts TLS. The product copy calls the free build a preview, not a private one, and the lamp page says anyone who has the address can open it. A second web server on a taken port exits with one line instead of a stack trace. The browser suite refuses to reuse a server already running on its port unless told to.
- **v1 QA tests run in a child process,** and the Python test suite refuses non-loopback network access by default.
- **The worker owns a Railway project only for the attempt that created it.** The ids are written to the build row only when the build reaches preview; a failed attempt deletes the project it created and nobody announced, never one a row records; the janitor deletes failed builds' rows and no project, and keeps a build that something else depends on. A claim needs a free worker thread. A deployed app that never answers `/health` is retried, not previewed. A status write with no attempt token is refused, the daily spend cap counts a retrying build, and the retry budget runs from the first attempt of a series. Cooperative cancellation reaches the v1 fix loops and model calls, with one key per attempt. After a healthy `/health` the worker's login probe signs in by `POST /magic/consume`, with the token in the body, and uses it up.
- **Probes resolve a name once and connect to the address they checked.** The monitor and deploy probes send through `guarded_session`, which refuses a URL that urllib3 and the standard library read differently, refuses a host with a non-public address and checks every redirect hop; the review browser is not covered. The health monitor's loop survives a database error.
- **The faithful-copy crawler never parses on the web process's event loop.** Its HTML is parsed by single-pass scanners in a worker thread that is killed on a deadline, every request is abandoned 15 seconds after it starts, and page paths and media URLs are capped.
- **A generated site publishes only what the spec says.** A model's rows are public only where the spec sets `public_listing_path` or an archetype's page reads the table; a page that shares a model's name no longer publishes it. A row a visitor submits is stored unpublished until the admin publishes it, and each submitted value is checked first.
- **The coordinator's automatic rebuilds are bounded, and its ticks lose no events.** A rebuild is refused for a deterministic failure, at the customer's build-start limits, at two per parent in 24 hours and at three per root build in 7 days; a tick reads from the previous tick's start, and a restarted worker resumes from the last completed tick.
- **Generated sites log no query strings, and a spec that cannot be protected is refused.** A page listing several roles opens for any one of them; the contact form, its handler, its table and a listing's order come from the model; a protected page whose path something else answers without a login refuses the build.
- **Customer-facing copy says what the code does.** Pages, emails, support answers, the intake prompt and the persona describe a site as built from a library of tested building blocks and reviewed before it goes live, name no reviewer, and say the preview address is emailed when the build is ready. Requests the app refuses render their real status (403, 404, 413, 429) instead of "500", and the lamp page shows a notice for each state a subscription can be in. The artificial delay that held every AI reply back by 0.8 to 2.4 seconds was removed.
- **Shipped defaults differ from a deployment.** `web/.env.example` enables Harbor, because a fresh checkout needs it for the conversation to reach a build, and the roadmap executor's config ships with `"enabled": false`.
- **Probes and provider calls have a deadline and a byte cap.** A health check that does not finish its answer in time is a failed check, and a body larger than the cap is cut at the cap; before, one app could hold the loop. The review browser's pages have timeouts and a screenshot is cut at 16,000 px.
- **The coordinator treats unknown as unknown, and nothing in it commits to a repository.** A cost report it cannot read, or that lacks today, gives a tick no budget; a failing agent and category pair is skipped until a probe succeeds; filing an approval request is a permission; the GitHub client, the learning loop and the three commit playbooks are gone.
- **An enabled executor needs `ANTHROPIC_ADMIN_KEY` on the web app,** because it starts a session only on a complete cost report; its guard refuses non-ASCII paths and the deletion of any test file, its gate runs `compose/tests`, and an interrupted merge is settled from a journal.
- **The build request and the legal pages say what the code does.** A conversation that holds nothing the extraction may read is told so (409), a failed model call is 502, a refusal on a JSON route is JSON, the privacy and terms pages state the cookies, what is stored and what deletion leaves, and error-tracking events carry no request bodies or cookies.
- **A spec is checked for the shape and size of what the engine reads, and a generated site's `/health` includes its home page.** `validate_spec` returning nothing now means `resolve_spec` accepts the spec too: a wrong-typed value is a refusal that names the position, not a traceback or a page that throws, a spec over the size bounds is refused before anything walks it, and a site whose home page did not render when it started answers `/health` with 503 `home_page_error`, so the preview is not announced. The build report's `warning: ` lines are the engine's alone and come first; the spec's own notes follow as at most 40 `spec-warning: ` lines. A refused link-lint destination is reported without the address it resolved to.
- **A payment is applied only where it can be, and a payment that cannot be is not silent.** A second trial's session for an account whose keeper already has a subscription, a trial that is not the build's own, and a keeper's second payment while the first still publishes are recorded in `harbor_subscriptions`, leave the keeper row, the trial and the build as they were, and mail the operator; nothing is refunded and Stripe is never called. The other cases where money arrives and the site cannot go live (the build is missing or no longer publishable, no account can be found) send the same mail. A released trial's cookie speaks as a keeper only if its own trial was promoted into that keeper.
- **The executor takes back a merge it gave up on only where it is safe, and the schema file is held to the rule the `live` statements are.** `take_back_merge` acts only on the target branch, only on the loop's own merge and with `git reset --keep`; otherwise the merge, its journal and the stash stay and nothing starts. The merge guard also protects the Tailwind and Playwright configuration, the Dockerfiles, the Railway and compose configuration, `requirements*.txt`, the `Makefile` and the schema file. Any row change in `schema.sql` needs a reason of its own, and none may name the status `live`, whatever the comment.
- **The engine refuses more of what would build a site that fails, and says so before the deploy.** A spec is refused, with a message that names the position, when a column the engine reads with a fixed meaning has a type it cannot work with, models belong to each other in a ring, a public form page names no column a visitor may fill in, or a stock photo of a specific person or place is named; a seed value or a default that Postgres would refuse is left out with a warning. A page that lists roles requires a login, a row whose flag has no value is public nowhere, a visitor sorts a public list only by a column the list shows, and the build report says whether the external-URL lint was skipped, ran or failed. Every public form page of a v1 spec needs `allowed_fields` (three fixtures gained it).
- **The coordinator says what became of each action, and the worker and the monitor stop leaving things behind.** An agent's result reports each alert, finding, KB entry, rebuild and approval request as sent, recorded, queued, dry_run, refused or failed; `query_readonly` runs exactly one statement in a read-only transaction; a tick with no budget still runs the tasks that cannot make a model call. A thread the supervisor gave up on deletes its project on a connection of its own, a crashed deployment whose log cannot be read is retried once instead of being called the app's fault, and a dump whose `pg_dump` is older than the server is refused with both versions named. The credentials of a URL are masked by one rule, `scheme://***@host` (it was `scheme://user:***@host`), in the worker, `cli/deploy.py` and the failure knowledge base.
- **Smaller visible differences.** `STRIPE_BYPASS` is an on/off switch: `false` leaves the bypass off. The contact form answers 400 when it refuses a message, and the home and About page titles carry the brand once. Every password hash has one cost. `POST /account/delete` is rate limited. The page-view log keeps the Referer as a path. The status hook's review state follows `CAS_HARBOR_AUTO_REVIEW` like the worker's, and it accepts `preview_url`.
- **Content is meant to be fictional.** The sample customers and their sites were replaced with invented names and sample copy, and the stock photos are generated; sample sites will not match what production served. Nothing in the repository can show that a business name or a place in a test string is invented: [test_no_customer_markers.py](../tests/test_no_customer_markers.py) checks structural markers, not names ([KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md)).

## What was not verified

- **No live calls, with two exceptions in the fix rounds.** Nothing was sent to Anthropic, Stripe, Resend, Railway or the error-tracking service as part of the review, except twice by accident while old code was being run to prove that a new test fails on it. A scratch copy of the old make-public route made one request to Stripe's API with an empty key (rejected with a 401; the payload was a fictional `@example.test` address), and a scratch run of the old worker, whose test network guard had been lifted at the end of the pytest session while a build thread was still running, made one request to the model provider with a made-up key and fixture text (rejected with a 401). No credential was involved in either. Afterwards the Python tests' network guard was changed so that it is never lifted, and the real-database web test refuses any non-loopback HTTP, HTTPS or `fetch`. Model behavior, payment flows, mail delivery and every provider-specific response shape are exercised against test doubles only. The subscription cancel route was exercised only up to the call to Stripe, Checkout with `customer_email` and no pre-created customer rests on Stripe's documented API and a mocked SDK, and the contact form's success path was run against a local stand-in for the mail provider, not the provider.
- **The worker image was not built,** and no deploy was run (the `worker-image` job of `test.yml` now builds it; it had not run on GitHub when the release was prepared). In particular `railway up` with the scrubbed environment was not run against the real Railway CLI, and the URL guards and the QA child process were not run on the pinned Linux image. Everything described under the worker was run on a developer's macOS machine.
- **Customer databases and backups.** How Railway treats a database service created without a volume is not established, and nothing was run against Railway, so whether the worker can reach a customer database to back it up is unknown. The restore (one transaction, stop at the first error) and the dump flags were run on a local Postgres 15 only, not on a customer-app schema, and whether production ever had two apps with the same name, which the old backup layout overwrote, cannot be told from the repository.
- **Concurrency.** Two simultaneous deliveries of one Stripe event, the lock order between the checkout and subscription handlers, the lock order of account deletion against the payment webhook, and the race between two dispatches of one conversation were reasoned from Postgres semantics and tested with mocked orderings, not reproduced with concurrent transactions. The two-process race on a build lease was reasoned about, not reproduced; the claim-and-lease gap inside one process is now run against a real database with a held tail. Two worker processes against one database were never run.
- **In-memory limits across instances.** Rate limits, the model-call budget, the trial-mint limiter and the crisis alert bounds were reasoned about and tested for one process; the weekly sweeps' claim in `platform_metadata` was tested with concurrent claims on one connection pool, not with two web processes. Behavior with several web replicas is described in comments and in [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md), not observed.
- **The generated-site tests** boot a built site against Postgres. They were run on a developer's macOS machine with Node 25 and a Python 3.12 virtual environment, not on the CI image, Node 24 or the worker's Python 3.10. Five modules boot a site (`test_compose_end_to_end.py`, `test_smoke_suite.py`, `test_generated_app_guards_e2e.py`, `test_generated_site_security_e2e.py`, `test_generated_site_publication_e2e.py`); the CI workflow was changed so that they run there, and no CI run is claimed. The tests marked `v2_integration` were run once, by the agent that rewrote them, in a scratch copy on the machine the review ran on (16 passed), and not otherwise; the worker's and the deploy path's probes against the changed `/set-password` route, and its form in a browser, were not run. What Resend's error responses contain, whether the hosting platform's own request log records query strings, and the cause of one run of 17 setup errors (a port race, inferred from timing and a simulation) were not established.
- **The pinned crawl transport over real HTTPS.** Its tests use plain-HTTP servers on loopback; certificate handling, SNI and real DNS were not exercised.
- **The roadmap executor** was run only against a fake agent, a stand-in for the ops API and a local bare repository, never with a real agent session, a real remote or a real deploy. Whether a real Claude Code session leaves untracked files in its worktree, which the guard treats as a reason to reject the run, was not tried. The guard's branch for a diff it cannot compute has no test. Nothing ran under launchd, with a real `gh`, or on Linux.
- **The crisis scan's patterns and the wording of its replies had no clinical review.** No clinician, crisis-line worker or person with lived experience has read the patterns or the replies, including the 911 line for a medical emergency and the opening and emergency-number lines for a threat to another person that the third round added. Every set the scan was scored on was written by a language model, not drawn from real conversations, so the numbers measure agreement with those authors and are not an estimate of how well the scan finds what people write.
- **Error-tracking scrubbing** was tested against one SDK version; the version range in the requirements allows others, and an installed newer release was not re-tested.
- **Interpreters.** The measured suite results are from a Python 3.12 virtual environment (the version CI uses); the system Python 3.14 cannot install the pinned requirements, so no full-suite result comes from it. Some probes in the fix rounds ran on the system Python 3.14 (for example the check that a top-level `ipaddress.py` shadows the standard library under pytest) and the earlier rounds' static checks ran under it; the static analysis run in the fix rounds (`bandit` and `pip-audit`, through `scripts/run_python_security_audit.sh`) ran from the 3.12 virtual environment. The worker image runs Python 3.10, and Python below 3.11 was checked only for the executor gate's refusal (`python3 -P` exits with an error). The `bandit` gate is medium severity and confidence; the lower-rated findings it also reports were not triaged. `pip-audit` and `npm audit` depend on the advisory databases on the day they ran.
- **CI results and browsers.** CI runs on GitHub's hosted runners on every push to the default branch and on every pull request, and the badge in the README shows the result of the latest run on the default branch; this file claims no result for it. The fix rounds added steps to the workflow (one builds the sample generated site, one installs Python 3.12 and the worker requirements in the `ui` job and runs the web integration tests against a real Postgres) that have not run on a hosted runner. The Playwright suite was run locally in desktop Chromium only: no mobile viewport and no other browser, and it was not re-run after the second round's copy changes (a screen-reader spec still expects the old chat subtitle). Pages changed in the second round were fetched and read as text, not looked at in a browser. The quickstart was also reproduced locally without Docker against a throwaway database. The Mermaid diagrams in [ARCHITECTURE.md](../ARCHITECTURE.md) were not render-tested.
- **Browsers.** The web security pass included headless-browser checks against a local server, on a limited set of pages. Other pages, other browsers and assistive technology were not re-tested, and the dated accessibility audits in [docs/audits/](audits/) were not re-run.
- **Smaller gaps in the first fix round.** The session-secret rule was sampled against random values and not proven never to refuse a good secret. The 30-day cookie window was checked by row values and unit tests, not by waiting. The TLS decision for a database URL with no host (`PGHOST`) is unit-tested only. A web server started beside a listener bound to one specific address was not tried. The web test files are not type-checked, because the web `tsconfig` covers `src` only. The log line for an app the monitor stops watching is untested. For two fixes, the coordinator's scan for side effects outside the actuator layer and the web server's handling of a taken port, the evidence against the old code is a probe or a before-and-after run, not a failing test, because the old code could not run the new test.
- **Smaller gaps in the second fix round.** Requests through `guarded_session` were exercised over plain HTTP on loopback, not against a TLS listener (SNI and certificate checking on a pinned address are untested), and the connection override was run on one urllib3 release although the requirements allow older ones. The crawler was never run against a real remote site or through the live admin route under Express, and its super-linearity probe over the web source's regular expressions is a heuristic: a pattern it did not flag is not proven linear. The executor was never run with a real agent session, `gh` or a remote, nor with the real repository's suites inside the loop, nor on Linux; the PostCSS and `ipaddress` shadowing vectors are probe results, not repository tests, and a fresh `npm install` inside the gate without an existing `web/node_modules` was not tried. The backfill of `builds.is_harbor` was tested on fixtures, not on production-shaped data. The coordinator ran against stubs of the model client and the cost report. The Playwright accessibility specs were not run, so the keyboard and screen-reader reviews remain static.
- **What the adversarial reviewers themselves did not verify.** In the first round the reviewer who ran the suites did not run `npm audit` or `pip-audit`, the CI workflows, the Docker path, the worker image, or anything against Railway, Stripe, Resend or Anthropic, and read only parts of the legacy v1 engine and the admin routes; the reviewer who followed only the README did so without Docker and with a warm package cache. In the second round the reviewer who ran the suites did not reproduce three of its findings (the failed redeploy, the health gate, the claim gap) and checked the role-guard and hard-coded-SQL findings in emitted source, not under Express or Postgres; the reviewer who read the repository from the top ran nothing.
- **Smaller gaps in the third fix round.** The Sentry scrub was tested on hand-built events and never against Sentry or the SDK's real event shapes. The scan's timing was measured on macOS under load, not on Linux or in CI. The classification of Railway mutations (`RailwayOutcomeUnknown`) and of deployment end states rests on the Railway API as the code and its test doubles model it. The "Paid keepers" view was fetched as HTML as the admin and compared with the database, not looked at in a browser, and the make-public form's Tab order was walked in a browser for the fixed-address branch only. The lock order of account deletion against a keeper's own build request was reasoned from Postgres semantics, and the deadlock between them is described, not reproduced. The translator-to-engine tests skip without node and `web/node_modules/typescript`; the CI `python` job installs the web dependencies (`cd web && npm ci`) before it runs `compose/tests`, so they are meant to run there; the 648-case probe is a scratch script that is not in the repository.
- **Smaller gaps in the fourth fix round.** The Sentry fix was checked with the real SDK and an in-memory transport, not against a Sentry server, and the worker's Sentry setup was not checked. Nothing was run against the worker image (Python 3.10, Playwright 1.42), Railway, Resend or Anthropic; answer shapes come from the code and local listeners, and whether the Anthropic cost report always carries a bucket for the current day was not checked. The executor was run on macOS with bash 3.2 only: not on Linux or bash 4 or 5, not under launchd, with the real agent CLI, a hosted remote or `gh pr create`; the whole watchdog was deliberately never run with `"enabled": true`, and signals inside the merge section were not tried in parallel mode. The destructive-DDL tokenizer was not compared with PostgreSQL's own parser. The coordinator's constructor rule and its scan cover `coordinator/` only, `except Exception` handlers with a body other than `pass` were not reviewed, and the worker does not surface `spec_warnings_omitted` in the build log. The make-public email and page sentences were checked as text, not through a paid flow, no test drives two concurrent dispatches through the new release path, and the privacy and terms pages have had no legal review.
- **What the fourth round's reviewers did not verify.** Docker option A, CI on GitHub, `npm audit`, `pip-audit`, bandit and gitleaks (no network or tools); anything needing Railway, Stripe, Anthropic or Resend; the generated-site tests (102 when the round ran, 103 in the final tree) and the opt-in end-to-end module (they need a built sample site and `npm install`); Node 20 or 24, Linux and the worker image; two worker processes; most of the v1 engine, `harbor_to_compose.ts`, `site_copy_parse.ts`, `svg_sanitize.ts` and most of `admin.ts`; and every claim that needs the private history. - **What the generator's fix did not verify.** Linux, Node 20 and the worker image; a real Railway deploy; `verify_health` against a live URL (it refuses loopback, so only `health_response_ok` was checked, on the real answer); POST handlers under wrong types; two wrong values at once; strings between 20,000 and 100,000 characters at each position; and the opt-in end-to-end module. The matrix covers the positions in its ten fixtures and the extras taken from a run of the engine that recorded every key it read, so a key the engine reads only on a path no fixture takes is not covered, and most emitters in `compose/build.py` and `compose/intake.py` were not read line by line (the matrix stood in for reading). The full run of 25,163 cases, the deletion of 41 and 32 gate conditions, and the booted site with a failing home page were done once by the fixing agent and were not repeated while the documents were written. Seed rows and defaults against column types, the number of engine warning lines and dropped page-data keys are known limits, not fixes ([KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md)).
- **Smaller gaps in the fifth fix round (web and executor).** No real Stripe, Resend or Railway; the title and contact-form changes were checked through the app's test client and not in a browser; the production branches of the account-deletion limiter and the page-view logger were run with `NODE_ENV` switched inside a test, not as a deployed process. A subscription the webhook refuses to apply is not shown to its account's owner and cannot be cancelled by them from the lamp page, and a cookie from before `promoted_customer_id` existed is treated as stale (both in [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md)). The destructive-DDL corpus is hand-derived from PostgreSQL's documented lexical rules and checked by two readers and a fuzz, not by a live parser such as `pg_query`, and both readers assume `standard_conforming_strings = on`; the checker's time grows with the square of a statement's length up to its 2,000-token bound (about 80 s per MiB for a hostile all-`COPY` file, about 11 minutes at the 8 MiB limit; `schema.sql` takes a fraction of a second). `promote_staging.sh` and `sync_staging_from_master.sh` were read and only the first one's rollback guard was added; neither was run. - **Smaller gaps in the fifth fix round (generator).** The wrong-type matrix was not run in full on its case list as it is now (30,039 v2 cases; the last full run was 25,163 cases, in 48 minutes). The booted-site modules ran in a scratch copy that had `node_modules` and skip in the repository; the root `tests/` suite and the whole web suite were not run after the generator changes (the root tests that call the engine and seven web files were), and nothing ran on Linux, Node 20 or the worker image. The worker's seed-row count lint can now log a count mismatch when the engine drops an unfit seed row, and a v2 app that fails to boot is classed `[v2-deterministic]` while the new gate refusals say "Spec validation failed"; the worker's handling of both was not checked.
- **Smaller gaps in the fifth fix round (worker, coordinator and monitor).** The worker image was not built, so the PostgreSQL apt repository's key URL, its fingerprint (typed from memory), `gpg --show-keys` in the base image, the `jammy-pgdg` suite, `postgresql-client-15` and a real `pg_dump` 15 against `postgres:15` were not exercised; the `worker-image` CI job does that and had not run on GitHub when the release was prepared. Two worker processes on one database were not run: the attempt lock and the hand-off were tested with two threads in one process. The 20-run series of the real-database files is 19 clean runs and one run that failed for a full disk. Forty single-edit mutations of the round's worker, coordinator and monitor fixes were run: 39 were caught and one is equivalent. Not fixed: a task that makes no model call is still booked at an estimated model cost in `agent_tasks.actual_cost_usd`; two customer-service handlers that log and return False are not in `effects`; the pipeline thread's reconnected connection is never closed explicitly; `monitor/diagnose.py` still aborts a fix behind a failed snapshot, by design.
